Common reading mistakes

  • "The abstract's number is the paper's result." Abstracts quote the most favorable comparison. DeepSeek-V2's "93.3% smaller KV cache and 5.76× generation throughput" compares against the dense DeepSeek 67B, an end-to-end system comparison and not an isolated MLA ablation (page 07). Before quoting a number, find the table, the baseline, the metric and the setting.
  • "A benchmark gap is a real gap." Ask for error bars: for accuracy \(\hat p\) on \(n\) questions the standard error is \(\sqrt{\hat p(1-\hat p)/n}\) (page 18). DeepSeek-R1's AIME 2024 figures of 79.8% pass@1, 86.7% cons@64 and 90.0% pass@64 are three different quantities, so read which one a comparison uses.
  • "An ablation transfers across labs and scales." DeepSeek's own ablations put MLA ahead of MHA on 7 of 8 comparisons, while Llama 2's 30B ablation found GQA roughly matching MHA; parameter matching, training length and benchmark choice differ (page 07). Small-scale evidence is weak evidence about frontier scale: ST-MoE notes that small models are rarely unstable, so stability tricks are hard to test cheaply (page 11).
  • "If a report gives no reason for a choice, the choice was validated." Technical reports skip ablations. Qwen3's MoE drops the shared expert, and the report gives no reason and no ablation (page 30). Mark such choices "unexplained", not "proven", and say so in an interview.
  • "Read the newest report first." DeepSeek-V4 and V4.1-Flash build on V2 and V3: to see what CSA and HCA replace you need MLA's cache model and V3's expert layout. Read in release order, as the list is sequenced.
  • "Numbers from different papers are comparable." Check which \(N\) (total, non-embedding, activated), which peak (dense or with sparsity) and which unit (GB or GiB) each paper uses. Using the sparse 1,979 TFLOP/s peak instead of the dense 989 halves every MFU you compute (page 04, page 34).
  • "An arXiv link is one fixed document." Versions change numbers. DeepSeek-R1's January 2026 arXiv v2 differs from v1 in places, so cite the version you read (page 24, page 28).
  • "Having read it means being able to say it." Interviews test recall under pressure. After a paper, close it and rebuild one equation or table from memory: the DPO loss, the \(2N + 2N + KN\) memory accounting of ZeRO, the KV bytes per token of GQA.

Interview questions: can you explain it in one minute?

Self-test prompts built from the glossary. Each answer is what you would say in about a minute; try it aloud before opening the answer, and follow the link if any number is not yours yet.

Warm-up Explain the KV cache and how large it is for Llama-3-8B.

Causal attention never changes the keys and values of earlier tokens, so a decode step stores them and computes only the new token's query, key and value. The cost is memory: \(2\,n_{kv}\,d_h\,L\) elements per token. For Llama-3-8B (\(n_{kv}=8\), \(d_h=128\), \(L=32\), bf16) that is \(2 \cdot 8 \cdot 128 \cdot 32 \cdot 2 = 131{,}072\) bytes, 128 KiB per token, so an 8K context is exactly 1 GiB per sequence. Every decode step must also stream this cache from HBM, which is why decode is memory-bound. See page 06 and page 07.

Warm-up What is perplexity, and why is it not comparable across tokenizers?

Perplexity is \(\exp\) of the mean per-token loss in nats: the effective number of equally likely next tokens. It is per token, so a tokenizer that cuts the same text into fewer, longer tokens has a higher per-token loss without being a worse model. To compare models across tokenizers, normalize by the text itself: total negative log-likelihood divided by the number of bytes, in bits per byte. See page 01.

Warm-up Define MFU, and say what value is normal.

Model FLOPs utilization (模型浮点运算利用率) is the model FLOP throughput you observe divided by the hardware's dense peak, counting about \(6N\) FLOPs per token for training. An H100 SXM's dense bf16 peak is 989 TFLOP/s; the 1,979 figure on the datasheet assumes sparsity and halves every MFU if used by mistake. Llama 3 405B reports 430 TFLOP/s per GPU, 43%, on 8,192 GPUs; values from 30% to 45% are typical at scale. See page 04 and page 34.

Core Compare the KV cache of MHA, GQA and MLA with numbers.

Cached elements per token per layer: MHA \(2n_hd_h\), GQA \(2n_{kv}d_h\), MLA \(d_c + d_h^R\). Llama-3-8B with GQA caches \(2 \cdot 8 \cdot 128 = 2048\) elements per layer, so 128 KiB per token over 32 layers; with MHA it would be 4 times that (\(n_h/n_{kv} = 4\)). DeepSeek-V3 with MLA caches \(512 + 64 = 576\) per layer, 70,272 bytes (68.6 KiB) per token over 61 layers in bf16, about 57 times less than MHA at its 128 heads (\(2 \cdot 128 \cdot 128 = 32{,}768\) elements). GQA's savings come from sharing heads, MLA's from a low-rank latent shared by all heads. See page 07.

Core How do you decide model size and token count, and why do labs over-train?

Use \(C \approx 6ND\) and the compute-optimal rule of about 20 tokens per parameter (Chinchilla), so \(N_{\text{opt}} \approx \sqrt{C/120}\). For \(C = 10^{24}\) FLOPs that is about 91B parameters and 1.8T tokens. That rule minimizes loss at fixed training compute and ignores inference. If the model will serve trillions of tokens, a smaller model trained much longer gives the same quality for less serving cost: Llama 3 8B saw 15T tokens, about 1,900 tokens per parameter, roughly 90 times the optimum. See page 13.

Core Total versus activated parameters in an MoE: what does sparsity save, and what does it not?

The FFN is replaced by \(n_r\) routed experts plus shared ones, and a router sends each token to \(k\) of them. FLOPs per token follow the activated parameters, \(C \approx 6N_{\text{act}}D\), but every expert must still be stored, so memory follows the total. DeepSeek-V3: 671B total, 37B activated (5.5%), so training FLOPs are about 18 times below a dense 671B model, while the weights still occupy about 671 GB at one byte per parameter (fp8). The price is load balancing (routing collapse, stragglers, overflow) and all-to-all communication under expert parallelism. See page 08.

Core Derive the DPO loss in one minute.

The KL-regularized objective \(\max_\pi \E[r] - \beta\,\KL(\pi \Vert \pi_{\text{ref}})\) has the optimum \(\pi^\star(y|x) = \pi_{\text{ref}}(y|x)\,e^{r(x,y)/\beta}/Z(x)\). Invert it: \(r = \beta\log\frac{\pi^\star}{\pi_{\text{ref}}} + \beta\log Z(x)\). Bradley-Terry needs only the reward difference \(r(x,y_w) - r(x,y_l)\), so the intractable \(Z(x)\) cancels. Substituting and maximizing the likelihood of the preferences gives \(-\log\sigma\big(\beta[\log\frac{\pi_\theta(y_w|x)}{\pi_{\text{ref}}(y_w|x)} - \log\frac{\pi_\theta(y_l|x)}{\pi_{\text{ref}}(y_l|x)}]\big)\): a classification loss with no reward model and no RL loop. Its limits are offline data and likelihood displacement. See page 21.

Core What does GRPO change relative to PPO, and what do DAPO's fixes address?

PPO estimates advantages with a learned critic, a second model as large as the policy (a 7B critic adds about 112 GB of training state at 16 bytes per parameter). GRPO samples a group of responses per prompt and uses the group's mean reward as the baseline (normalized by the standard deviation), so it needs no critic; the clipped ratio and the KL term stay. At scale, runs suffer entropy collapse and batches full of zero-advantage groups, and DAPO's four fixes target these and related problems: clip-higher (against entropy collapse), dynamic sampling (drop groups whose rewards are all equal), a token-level loss (normalize by total tokens, not per sample), and overlong reward shaping (against truncation noise). The reward is often a verifier (RLVR). See page 24.

Core How many bytes per parameter does mixed-precision Adam need, and what does each ZeRO stage shard?

bf16 weights (2) plus bf16 gradients (2) plus fp32 master weights and two Adam moments (4 + 4 + 4 = 12): \(2N + 2N + KN\) with \(K = 12\), so 16 bytes per parameter before activations. ZeRO stage 1 shards the optimizer states across the \(N_d\) data-parallel ranks, stage 2 adds the gradients, stage 3 adds the parameters, giving \(16N/N_d\) bytes per GPU. A 70B model needs 1.12 TB of states, so 17.5 GB per GPU on 64 GPUs at stage 3. Stages 1 and 2 keep the communication of plain data parallelism; stage 3 costs about 1.5 times as much. See page 15.

Deep-dive Why is batch-1 decode slow, and how does speculative decoding help without changing the output?

One decode step reads all weights and the KV cache and does only about one FLOP per byte, far below the H100 ridge of 295 FLOPs per byte, so it is memory-bound and the time is about (weight bytes + KV bytes)/HBM bandwidth. Llama-3-8B in bf16: 16.06 GB at 3.35 TB/s is 4.8 ms, about 208 tokens per second at batch 1. Speculative decoding uses the slack: a cheap draft \(q\) proposes \(\gamma\) tokens, the target \(p\) scores all \(\gamma + 1\) positions in one pass (intensity rises to about \(\gamma + 1\), still far below 295), and an acceptance rule keeps a prefix so that the output distribution is exactly \(p\). See page 17 and page 34.

Deep-dive How does a linear-attention or hybrid layer differ from full attention in memory and in recall?

Full attention caches \(2d_h\) numbers per token per KV head, growing with context. Linear attention keeps a fixed \(d_k \times d_v\) state per head (16,384 numbers for \(d_k = d_v = 128\), the cache of 64 tokens for one KV head), updated by a recurrence, so memory and per-token cost do not grow. The price is exact recall: any causal recurrent model needs \(\Omega(N)\) bits of state to solve multi-query associative recall over \(N\) tokens. Hybrids keep a few softmax layers to repair this (Qwen3-Next: 3 Gated DeltaNet layers to 1 softmax layer), and the gated delta rule adds decay (fast erasure) to the delta update (targeted overwrite). DeepSeek-V4 takes the other route: keep softmax attention but compress the KV cache along the sequence (CSA compresses every \(m\) tokens into one entry and then selects the top-\(k\) entries; HCA compresses every \(m' \gg m\) tokens into one). See page 09.

Deep-dive Explain RoPE and how YaRN extends its context.

RoPE rotates each pair of dimensions of \(q\) and \(k\) at position \(t\) by the angle \(t\theta_i\) with \(\theta_i = b^{-2i/d_h}\), so \(q_t \cdot k_j\) depends only on \(t - j\). Beyond the trained length it fails for two reasons: angles the network never saw, and attention dilution over more keys. Position interpolation divides every position by the scale \(s\), which also squeezes the high-frequency pairs that resolve local order. YaRN treats pairs by wavelength: pairs that turn many times inside the trained window are left alone, pairs with wavelength at least \(L\) are divided by \(s\), and pairs in between are blended. It also multiplies the logits by \((0.1\ln s + 1)^2\) to counter dilution. DeepSeek-V3 uses it to go from 4K to 128K. See page 05 and page 10.
