Decoding & the KV cache

P0 ~55 min Prereqs: 01 Big picture, 03 Attention, 04 Transformer block

A language model outputs only a distribution over the next token. This page covers how that distribution becomes text (greedy, temperature, top-k, top-p, min-p, penalties, beam search), why generation stores and reuses keys and values (the KV cache), and the performance model that explains why producing one token is memory-bound while reading a prompt is compute-bound.

What interviewers probe
  • Sampling fluency: temperature, top-k, top-p and min-p written from memory, their limits, when to use each, and whether the order in which you apply them matters.
  • The KV cache from first principles: why cached keys and values are exact, what exactly is stored, bytes per token from a config, and per-step cost with and without it.
  • The inference performance model: why prefill is compute-bound and decode is memory-bound, and a tokens-per-second estimate for an 8B model on an H100 in two minutes.
  • Batching trade-offs: how batch size moves latency and throughput, why the KV cache caps the batch, and what TTFT and TPOT measure.
  • Correctness traps: why temperature 0 is not reproducible on GPUs, and why speculative decoding does not change the output distribution.

The generation loop

Pretraining teaches the model \(p_\theta(x_t \mid x_{\lt t})\) (page 01). To produce text we run the model in a loop, called autoregressive generation 自回归 or decoding 解码. Picking a token from the model's distribution is sampling 采样, and greedy selection is its deterministic special case. One request goes through these stages:

  1. Tokenize the prompt into ids \(x_1,\dots,x_P\) (page 02).
  2. Prefill 预填充: one forward pass over all \(P\) tokens at once. This is the same computation as a training forward pass with a causal mask, so it is parallel over positions. Only the last position's logits \(z_P \in \R^V\) are needed. As a side effect, the pass stores every layer's keys and values for all \(P\) tokens: the KV cache 键值缓存 (see The KV cache).
  3. Choose \(x_{P+1}\) from \(\softmax(z_P)\) with a decoding strategy (next section).
  4. Decode step: feed only \(x_{P+1}\) through the model, reading all earlier positions from the cache. This gives \(z_{P+1}\), from which \(x_{P+2}\) is chosen. Repeat.
  5. Stop at an end-of-sequence id, a stop string, or the length limit. Chat models emit a dedicated end-of-turn token, so engines accept a set of stop ids (the Qwen2.5-7B-Instruct generation config lists two [config]).
@torch.no_grad()
def generate(model, prompt_ids, max_new_tokens, eos_id, pick):
    """prompt_ids: (1, P) LongTensor; pick(logits) -> (1,) token id (argmax, a sampler, ...)."""
    cache = model.new_cache()                      # empty KV cache, one (K, V) pair per layer
    logits = model(prompt_ids, cache)[:, -1]       # PREFILL: P tokens in parallel, logits (1, V)
    out = []
    for _ in range(max_new_tokens):
        tok = pick(logits)                         # (1,)
        out.append(tok.item())
        if tok.item() == eos_id:
            break
        logits = model(tok[:, None], cache)[:, -1] # DECODE: 1 token in, cache grows by 1
    return out

Two properties of this loop drive the rest of the page.

  • It is sequential in time. \(n\) new tokens need \(n\) forward passes, because each input depends on the previous choice. Training escapes this with teacher forcing, which feeds all positions in parallel. Decoding cannot, and that single fact produces the performance story in Prefill vs decode.
  • The model consumes its own outputs. Training always conditions on true prefixes. At inference a sampled token becomes context for every later step, so the decoding rule shapes the inputs the model sees.
From your jet tagger

Your tagger made one forward pass per jet, and every particle attended to every other particle. That is the prefill regime: one large parallel pass, compute-bound. It had no loop, no notion of "next", and no cache, because with bidirectional attention adding one input changes every representation. A language model uses causal masking precisely so that adding a token changes nothing about the past. That property is what makes the KV cache exact.

Decoding strategies: from logits to a token

At each step the model returns logits \(z \in \R^V\), and its distribution is \(p = \softmax(z)\). A decoding strategy maps \(p\) to one token. Everything below acts on the last position's logits only and is cheap next to the forward pass (\(V\) is about 128K for Llama 3).

Greedy decoding and why it degenerates

Greedy decoding takes \(x_t = \argmax_i z_i\). It is deterministic, needs no random numbers, and is the usual choice for many benchmarks. For open-ended generation it is bad, and the effect is large. Holtzman et al. generated 5,000 passages of up to 200 tokens with GPT-2 Large under different decoders and measured the result [Holtzman et al. 2019, Tab. 1]:

Perplexity is measured by the generating model on its own output. "Repetition %" is the share of generations that end in a repeated loop. HUSE combines human judgments with a statistical discriminator.

Two mechanisms explain the greedy row. First, repetition feeds itself: the probability of a phrase rises with each repetition already in the context, "creating a positive feedback loop" [Holtzman et al. 2019, Fig. 4], and greedy never leaves the loop. Second, human text is not high-probability text: its per-token probability is far lower than that of decoded text (perplexity 12.4 versus 1.5), because people avoid stating the obvious, while a likelihood-trained model's argmax is the most generic continuation [Holtzman et al. 2019, §4.3]. The aim is therefore text with the statistics of human text, which needs randomness with a controlled tail.

Post-trained models are less prone to this, but long generations can still loop: the DeepSeek-R1 model card recommends a temperature of 0.5 to 0.7 (0.6 recommended) "to prevent endless repetitions or incoherent outputs" [DeepSeek-R1 model card].

Temperature

Temperature 温度 \(\tau\) rescales the logits before the softmax. This is the Boltzmann distribution from statistical physics with energies \(-z_i\), and it is applied to language models as in Holtzman et al. (their Eq. 4):

\[ p_i(\tau) = \frac{\exp(z_i/\tau)}{\sum_j \exp(z_j/\tau)} \;\propto\; p_i^{\,1/\tau} \]
Low temperature sharpens, high temperature flattens, temperature 1 is the model's own distribution

Limits: with \(\Delta_i = z_{\max} - z_i \gt 0\) we have \(p_i / p_{\max} = e^{-\Delta_i/\tau}\), which goes to 0 as \(\tau \to 0^+\), so the distribution collapses onto the argmax (uniform over ties). As \(\tau \to \infty\) every ratio goes to 1 and the distribution becomes uniform, \(1/V\). Entropy rises monotonically with \(\tau\). Because temperature raises probabilities to the power \(1/\tau\), \(\tau = 0.5\) squares them: \([0.5, 0.3, 0.15, 0.05]\) becomes \([0.685, 0.247, 0.062, 0.007]\).

The formula divides by \(\tau\), so APIs define \(\tau = 0\) as greedy (vLLM switches to argmax below \(10^{-5}\) [sampler.py]). Temperature reshapes the whole distribution; the next three methods cut it instead. For RL (page 22): the policy you sample from is \(\softmax(z/\tau)\), so a policy-gradient loss must compute log-probabilities with the same \(\tau\).

Cutting the tail: top-k, top-p, min-p

Sampling from the full softmax fails for a specific reason. With \(V \approx 128\text{K}\), the tail holds tens of thousands of tokens that each have tiny probability but together carry real mass, so they are "over-represented in the aggregate" [Holtzman et al. 2019, §1]. Lowering \(\tau\) shrinks the tail but costs diversity (sampling at \(\tau < 0.9\) already sharply increases repetition, their Fig. 9). Truncation methods zero the tail explicitly and renormalize.

  • Top-k keeps the \(k\) largest probabilities. Fan et al. used \(k = 10\) for story generation [Fan et al. 2018, §5.4]. The flaw is that one \(k\) must serve every context: a flat distribution over hundreds of reasonable words needs a large \(k\), a peaked one a small \(k\) [Holtzman et al. 2019, Fig. 5].
  • Top-p, or nucleus sampling 核采样, keeps the smallest set \(V^{(p)}\) of top tokens whose total probability is at least \(p\), then renormalizes: \(P'(x) = P(x) / \sum_{v \in V^{(p)}} P(v)\) for \(x \in V^{(p)}\) [Holtzman et al. 2019, Eqs. 2-3]. The set grows when the model is unsure and shrinks to one token when it is confident.
  • Min-p keeps every token with \(p_i \ge p_{\text{base}} \cdot p_{\max}\), then renormalizes [Nguyen et al. 2024, §3.1]. The threshold scales with the top token's probability. In logit terms, after temperature it keeps every token within \(\tau \ln(1/p_{\text{base}})\) of the top raw logit, and it needs a maximum, not a sort.
Top-p (nucleus) sampling
Problem
Pure sampling draws from the unreliable tail. Top-k uses one fixed cutoff for both flat and peaked distributions.
Idea
Keep the smallest set of most likely tokens whose mass reaches \(p\), renormalize, sample.
Why it works
The candidate count adapts to confidence: one token when \(p_{\max} \ge p\), hundreds when the distribution is flat.
Evidence
GPT-2 Large, \(p = 0.95\): perplexity 13.13 against 12.38 for human text, 0.36% repetition, and the best HUSE of the decoders tested (0.97) [Holtzman et al. 2019, Tab. 1].
Cost
\(p\) is a mass, so when temperature flattens the distribution the nucleus grows and admits junk [Nguyen et al. 2024, §2]. It needs a sort per step.
Used by
Hugging Face Transformers, vLLM, llama.cpp. Typical \(p\) is 0.9 to 0.95. Qwen2.5-7B-Instruct ships \(\tau = 0.7\), top-p 0.8, top-k 20 [config].
Min-p sampling
Problem
At high temperature the distribution is flat, so a fixed mass \(p\) admits many low-quality tokens.
Idea
Threshold relative to the top token: keep \(p_i \ge p_{\text{base}} \cdot p_{\max}\).
Why it works
A confident model (\(p_{\max} = 0.9\)) gets an aggressive cut (threshold 0.09 at \(p_{\text{base}} = 0.1\)), an uncertain one (\(p_{\max} = 0.3\)) a permissive one (0.03). It is a ratio test, so earlier renormalization does not change it.
Evidence
Contested. Nguyen et al. report gains at high temperature (main results span 0.7 to 3.0) on GPQA, GSM8K chain-of-thought and creative writing, mainly with Mistral-7B [Nguyen et al. 2024, §5]. An independent re-analysis finds no advantage over top-p or top-k once hyperparameter budgets are equalized, and flags problems in the original human evaluation [Schaeffer et al. 2025, §2-5] (a preprint, as of September 2026).
Cost
On a peaked distribution \(p_{\text{base}} = 0.1\) can drop far more than 10% of the mass (probabilities 80, 7, 3, 2, 1%: top-p 0.9 keeps three tokens, min-p 0.1 keeps one [App. A.4]). The authors advise against stacking truncation methods (§3.4).
Used by
Hugging Face Transformers, vLLM, llama.cpp. Suggested \(p_{\text{base}}\): 0.05 to 0.1.

A practical rule: one truncation method plus a temperature. Greedy or \(\tau \le 0.3\) for tasks with a checkable answer; \(\tau \approx 0.6\) to 1.0 with top-p or min-p for chat and writing; \(\tau = 1\) untruncated when samples must follow the model's own distribution (RL rollouts, page 24). Order of operations

The methods do not commute, and libraries disagree. Each row below was checked against the library's source (as of September 2026):

Three consequences follow, and all three are interview material.

  1. Temperature before or after truncation. Top-k is unaffected by \(\tau\) (dividing by a positive number preserves rank order). Top-p and min-p are not. With temperature first, raising \(\tau\) enlarges their candidate sets. With temperature last, the candidate set is fixed and \(\tau\) only changes how you sample inside it. On the Figure 2 logits with top-k 5, top-p 0.9 and min-p 0.2, Hugging Face's order keeps 2 tokens at \(\tau = 0.5\) and 5 at \(\tau = 2\), while llama.cpp's order keeps 4 in both cases.
  2. Top-p depends on what ran before it; min-p does not. Each Hugging Face warper takes a softmax of the surviving logits, so top-p's mass is relative to the survivors. With probabilities \([0.4, 0.3, 0.2, 0.1]\), top-p 0.5 alone keeps two tokens; after top-k 2 the survivors are \([0.571, 0.429]\) and it keeps one. Min-p's ratio \(p_i / p_{\max}\) is unchanged by renormalization.
  3. Min-p before top-p (vLLM) keeps no more tokens than after it (Hugging Face). If min-p first leaves mass \(M \le 1\), the renormalized top-p threshold \(p\) equals \(pM\) in original units, which is lower, so the prefix is shorter. Random logit vectors confirm it: 5,000 trials, never larger, strictly smaller in 3,360.

When you compare numbers across frameworks or reproduce a paper, check the order and the defaults. (The min-p paper's two human studies applied temperature after and before truncation respectively [Schaeffer et al. 2025, §2.4].)

Repetition, frequency and presence penalties

Penalties attack repetition by editing logits according to what has been generated. CTRL's repetition penalty divides the temperature by \(\theta\) for tokens already in the generated set \(g\): \(p_i \propto \exp\big(z_i / (\tau \cdot I(i \in g))\big)\), with \(I = \theta\) inside \(g\) and 1 outside, and \(\theta \approx 1.2\) worked well with greedy decoding [Keskar et al. 2019, §4.1]. Dividing a negative logit by \(\theta \gt 1\) would raise it, so Hugging Face multiplies negative logits and divides positive ones, applies the penalty once per distinct token, and includes the prompt by default [logits_process.py].

Frequency and presence penalties are additive. With \(c_j\) the number of times token \(j\) appeared in the output so far:

\[ z_j \leftarrow z_j - \alpha_{\text{freq}}\, c_j - \alpha_{\text{pres}}\, \mathbf{1}[c_j \gt 0] \]

vLLM implements exactly this and notes that it follows the OpenAI API definition [layers/utils.py]. Subtracting from a logit multiplies the probability by \(e^{-\alpha c_j}\): the frequency term grows with each repeat, the presence term is a one-time charge.

All penalties share one flaw: they cannot tell harmful repetition from necessary repetition. Identifiers, brackets, digits and quotes must repeat, so heavy penalties damage code, JSON and math. Shipped defaults are mild (Qwen2.5-7B-Instruct: repetition penalty 1.05).

The whole sampler fits in a screen. This is the core of the drill in exercises/solutions/sampling.py:

import torch
import torch.nn.functional as F

def top_k_filter(z, k):                                # z: (..., V) logits
    kth = torch.topk(z, k, dim=-1).values[..., -1:]    # k-th largest logit per row
    return z.masked_fill(z < kth, float("-inf"))       # ties with the k-th value survive

def top_p_filter(z, p):
    probs = z.softmax(-1)
    sp, order = probs.sort(dim=-1, descending=True, stable=True)
    before = F.pad(sp.cumsum(-1)[..., :-1], (1, 0))    # mass strictly before each token
    drop = torch.zeros_like(probs, dtype=torch.bool).scatter(-1, order, before >= p)
    return z.masked_fill(drop, float("-inf"))          # keep a token while mass so far < p

def min_p_filter(z, p_min):
    probs = z.softmax(-1)
    return z.masked_fill(probs < p_min * probs.amax(-1, keepdim=True), float("-inf"))

def sample(z, gen, temperature=1.0, top_k=None, top_p=None, min_p=None):
    if temperature == 0:
        return z.argmax(-1)                            # greedy
    z = z / temperature                                # 1) temperature first (HF order)
    if top_k: z = top_k_filter(z, top_k)               # 2) each filter renormalizes
    if top_p: z = top_p_filter(z, top_p)               # 3) over the survivors
    if min_p: z = min_p_filter(z, min_p)               # 4)
    probs = z.softmax(-1)
    ids = torch.multinomial(probs.reshape(-1, probs.size(-1)), 1, generator=gen)
    return ids.reshape(probs.shape[:-1])

Beam search, and why chat models rarely use it

Beam search 束搜索 is a deterministic search for a high-probability sequence. It keeps \(b\) partial hypotheses (the beam), expands each by all \(V\) tokens, scores every candidate by its cumulative log-probability \(\sum_t \log p(x_t \mid x_{\lt t})\), and keeps the best \(b\) of the \(bV\) candidates. Hypotheses that end in EOS are set aside as finished. It costs \(b\) times the compute and KV cache per request, and each step must reorder the cache so every survivor points at its parent's entries.

Every extra token adds a negative log-probability, so raw scores favor short outputs. GNMT divides by a length penalty: \(s(Y,X) = \log P(Y \mid X) / lp(Y) + cp(X;Y)\) with \(lp(Y) = (5 + |Y|)^\alpha / 6^\alpha\), plus a coverage penalty \(cp\) specific to attention-based translation. \(\alpha \in [0.6, 0.7]\) was usually best on development sets, and tuning both terms raised WMT'14 En-Fr BLEU from 30.3 to 31.4 [Wu et al. 2016, §7, Tab. 2].

Where it works. In translation, summarization and speech recognition the input nearly determines the output, so the mode is what you want. GNMT kept 8 to 12 hypotheses, and Shazeer used beam 4 with \(\alpha = 0.6\) [Shazeer 2019, §4.2].

Why it fails for chat and open-ended text:

  1. Mode-seeking output is bland and loops. With \(b = 16\), GPT-2 Large has perplexity 1.48 (human text: 12.38) and 28.94% looped generations (table above). At \(b = 32\) it loops on an institution's name, and for \(b \ge 64\) it "prefer[s] to stop generating immediately after the given context" [Holtzman et al. 2019, Fig. 1]. Fan et al. also found beam output "short and generic" [Fan et al. 2018, §5.4].
  2. The beam search curse. Larger beams find higher-probability outputs that are worse translations: Koehn and Knowles found optima between beams of 4 and about 30 (30 to 50 with length normalization) and falling quality beyond, mainly from shorter outputs [Koehn and Knowles 2017, §3.6, Fig. 10]. Stahlberg and Byrne ran exact search and found that for 51.8% of sentences the highest-scoring output is the empty string (BLEU 2.1, against 30.3 for beam 10). Beam search works only because it makes search errors [Stahlberg and Byrne 2019, Tab. 1]. The model's probability is a poor objective, and better search makes it worse.
  3. Cost. \(b\) sequences per request multiply memory traffic and complicate batching. PagedAttention shares prompt blocks across beams (37.6% to 55.2% of KV memory saved for beam width 2 to 6 on their Alpaca trace [Kwon et al. 2023, §6.3]), but the compute multiplier stays.

In current practice, open-ended and reasoning models are sampled, often several times, and the samples filtered or aggregated (page 24), rather than beam-searched.

Reproducibility: seeds and nondeterministic GPUs

There are two sources of randomness. Sampling randomness is controlled by a seed: the same logits and generator state give the same token (serving engines keep a generator per seeded request). Numerical randomness is why "temperature 0" is not a reproducibility guarantee:

  • Floating-point addition is not associative, and bf16 keeps only about three decimal digits.
  • GPU kernels pick a reduction order from the input shape (tiling, split-K, split-KV attention), and a server batches the same request with different neighbors each time, so its logits differ in the last bits.
  • When the top two logits are closer than that noise, the argmax flips, the context changes, and the two continuations diverge.

The Thinking Machines analysis argues the usual culprit, concurrent atomic adds, is not the main cause: a typical LLM forward pass contains no atomic adds, and a fixed batch gives deterministic output. The cause is missing batch invariance: results depend on batch size, which varies with server load. Sending one prompt 1,000 times at temperature 0 to Qwen3-235B gave 80 unique completions. With batch-invariant kernels all 1,000 were identical, at some cost in speed [He and Thinking Machines Lab 2025].

PyTorch documents no bitwise reproducibility across releases, platforms, or CPU versus GPU even with identical seeds, and torch.use_deterministic_algorithms(True) removes nondeterministic PyTorch ops but not batch-composition effects [PyTorch notes]. This matters for evals, debugging, and RL, where the trainer and the inference engine can disagree on log-probabilities (page 25). Even speculative decoding guarantees only the output distribution: "a single token deviating due to numerics could result in two sequences diverging wildly" [Chen et al. 2023, §Evaluation].

The KV cache

Why the cache is exact

In layer \(\ell\), token \(t\) contributes a query, key and value (row vectors, per head): \(q_t = x_t W^Q\), \(k_t = x_t W^K\), \(v_t = x_t W^V\), and its attention output is

\[ o_t = \sum_{j \le t} \softmax_j\!\left(\frac{q_t \cdot k_j}{\sqrt{d_h}}\right) v_j . \]

Causal masking means the hidden state of token \(j\) at every layer depends only on tokens \(1..j\). By induction over layers, \(k_j^{(\ell)}\) and \(v_j^{(\ell)}\) for \(j \lt t\) do not change when token \(t\) is appended, so each key and value is computed once and stored. The KV cache is therefore exact, not an approximation. A bidirectional encoder like your tagger's has no such cache: adding one input changes every representation.

What is stored, and what is not

Per layer and per KV head the cache holds \(K\) and \(V\) after the linear projections. Keys are stored after RoPE (page 05): a key's rotation depends only on its own position, so it is applied once at write time, and each query is rotated at its own position when used. Not stored: queries (used once), scores, FFN activations and earlier hidden states, none of which later tokens need.

Why \(K, V\) rather than the layer input \(x_j\)? Caching \(x_j\) (\(d\) numbers per layer) would force us to redo the \(K\) and \(V\) projections of every past token at every step, about \(2\,t\,d \cdot 2 n_{kv} d_h\) FLOPs per layer. The cache trades memory for compute, and MLA caches a compressed latent to change that trade (page 07).

How big is it

\[ \text{KV bytes per token} = 2 \cdot L \cdot n_{kv} \cdot d_h \cdot b \]
2 for K and V; b = bytes per element (2 for bf16)

Llama-3-8B (\(L = 32\), \(n_{kv} = 8\), \(d_h = 128\), bf16): \(2 \cdot 32 \cdot 8 \cdot 128 \cdot 2 = 131{,}072\) B = 128 KiB per token. At 32K tokens (valid for Llama 3.1, not the 8K base model) that is \(128 \text{ KiB} \times 32{,}768 = 4\) GiB per sequence, and 16 GiB at 128K. A batch of 32 sequences at 4K tokens is also 16 GiB. For comparison, OPT-13B costs \(2 \cdot 5120 \cdot 40 \cdot 2 = 819{,}200\) B per token, or about 1.6 GiB for 2,048 tokens [Kwon et al. 2023, §3]. Page 07 derives the MQA, GQA and MLA variants.

Per-step cost with and without it

Let \(N_{\text{mm}}\) be the parameters that take part in matmuls (7.50B for Llama-3-8B: the layers plus the output head, not the embedding lookup). Without a cache, producing the token after \(t\) tokens re-runs the pass over all \(t\): about \(2 N_{\text{mm}}\, t\) FLOPs. With a cache it processes one token: \(2 N_{\text{mm}}\) FLOPs plus \(4 L\, n_h d_h\, t\) for attention over the cache. So the cache turns weight-matmul work from quadratic to linear in length. Example: prompt \(P = 2048\), \(n = 256\) new tokens. Without a cache the loop pushes \(\sum_{i=0}^{255} (2048 + i) = 556{,}928\) token-positions through the network. With one it pushes \(2048 + 255 = 2{,}303\), 242 times fewer.

Attention stays quadratic in total but is minor in FLOPs: \(4 \cdot 32 \cdot 128 \cdot 2048 \cdot 32 = 1.07\) GFLOP per new token at \(t = 2048\), against 15.0 GFLOP for the weights. What the cache does not remove is the bytes: every step reads all of it (next section).

KV cache
Problem
Naive decoding re-runs the whole prefix through every layer for every new token.
Idea
Store each layer's keys and values once. Each step computes only the new token's \(q, k, v\), appends \(k, v\), and attends over the stored columns.
Why it works
Causal masking makes earlier keys and values independent of later tokens, so the cache is exact.
Evidence
242 times fewer token-positions in the example above. Shazeer's analysis shows total arithmetic stays \(\Theta(b n d^2)\) across \(n\) incremental steps [Shazeer 2019, §2.4.1].
Cost
\(2 L\, n_{kv}\, d_h\, b\) bytes per token per sequence, reread in full every step, so it limits both batch size (capacity) and speed (bandwidth). Sequences of unknown length also fragment memory.
Used by
Every autoregressive inference stack. Hugging Face has a dynamic cache (torch.cat each step) and a static one (preallocated, index_copy_) [cache_utils.py]. vLLM pages it (below).

Implementation: preallocate, do not concatenate

The simplest cache appends with torch.cat at every step. That allocates a new tensor and copies all \(t\) entries (two extra passes over the cache on top of the attention read) and fragments memory. Instead, allocate \((B, n_{kv}, S_{\max}, d_h)\) once per layer, write in place, and give attention a view of the filled prefix. Shapes stay fixed, as graph capture (CUDA graphs, torch.compile) requires. This is the drill in exercises/solutions/kv_cache.py:

class KVCache:
    def __init__(self, n_layers, batch, n_kv, max_len, d_h,
                 dtype=torch.bfloat16, device="cuda"):
        shape = (batch, n_kv, max_len, d_h)            # allocated once, never resized
        self.k = [torch.zeros(shape, dtype=dtype, device=device) for _ in range(n_layers)]
        self.v = [torch.zeros(shape, dtype=dtype, device=device) for _ in range(n_layers)]
        self.n = [0] * n_layers                        # cached positions per layer

    def update(self, layer, k_new, v_new):             # (B, n_kv, T, d_h); K already has RoPE
        s, T = self.n[layer], k_new.shape[2]
        self.k[layer][:, :, s:s + T] = k_new           # in-place write: O(T) bytes moved
        self.v[layer][:, :, s:s + T] = v_new
        self.n[layer] = s + T
        return self.k[layer][:, :, :s + T], self.v[layer][:, :, :s + T]   # views, no copy

Preallocation reserves \(S_{\max}\) per sequence, which wastes memory when lengths vary: the vLLM paper measured only 20.4% to 38.2% of KV memory holding token states in earlier systems [Kwon et al. 2023, Fig. 2]. PagedAttention removes that waste (Serving teasers).

Prefill vs decode: the performance model

Assumptions for every number below: one H100 SXM with 3.35 TB/s of HBM3 bandwidth and 1,979 TFLOPS of BF16 tensor-core throughput "with sparsity" on NVIDIA's page [NVIDIA H100]. Dense throughput is half of that, 989.5 TFLOP/s (the H100 NVL figures in a recent profiling study show the same factor of two, 835 dense and 1,671 sparse [Siavashi et al. 2026, §2.1]). Model: Llama-3-8B in bf16.

Arithmetic intensity: why the two phases differ

Arithmetic intensity 算术强度 is FLOPs performed per byte moved from memory. A kernel is memory-bound 访存受限 below the hardware's ridge point and compute-bound 计算受限 above it. For an H100 the ridge is \(989.5 \text{ TFLOP/s} \,/\, 3.35 \text{ TB/s} \approx 295\) FLOPs per byte. For one weight matmul \(y = xW\) with \(x\) of shape \(m \times d_{\text{in}}\) in bf16:

\[ \frac{\text{FLOPs}}{\text{bytes}} \approx \frac{2\, m\, d_{\text{in}} d_{\text{out}}}{2\, d_{\text{in}} d_{\text{out}}} = m \quad \text{(weights dominate the bytes when } m \ll d\text{)} \]

The intensity is the number of tokens \(m\) sharing one read of the weights. In prefill, \(m\) is the prompt length, thousands, far above 295: compute-bound. In decode, \(m\) is the batch size, and at batch 1 the intensity is about 1 FLOP per byte, 0.3% of the ridge. The tensor cores idle while HBM streams the weights, so step time is set by bytes, not FLOPs. Pope et al. make the same point: at small batch and short context the time to load weights dominates, and at large batch and long context the time to load the KV cache dominates [Pope et al. 2022, §2].

Decode: time per token is bytes over bandwidth

\[ t_{\text{step}} \;\gtrsim\; \max\!\left( \underbrace{\frac{W + B\,\bar S\,\kappa}{\text{BW}}}_{\text{memory time}},\ \underbrace{\frac{2 N_{\text{mm}} B + 4 L n_h d_h\, B \bar S}{\text{peak FLOP/s}}}_{\text{compute time}} \right) \]
Roofline lower bound on decode step time

\(W\): weight bytes; \(\kappa\): KV bytes per token; \(\bar S\): mean context length; \(B\): batch size; \(N_{\text{mm}}\): parameters that take part in matmuls. Real kernels reach a fraction of this bound.

Weights. Per layer, attention has \(4096 \cdot 4096 \cdot 2 + 4096 \cdot 1024 \cdot 2 = 41{,}943{,}040\) parameters, the SwiGLU FFN has \(3 \cdot 4096 \cdot 14336 = 176{,}160{,}768\), and the norms add 8,192: 218,112,000 per layer. Times 32 layers, plus the embedding and the untied output head (\(128{,}256 \cdot 4096 = 525{,}336{,}576\) each) and a final norm: \(N = 8{,}030{,}261{,}248\). In bf16 that is 16.06 GB.

Batch 1. Each step reads every weight once: \(16.06 \text{ GB} / 3.35 \text{ TB/s} = 4.79\) ms, so at most 208 tokens per second. Adding the KV cache of a 4K context (0.54 GB) gives 4.95 ms and 202 tokens/s. Excluding the embedding table (a lookup, not a stream) gives 15.0 GB, 4.48 ms and 223 tokens/s, so the bound moves about 7% with what you count. Compute time is \(2 N_{\text{mm}} / 989.5\text{ TFLOP/s} = 0.015\) ms: 0.3% of peak. Real engines reach a fraction of the bound. A profiling preprint measured 5.27 ms per token for Llama-3-8B at batch 1 and a 2,048-token context on an H100 NVL (vLLM, FlashAttention-3), against a 4.19 ms roofline for that GPU's 3.9 TB/s: about 80% [Siavashi et al. 2026, §5]. It is one measurement on a different SKU, so use it as a sanity check. Expect roughly 150 to 180 tokens/s on an SXM part.

Batching: weights are shared, caches are not

With batch \(B\), one read of the weights serves \(B\) tokens, so \(W\) is amortized. Each sequence has its own cache, so the KV term grows linearly with \(B\). Take 4K-token contexts. Capacity is the limit on \(B\): with 90% of 80 GB usable (vLLM's current default gpu_memory_utilization is 0.92 [cache.py]), \((72 - 16.06) \text{ GB} / 0.537 \text{ GB} = 104\) sequences.

  • Latency versus throughput. From \(B = 1\) to \(B = 32\), total throughput rises 16 times while per-user speed halves (202 to 101 tokens/s). The first steps of the trade are nearly free: going from 1 to 8 sequences adds 23% to the step time and gives 6.5 times the throughput, because the KV slice is still small next to the weight slice.
  • The ceiling is the KV cache. As \(B \to \infty\) the weight term vanishes and throughput approaches \(\text{BW} / (\bar S \kappa) = 3.35 \text{ TB/s} / 0.537 \text{ GB} = 6{,}240\) tokens/s per GPU at 4K context. At large batch the whole model's intensity is \((2 N_{\text{mm}} + 4 L n_h d_h \bar S) / (\kappa \bar S) = 4 + 2N_{\text{mm}} / (\kappa \bar S)\). The 4 is \(n_h / n_{kv}\), page 07's attention intensity. This crosses the 295 ridge only when \(\bar S \lesssim 390\) tokens, so above that GQA-8 decode stays memory-bound at any batch size.

PaLM 540B with multi-query attention (a tiny KV cache) shows the same gap between phases: decode reached 33% MFU at batch 512 and 14% at batch 64, while prefill reached 76% at batch 512 and 43% at batch 1 [Pope et al. 2022, Tab. 2]. The levers that raise the ceiling are architectural (fewer or smaller KV heads, page 07), numeric (KV quantization) and systemic (page 17).

Prefill: the compute-bound side

A forward pass over \(T\) tokens costs about \(2 N T\) FLOPs [Pope et al. 2022, §2]. For \(T = 2048\): \(2 \times 8.03 \times 10^9 \times 2048 = 3.29 \times 10^{13}\) FLOPs. At 100% of peak that is \(3.29 \times 10^{13} / 989.5 \times 10^{12} = 33.2\) ms. Nobody reaches peak, and 50% MFU (model FLOPs utilization) is a fair planning number: 66.5 ms, or 30,800 prompt tokens per second, about 150 times the rate of one decode stream. The weights are still read once (4.8 ms, small against 33 ms), so the pass is compute-bound. Pope et al. report prefill MFU of 43% to 76% on PaLM (Tab. 2).

The rule \(2NT\) is a slight overestimate. Counting exactly (no FLOPs for the embedding lookup, the output head on the last position only, causal attention over half the score matrix) gives \(2.97 \times 10^{13}\), 10% less. At long contexts the quadratic attention term matters: at \(T = 32{,}768\) attention is 38% of the FLOPs and the total is \(7.4 \times 10^{14}\) (0.75 s at peak, 1.5 s at 50% MFU), 40% more than \(2NT\).

Metrics and the trade-off

Serving is judged on four numbers, defined as in NVIDIA's benchmarking tools [NVIDIA benchmarking guide]:

  • Time to first token (TTFT, 首 token 延迟): request arrival to the first output token, including queueing, prefill and network. For the 2,048-token prompt on an idle H100 it is about 70 ms, growing linearly (then quadratically) with prompt length.
  • Time per output token (TPOT, also inter-token latency): \((\text{e2e latency} - \text{TTFT}) / (\text{output tokens} - 1)\). At batch 1 it is one decode step.
  • End-to-end latency \(= \text{TTFT} + (n-1)\cdot\text{TPOT}\).
  • Throughput: output tokens per second across all requests.

Batch size moves TPOT and throughput in opposite directions (table above). Pope et al. show the same trade on PaLM: cost per token is lowest at batches above about 512, while smaller batches cut latency at a higher cost per token [Pope et al. 2022, §4.4]. A long prefill also stalls the decode steps that share its GPU and spikes TPOT for everyone else; chunked prefill and disaggregating prefill from decode address that (page 17).

Serving teasers

One paragraph each. Page 17 treats them properly.

Continuous batching 连续批处理. A static batch runs until its longest sequence finishes, so short requests wait and the GPU idles. Orca schedules per model iteration: finished sequences leave and waiting requests join at every step, with batching applied only to a selected set of operations ("selective batching") so that sequences at different positions can share a step [Yu et al. 2022, OSDI]. It reported 36.9 times the throughput of FasterTransformer at the same latency on GPT-3 175B.

PagedAttention. Contiguous per-sequence reservations waste most of the cache (20.4% to 38.2% useful, above). PagedAttention splits each sequence's cache into fixed-size blocks (16 tokens by default) allocated on demand, with a per-sequence block table mapping logical positions to physical blocks, like virtual memory. Waste is limited to the last partial block, blocks can be shared with copy-on-write, and vLLM reports 2 to 4 times the throughput of FasterTransformer and Orca at the same latency. The price is a slower attention kernel: 20% to 26% higher latency than FasterTransformer's [Kwon et al. 2023, Abstract, §7.1].

Prefix caching 前缀缓存. A token's keys and values depend only on the tokens before it, so requests that share a prefix (system prompt, few-shot examples, earlier chat turns) can share those cache entries and skip that part of prefill. SGLang's RadixAttention keeps cached prefixes in a radix tree with LRU eviction and reports up to 6.4 times higher throughput on its workloads (the gain combines several optimizations). In its Chatbot Arena deployment, hit rates were 52.4% and 74.1% on two models, with 1.7 times lower first-token latency for Vicuna-33B [Zheng et al. 2023, §3, §6]. It helps TTFT and capacity, not per-token decode cost.

Speculative decoding
Problem
Decode is memory-bound: each step reads all weights and the whole cache to produce one token, and steps are sequential.
Idea
A cheap draft distribution \(q\) proposes \(\gamma\) tokens. The target scores all \(\gamma + 1\) positions in one forward pass. Accept draft token \(x\) with probability \(\min(1, p(x)/q(x))\). At the first rejection, resample from \(\text{norm}(\max(0, p - q))\) and discard the rest. If all are accepted, sample a bonus token from the target.
Why it works
Scoring \(\gamma + 1\) tokens is one pass with intensity \(\gamma + 1\) FLOPs per byte, still far below the 295 ridge, so it costs about one decode step while yielding several tokens. Exactness: \(P(x) = q(x)\min(1, p/q) + (1-\alpha)\cdot\text{norm}(\max(0,p-q))(x) = p(x)\), where \(\alpha = \sum_x \min(p, q)\) is the acceptance rate.
Evidence
2.3 to 3.4 times faster on T5-XXL at batch 1 with the best draft (T5-small), identical outputs [Leviathan et al. 2022, Tab. 2]. Chinchilla 70B: 1.92 to 2.46 times on XSum and HumanEval [Chen et al. 2023, Tab. 1].
Cost
Wasted compute on rejected tokens, a draft model to host, and shrinking gains as the batch grows and decode nears compute-bound. The distribution is preserved, but the bits are not identical to plain decoding.
Used by
Both original papers (Google, DeepMind). Draft-free variants and deployment details: page 17.

Expected tokens per target pass: \((1 - \alpha^{\gamma+1}) / (1 - \alpha)\). Wall-clock speedup: that divided by \(1 + \gamma c\), with \(c\) the draft-to-target cost ratio [Leviathan et al. 2022, Eq. 1, Thm. 3.8]. With \(\alpha = 0.8\), \(\gamma = 4\), \(c = 0.05\): 3.36 tokens per pass and a 2.8 times speedup. In a memory-bound decoder \(c\) is close to the ratio of bytes read, so a draft with 1/16 of the target's weights has \(c \approx 0.06\).

Common misconceptions

  • "Temperature 0 gives the same output on every run." Not on GPUs. Kernel reduction order depends on the batch, near-tie logits flip the argmax, and the text diverges from there.
  • "Top-p 0.9 keeps 90% of the tokens." It keeps the smallest set holding at least 90% of the probability mass: one token or thousands.
  • "Top-k, top-p and min-p compose in any order." Order and renormalization matter, and libraries differ: temperature comes first in Hugging Face and vLLM, last in llama.cpp.
  • "The KV cache is an approximation that skips attention." It is exact. It skips recomputing earlier tokens' projections and FFNs, while attention still reads every cached key and value at every step.
  • "A bigger batch fixes memory-bound decoding." It amortizes the weight reads only. Each sequence's KV cache is its own, so throughput saturates near \(\text{BW}/(\bar S \kappa)\).
  • "Beam search finds the best answer, so wider is better." Model probability is a poor objective: wider beams give shorter outputs, and exact search returns the empty string for about half the sentences in one study.
  • "Decode is slow because it needs many FLOPs." It needs few: at batch 1 an H100 uses 0.3% of its FLOP/s while streaming 16 GB of weights.
  • "Speculative decoding is an approximation." With the correct accept and resample rule the output distribution equals the target's exactly. It does not promise bitwise-identical text.

Interview questions

Warm-up Walk through the generation loop. How does the first step differ from the rest?

Tokenize the prompt. Prefill: one parallel forward pass over all \(P\) prompt tokens with a causal mask. It fills the KV cache and gives the last position's logits, from which the first token is chosen. Then repeat decode steps: feed only the newest token, compute its \(q, k, v\), append \(k, v\) to the cache, attend over the cache, get logits, choose. Stop on EOS, a stop string or the length limit.

Prefill has \(P\) tokens per weight read (compute-bound) and sets time to first token. Each decode step has one token per sequence (memory-bound) and sets time per output token.

Warm-up What does temperature do? What happens as \(\tau \to 0\) and \(\tau \to \infty\)?

It divides the logits by \(\tau\) before the softmax, so \(p_i \propto \exp(z_i/\tau) \propto p_i^{1/\tau}\): sharper for \(\tau \lt 1\), flatter for \(\tau \gt 1\). As \(\tau \to 0^+\), \(p_i/p_{\max} = e^{-(z_{\max}-z_i)/\tau} \to 0\) for every non-maximal token, so the limit is greedy (uniform over exact ties). As \(\tau \to \infty\) all ratios tend to 1 and the distribution is uniform. Entropy rises monotonically with \(\tau\). Implementations special-case \(\tau = 0\) as greedy because the formula divides by zero.

Warm-up What exactly is stored in the KV cache, and how big is it for Llama-3-8B at 32K tokens?

For every layer, KV head and past token: the key (after projection and RoPE) and the value. Not stored: queries, scores, FFN activations, hidden states. It is exact because causal masking makes earlier keys and values independent of later tokens.

Size per token \(= 2 L\, n_{kv}\, d_h\, b = 2 \cdot 32 \cdot 8 \cdot 128 \cdot 2 = 131{,}072\) B = 128 KiB. At 32,768 tokens that is \(128 \text{ KiB} \times 32{,}768 = 4\) GiB per sequence (16 GiB with 32 KV heads). The base Llama-3-8B has an 8K window, so 32K needs Llama 3.1.

Warm-up Why does greedy decoding repeat itself?

Two effects. Repetition is self-reinforcing: the more often a phrase is in the context, the more probable its continuation (Holtzman et al., Fig. 4), and greedy always follows the highest probability, so a loop is absorbing. And likelihood-trained models put their highest probability on generic continuations, while human text is not the most probable text (perplexity 12.4 versus 1.5 for greedy output). On GPT-2 Large, 73.66% of greedy generations ended in a loop. Truncated sampling (top-p, min-p) adds controlled randomness to escape.

Core Explain temperature, top-k, top-p and min-p. When would you use each?

Temperature raises probabilities to the power \(1/\tau\): a global randomness knob. Top-k keeps the \(k\) most likely tokens: simple, but one \(k\) is too large when the model is sure and too small when many continuations are valid. Top-p keeps the smallest set with mass \(\ge p\), so its size adapts to confidence. Min-p keeps \(p_i \ge p_{\text{base}} p_{\max}\): the threshold scales with the top token and needs no sort.

Usage: greedy or \(\tau \le 0.3\) for checkable answers; \(\tau \approx 0.6\) to 1 with top-p 0.9 to 0.95 or min-p 0.05 to 0.1 for chat and writing; \(\tau = 1\) untruncated for RL rollouts. Use one truncation method. Nucleus sampling is well supported (Holtzman); min-p's advantage is disputed by an independent re-analysis.

Core Why is beam search rare for chatbots even though it finds higher-probability sequences?

Probability is not quality for open-ended text. Mode-seeking output is generic and loops: with \(b = 16\), GPT-2 Large has perplexity 1.48 (human text: 12.38) and 28.94% looped outputs. Bigger beams get worse, the "beam search curse": BLEU falls beyond beams of 4 to 50 as outputs shorten, and exact search returns the empty output for 51.8% of sentences (Stahlberg and Byrne), so beam search works only thanks to its search errors. Length normalization helps but does not fix the bias.

It remains right when the input nearly determines the output (translation, summarization, ASR). For chat it also costs \(b\) times the compute and KV cache and complicates batching, so sampling plus selection is used.

Core Does it matter whether temperature is applied before or after top-p (or min-p)?

Yes for top-p and min-p, no for top-k. Top-k depends only on rank order, which \(\tau \gt 0\) preserves. Top-p's mass and min-p's ratio come from probabilities, which temperature changes. With temperature first (Hugging Face, vLLM), higher \(\tau\) flattens the distribution and enlarges the nucleus. With temperature last (llama.cpp default), the candidate set does not depend on \(\tau\). On Figure 2's logits with top-k 5, top-p 0.9, min-p 0.2, Hugging Face's order keeps 2 tokens at \(\tau = 0.5\) and 5 at \(\tau = 2\), and llama.cpp's keeps 4 both times.

Also renormalization: after top-k 2 on \([0.4,0.3,0.2,0.1]\), top-p 0.5 keeps one token instead of two, while min-p is a ratio test and is unaffected. Check order and defaults (Hugging Face silently applies top-k 50 when unset).

Core Why is decoding memory-bandwidth-bound while prefill is compute-bound?

For a weight matmul, FLOPs per weight byte \(\approx m\), the number of tokens sharing that read. Prefill has \(m\) equal to the prompt length, thousands, far above the H100's ridge of about 295 FLOPs/byte (989.5 TFLOP/s over 3.35 TB/s): compute-bound. Decode has \(m = B\), about 1 at batch 1: the tensor cores wait while HBM streams 16 GB of weights.

Attention is worse. Each sequence's KV cache is read once per step for only \(n_h/n_{kv}\) FLOPs per byte (4 for Llama-3-8B), whatever the batch. So step time is about (weight bytes + KV bytes) over bandwidth.

Core Estimate tokens per second for an 8B model at batch 1 on an H100.

Decode is bandwidth-bound, so tokens/s \(\approx\) bandwidth over bytes read per token. Weights: 8.03B parameters in bf16 is 16.06 GB. H100 SXM bandwidth is 3.35 TB/s. So a token takes at least \(16.06 / 3350 = 4.79\) ms, at most about 208 tokens/s. With a 4K-token KV cache (0.54 GB): 4.95 ms, about 202 tokens/s.

Reality is lower: quote roughly 150 to 180 tokens/s (one profile measured 5.27 ms against a 4.19 ms bound on an H100 NVL). FP8 weights roughly double the bound. State the assumptions: bf16, batch 1, weights dominate, no speculation.

Core How does increasing the batch size affect latency and throughput during decode?

One weight read now serves \(B\) tokens, so throughput rises almost linearly while the weight term dominates, and per-token latency rises slowly as each sequence adds KV bytes. Llama-3-8B, 4K context, H100: \(B = 1\) gives 4.95 ms per step and 202 tokens/s. \(B = 32\) gives 9.92 ms, 3,225 tokens/s total (16 times) but 101 per user (half). \(B = 104\) fills the GPU: 21.5 ms, 4,846 tokens/s.

Throughput saturates at \(\text{BW}/(\bar S\kappa) \approx 6{,}240\) tokens/s because KV bytes scale with \(B\) too, and above about 390 tokens of context the whole step stays memory-bound. Batch is capped by KV capacity (104 here) and by any TPOT target.

Core Why can two runs with the same seed and temperature 0 give different outputs on GPUs?

Temperature 0 removes sampling randomness, but the logits are not bit-identical. Floating-point addition is not associative, and GPU kernels choose reduction orders (tiling, split-K, split-KV) from input shapes. A server batches the same request with different neighbors each time, so shapes and rounding change. When the top two logits are within that noise the argmax flips, and autoregression turns one different token into a different text.

The Thinking Machines analysis blames missing batch invariance rather than atomic adds: 1,000 identical requests to Qwen3-235B gave 80 distinct completions, and 1 with batch-invariant kernels, at a speed cost. Consequences: flaky evals, and a trainer versus rollout log-probability mismatch in RL.

Core Compare the per-step cost of decoding with and without a KV cache.

Without a cache each new token re-runs the network over a prefix of length \(t\): \(\approx 2N_{\text{mm}}\, t\) FLOPs, so a generation costs \(O(n^2)\) in weight-matmul FLOPs. With a cache a step costs \(2N_{\text{mm}}\) plus \(4Ln_hd_h\,t\) for attention, so the weight work is \(O(n)\). Prompt 2,048 plus 256 new tokens: 556,928 token-positions without the cache against 2,303 with it, 242 times fewer.

The cost moves to memory: \(2Ln_{kv}d_hb\) bytes per token (128 KiB for Llama-3-8B), all read every step. At \(t = 2048\) attention is 1.07 GFLOP against 15 GFLOP for the weights, but at large batch and long context the bytes dominate.

Deep-dive How does speculative decoding speed up generation without changing the output distribution?

Decode is memory-bound, so scoring \(\gamma + 1\) tokens in one pass costs about the same as scoring one: weights and cache are read once and intensity only rises to \(\gamma + 1\) FLOPs/byte. A cheap draft \(q\) proposes \(\gamma\) tokens and the target computes \(p\) at all \(\gamma+1\) positions in one pass. Accept draft token \(x\) with probability \(\min(1, p(x)/q(x))\). At the first rejection, resample from \(\text{norm}(\max(0, p-q))\) and stop. If all are accepted, take a bonus token from the target.

Exactness: the probability of emitting \(x\) is \(q(x)\min(1, p/q) + (1-\alpha)\,\text{norm}(\max(0,p-q))(x) = \min(p,q) + (p - \min(p,q)) = p(x)\), with \(\alpha = \sum_x \min(p,q)\). Check: \(p = (0.6, 0.3, 0.1)\), \(q = (0.4, 0.4, 0.2)\) gives \(\alpha = 0.8\), residual \((1, 0, 0)\), and token 0 is emitted with probability \(0.4 + 0.2 = 0.6\). Tokens per pass \(= (1-\alpha^{\gamma+1})/(1-\alpha)\); the speedup divides that by \(1+\gamma c\). Temperature and truncation are folded into \(p\) and \(q\) first. The guarantee is distributional, not bitwise, and gains shrink as batch grows.

Deep-dive Design question: serve Llama-3-8B chat on one H100 with 4K contexts and a 20 ms TPOT target. What batch size, and what limits you?

Step time must be at most 20 ms. With \(t_{\text{step}} = (16.06 + 0.537 B)\text{ GB} / 3.35\text{ TB/s}\), we need \(B \le (67.0 - 16.06)/0.537 \approx 94\), about \(94/0.020 = 4{,}700\) tokens/s. Capacity allows 104 sequences at 90% memory use, so the TPOT target binds first. With a 30 ms target \(B\) would be 157 and capacity (104) would bind instead.

Levers, roughly by cost: (1) shrink the KV term with FP8 KV, shorter or sliding-window contexts, and prefix caching; (2) continuous batching plus PagedAttention to keep the batch full without fragmentation; (3) speculative decoding for more tokens per step at low batch; (4) chunked prefill so long prompts do not spike TPOT; (5) tensor parallelism on more GPUs, at a communication cost. Measure TTFT and TPOT percentiles on your real length distribution: the mean context sets the KV traffic.

Deep-dive How would you implement a KV cache, and what are the failure modes of concatenation, preallocation and paging?

Concatenation (torch.cat per step, as in Hugging Face's dynamic cache) is trivial, but each step allocates a new tensor and copies all \(t\) entries, and it fragments memory. Preallocation of \((B, n_{kv}, S_{\max}, d_h)\) per layer with in-place writes moves \(O(1)\) bytes per step, keeps shapes static for CUDA graphs and torch.compile, and gives the kernel a view of the filled prefix. Its failure mode is internal waste: reserving \(S_{\max}\) per sequence, vLLM measured only 20.4% to 38.2% of memory holding real tokens in earlier systems.

Paging uses fixed-size blocks (16 tokens by default) and a block table per sequence. Waste is confined to the last block and blocks can be shared with copy-on-write, at the price of an indirection in the attention kernel (20% to 26% slower in vLLM's measurement) and more complex scheduling. Also state: store keys after RoPE, keep per-layer lengths, and check capacity before writing so an overflow cannot leave a half-written cache.

Deep-dive What do repetition, frequency and presence penalties do to the logits, and when do they backfire?

With \(c_j\) the number of occurrences of token \(j\): frequency subtracts \(\alpha_f c_j\), multiplying the probability by \(e^{-\alpha_f c_j}\), so each repeat costs more. Presence subtracts \(\alpha_p\) once if \(c_j \gt 0\). CTRL's repetition penalty is multiplicative: seen tokens' logits are divided by \(\theta\) (around 1.2). Because dividing a negative logit by \(\theta \gt 1\) would raise it, Hugging Face multiplies negative logits and divides positive ones, applies it once per distinct token, and includes the prompt by default. vLLM counts only generated tokens for frequency and presence.

They backfire because they cannot separate harmful repetition from required repetition: identifiers, brackets, digits, quoted text, repeated tags in JSON or code. Heavy penalties corrupt structured output. Shipped defaults are mild (1.05 for Qwen2.5-7B-Instruct), and repetition is better fixed at its source with data, post-training and truncated sampling.

The test compares cached generation with recomputing the full sequence every step. An interviewer would expect this in 30 to 40 minutes. exercises/drills/kv_cache.py

Run pytest exercises/tests/test_sampling.py exercises/tests/test_kv_cache.py; add --solutions to check the reference implementations.

Primary sources

  1. Holtzman et al. (2019). The Curious Case of Neural Text Degeneration. Why read it: nucleus sampling, and the cleanest evidence that likelihood-maximizing decoding fails on open-ended text (Tab. 1, Figs. 4 and 5).
  2. Nguyen et al. (2024). Turning Up the Heat: Min-p Sampling and Schaeffer et al. (2025). Min-p, Max Exaggeration. Why read it: a method and an independent critique of its evidence. Read both to practice judging a sampling claim.
  3. Keskar et al. (2019). CTRL. Why read it: §4.1 defines the repetition penalty that Hugging Face still implements.
  4. Shazeer (2019). Fast Transformer Decoding: One Write-Head is All You Need. Why read it: §2.4 is the memory-to-arithmetic analysis of incremental decoding, worth reproducing by hand.
  5. Pope et al. (2022). Efficiently Scaling Transformer Inference. Why read it: the prefill and decode cost model and latency versus cost on PaLM.
  6. Kwon et al. (2023). Efficient Memory Management for LLM Serving with PagedAttention. Why read it: quantifies KV-cache waste (§3, Fig. 2) and the block-table design that removes it.
  7. Yu et al. (2022). Orca and Zheng et al. (2023). SGLang. Why read it: iteration-level scheduling (continuous batching) and RadixAttention prefix caching.
  8. Leviathan et al. (2022). Fast Inference from Transformers via Speculative Decoding and Chen et al. (2023). Accelerating LLM Decoding with Speculative Sampling. Why read it: the accept and resample rule with its proof (Leviathan App. A.1, Chen Thm. 1) and the speedup analysis.
  9. Stahlberg and Byrne (2019). On NMT Search Errors and Model Errors: Cat Got Your Tongue? with Koehn and Knowles (2017). Why read it: the beam search curse, explained by exact search returning the empty output.
  10. He and Thinking Machines Lab (2025). Defeating Nondeterminism in LLM Inference. Why read it: the clearest current account of why temperature 0 is not deterministic, and what batch invariance costs.

Cheat sheet

  • Loop: prefill (\(P\) tokens in parallel, fills the cache), then decode (1 token per step). \(n\) new tokens need \(n\) forward passes.
  • Temperature: \(p_i \propto \exp(z_i/\tau) \propto p_i^{1/\tau}\). \(\tau \to 0\): greedy. \(\tau \to \infty\): uniform. \(\tau = 0\) means greedy in APIs.
  • Top-k: keep \(k\) largest. Top-p: smallest set with mass \(\ge p\) (0.9 to 0.95). Min-p: keep \(p_i \ge p_{\text{base}}\,p_{\max}\) (0.05 to 0.1). All renormalize. Order matters: Hugging Face is temperature, top-k, top-p, min-p; llama.cpp puts temperature last; unset Hugging Face top-k defaults to 50.
  • GPT-2 Large: greedy 73.66% looped, perplexity 1.50 (human 12.38). Nucleus 0.95: 0.36% looped, perplexity 13.13.
  • Penalties: repetition (divide positive, multiply negative logits, \(\theta \approx 1.2\)); frequency \(-\alpha_f c_j\); presence \(-\alpha_p \mathbf{1}[c_j \gt 0]\). They hurt code and structured output.
  • Beam search: keep the \(b\) best cumulative log-probs; normalize by \((5+|Y|)^\alpha/6^\alpha\). Good for translation; bland, looping and cursed at large \(b\) for open-ended text.
  • Temperature 0 is not deterministic on GPUs: non-associative floats, shape-dependent reductions, batch variance, argmax flips.
  • The KV cache is exact (causal). Bytes per token \(= 2 L n_{kv} d_h b\): Llama-3-8B 128 KiB, so 4 GiB at 32K and 16 GiB at 128K. Store K after RoPE. Preallocate, do not concatenate.
  • Weight-matmul intensity \(\approx m\) tokens per read. H100 ridge \(= 989.5/3.35 \approx 295\) FLOPs/byte. Decode at \(B = 1\): about 1.
  • Llama-3-8B on H100: weights 16.06 GB, so 4.79 ms and about 208 tokens/s at \(B = 1\) (202 with a 4K cache). Prefill of 2,048 tokens: \(2NT = 3.29\times10^{13}\) FLOPs, 33 ms at peak, 66 ms at 50% MFU.
  • Batching: \(t_{\text{step}} \approx (W + B\bar S\kappa)/\text{BW}\). At 4K, \(B = 32\) gives 3,225 tokens/s at 101 per user. Ceiling \(\text{BW}/(\bar S\kappa) = 6{,}240\) tokens/s. Memory-bound at any batch above about 390 tokens of context.
  • TTFT = queue + prefill. TPOT \(= (\text{e2e} - \text{TTFT})/(n-1)\). Serving: continuous batching, PagedAttention (16-token blocks), prefix caching, speculative decoding (accept \(\min(1,p/q)\), resample \(\text{norm}(\max(0,p-q))\)).
