Decoding & the KV cache

P0 ~55 min Prereqs: 01 Big picture, 03 Attention, 04 Transformer block

A language model outputs only a distribution over the next token. This page covers how that distribution becomes text (greedy, temperature, top-k, top-p, min-p, penalties, beam search), why generation stores and reuses keys and values (the KV cache), and the performance model that explains why producing one token is memory-bound while reading a prompt is compute-bound.

  • The KV cache from first principles: why cached keys and values are exact, what exactly is stored, bytes per token from a config, and per-step cost with and without it.
  • The inference performance model: why prefill is compute-bound and decode is memory-bound, and a tokens-per-second estimate for an 8B model on an H100 in two minutes.
  • Batching trade-offs: how batch size moves latency and throughput, why the KV cache caps the batch, and what TTFT and TPOT measure.
  • Correctness traps: why temperature 0 is not reproducible on GPUs, and why speculative decoding does not change the output distribution.

The generation loop

Pretraining teaches the model \(p_\theta(x_t \mid x_{\lt t})\) (page 01). To produce text we run the model in a loop, called autoregressive generation 自回归 or decoding 解码. Picking a token from the model's distribution is sampling 采样, and greedy selection is its deterministic special case. One request goes through these stages:

  1. Tokenize the prompt into ids \(x_1,\dots,x_P\) (page 02).
  2. Prefill 预填充: one forward pass over all \(P\) tokens at once. This is the same computation as a training forward pass with a causal mask, so it is parallel over positions. Only the last position's logits \(z_P \in \R^V\) are needed. As a side effect, the pass stores every layer's keys and values for all \(P\) tokens: the KV cache 键值缓存 (see The KV cache).
  3. Choose \(x_{P+1}\) from \(\softmax(z_P)\) with a decoding strategy (next section).
  4. Decode step: feed only \(x_{P+1}\) through the model, reading all earlier positions from the cache. This gives \(z_{P+1}\), from which \(x_{P+2}\) is chosen. Repeat.
  5. Stop at an end-of-sequence id, a stop string, or the length limit. Chat models emit a dedicated end-of-turn token, and engines accept a set of stop ids: the shipped generation_config.json of Qwen2.5-7B-Instruct lists two (151645 and 151643) [Qwen2.5-7B-Instruct config].
@torch.no_grad()
def generate(model, prompt_ids, max_new_tokens, eos_id, pick):
    """prompt_ids: (1, P) LongTensor. pick(logits) -> (1,) token id, e.g. argmax or a sampler."""
    cache = model.new_cache()                       # empty KV cache: one (K, V) pair per layer
    logits = model(prompt_ids, cache)[:, -1]        # PREFILL: P tokens in parallel; logits: (1, V)
    out = []
    for _ in range(max_new_tokens):
        tok = pick(logits)                          # (1,)
        out.append(tok.item())
        if tok.item() == eos_id:
            break
        logits = model(tok[:, None], cache)[:, -1]  # DECODE: one token in; the cache grows by one entry
    return out

Three properties of this loop drive the rest of the page.

  • It is sequential in time. \(n\) new tokens need \(n\) forward passes, because each input depends on the previous choice. Training escapes this with teacher forcing, which feeds all positions in parallel. Decoding cannot, and that single fact produces the performance story in Prefill vs decode.
  • Only the last position's logits are used. Everything before it is context, and the cache lets us read it instead of recomputing it.
  • The model consumes its own outputs. Training always conditions on true prefixes. At inference, a sampled token becomes context for every later step, so the decoding rule shapes the inputs the model sees, and a bad early token can derail the rest of the text.
From your jet tagger

Your tagger made one forward pass per jet, and every particle attended to every other particle. That is the prefill regime: one large parallel pass, compute-bound. It had no loop, no notion of "next", and no cache, because with bidirectional attention adding one input changes every representation. A language model uses causal masking precisely so that adding a token changes nothing about the past. That property is what makes the KV cache exact.

Decoding strategies: from logits to a token

At each step the model returns logits \(z \in \R^V\), and its distribution is \(p = \softmax(z)\). A decoding strategy maps \(p\) to one token. Everything below acts on the last position's logits only and is cheap next to the forward pass (\(V\) is about 128K for Llama 3).

Greedy decoding and why it degenerates

Greedy decoding takes \(x_t = \argmax_i z_i\). It is deterministic and needs no random numbers, and it is the standard choice for benchmarks. For open-ended generation it is bad, and the effect is large. Holtzman et al. generated 5,000 passages of up to 200 tokens with GPT-2 Large under different decoders and measured the result [Holtzman et al. 2019, Tab. 1]:

Perplexity is measured by the generating model on its own output. "Repetition %" is the share of generations that end in a repeated loop. HUSE combines human judgments with a statistical discriminator.

Two mechanisms explain the greedy row. First, repetition feeds itself: the probability the model assigns to a phrase increases with each repetition already in the context, "creating a positive feedback loop" [Holtzman et al. 2019, Fig. 4]. Once greedy picks a repeat, nothing pulls it back out. Second, human text is not high-probability text. Its per-token probability is much lower than that of decoded text (perplexity 12.4 versus 1.5), because people avoid stating the obvious, while a likelihood-trained model's argmax is the most generic continuation [Holtzman et al. 2019, §4.3]. So the aim is not "the most probable text". It is text with the statistics of human text, and that requires randomness with a controlled tail.

Instruction-tuned models are far less prone to this, but long generations can still loop. The DeepSeek-R1 model card recommends a temperature of 0.5 to 0.7 (0.6 recommended) "to prevent endless repetitions or incoherent outputs" [DeepSeek-R1 model card].

Temperature

Temperature 温度 \(\tau\) rescales the logits before the softmax. This is the Boltzmann distribution from statistical physics with energies \(-z_i\), and it is applied to language models as in Holtzman et al. (their Eq. 4):

\[ p_i(\tau) = \frac{\exp(z_i/\tau)}{\sum_j \exp(z_j/\tau)} \;\propto\; p_i^{\,1/\tau} \]
\(\tau < 1\) sharpens the distribution, \(\tau > 1\) flattens it, \(\tau = 1\) is the model's own distribution

Limits: with \(\Delta_i = z_{\max} - z_i \gt 0\) we have \(p_i / p_{\max} = e^{-\Delta_i/\tau}\), which goes to 0 as \(\tau \to 0^+\), so the distribution collapses onto the argmax (uniform over ties). As \(\tau \to \infty\) every ratio goes to 1 and the distribution becomes uniform, \(1/V\). Entropy rises monotonically with \(\tau\). Because temperature raises probabilities to the power \(1/\tau\), \(\tau = 0.5\) squares them: \([0.5, 0.3, 0.15, 0.05]\) becomes \([0.685, 0.247, 0.062, 0.007]\).

The formula divides by \(\tau\), so APIs define \(\tau = 0\) as greedy. vLLM's sampler, for instance, switches to argmax below \(10^{-5}\) [vLLM sampler.py]. Temperature is the only knob that reshapes the whole distribution. The next three methods cut it instead. One more point matters later for RL (page 22): the policy you actually sample from is \(\softmax(z/\tau)\), so a policy-gradient loss must compute log-probabilities with the same \(\tau\).

Cutting the tail: top-k, top-p, min-p

Sampling from the full softmax fails for a specific reason. With \(V \approx 128\text{K}\), the tail holds tens of thousands of tokens that each have tiny probability but together carry real mass, so they are "over-represented in the aggregate" and a sample regularly lands in incoherent territory [Holtzman et al. 2019, §1]. Lowering \(\tau\) shrinks the tail but costs diversity: sampling at \(\tau < 0.9\) already sharply increases repetition (their Fig. 9). Truncation methods zero the tail explicitly and renormalize the rest.

  • Top-k keeps the \(k\) largest probabilities. Fan et al. used \(k = 10\) for story generation [Fan et al. 2018, §5.4]. The flaw is that one \(k\) must serve every context: a flat distribution over hundreds of reasonable words needs a large \(k\), a peaked one needs \(k = 1\) [Holtzman et al. 2019, Fig. 5].
  • Top-p, or nucleus sampling 核采样, keeps the smallest set \(V^{(p)}\) of top tokens whose total probability is at least \(p\), then renormalizes: \(P'(x) = P(x) / \sum_{v \in V^{(p)}} P(v)\) for \(x \in V^{(p)}\) [Holtzman et al. 2019, Eqs. 2-3]. The set grows when the model is unsure and shrinks to one token when it is confident.
  • Min-p keeps every token with \(p_i \ge p_{\text{base}} \cdot p_{\max}\), then renormalizes [Nguyen et al. 2024, §3.1]. The threshold scales with the top token's probability. In logit terms, after temperature it keeps every token within \(\tau \ln(1/p_{\text{base}})\) of the top raw logit, and it needs a maximum, not a sort.

A practical rule: pick one truncation method plus a temperature. Use greedy or \(\tau \le 0.3\) for tasks with a checkable answer, \(\tau \approx 0.6\) to 1.0 with top-p or min-p for chat and writing, and \(\tau = 1\) without truncation when you need samples that match the model's own distribution (for example RL rollouts, page 24). Order of operations

The methods do not commute, and libraries disagree. I checked the source of each (as of September 2026):

Three consequences follow, and all three are interview material.

  1. Temperature before or after truncation. Top-k is unaffected by \(\tau\) (dividing by a positive number preserves rank order). Top-p and min-p are not. With temperature first, raising \(\tau\) enlarges their candidate sets. With temperature last, the candidate set is fixed and \(\tau\) only changes how you sample inside it. On the Figure 2 logits with top-k 5, top-p 0.9 and min-p 0.2, Hugging Face's order keeps 2 tokens at \(\tau = 0.5\) and 5 at \(\tau = 2\), while llama.cpp's order keeps 4 in both cases.
  2. Top-p depends on what ran before it; min-p does not. Each Hugging Face warper takes a softmax of the surviving logits, so top-p's cumulative mass is relative to the survivors. With probabilities \([0.4, 0.3, 0.2, 0.1]\), top-p 0.5 alone keeps two tokens. After top-k 2 the survivors renormalize to \([0.571, 0.429]\), and top-p 0.5 keeps one. Min-p compares \(p_i / p_{\max}\), which renormalization leaves unchanged.
  3. Min-p before top-p is at least as aggressive as after it. If min-p first removes mass \(1 - M\), the renormalized top-p threshold \(p\) equals \(pM\) in original units, which is lower, so the prefix is shorter. A quick simulation on 5,000 random logit vectors never gave a larger set for the vLLM order, and gave a strictly smaller one in 3,360 of them.

The upshot is practical: when you compare numbers across frameworks, or reproduce a paper's setup, check the order and the defaults. The min-p paper's own two human studies applied temperature after and before truncation respectively [Schaeffer et al. 2025, §2.4].

Repetition, frequency and presence penalties

Penalties attack repetition by editing logits based on what has already been generated. The repetition penalty 重复惩罚 of CTRL divides the temperature by a factor \(\theta\) for tokens already in the generated set \(g\): \(p_i \propto \exp\big(z_i / (\tau \cdot I(i \in g))\big)\) with \(I = \theta\) inside \(g\) and 1 outside, and they found \(\theta \approx 1.2\) a good balance with greedy decoding [Keskar et al. 2019, §4.1]. Dividing a negative logit by \(\theta \gt 1\) would raise it, so Hugging Face multiplies negative logits and divides positive ones, applies the penalty once per distinct token, and includes the prompt by default for decoder-only models [logits_process.py].

Frequency and presence penalties are additive. With \(c_j\) the number of times token \(j\) appeared in the output so far:

\[ z_j \leftarrow z_j - \alpha_{\text{freq}}\, c_j - \alpha_{\text{pres}}\, \mathbf{1}[c_j \gt 0] \]

vLLM implements exactly this, noting that it follows the OpenAI API definition [vLLM layers/utils.py]. Subtracting from a logit multiplies the probability by \(e^{-\alpha c_j}\). The frequency term grows with each repeat, while the presence term is a one-time charge for using a token at all.

All penalties share one flaw: they cannot tell harmful repetition from necessary repetition. Variable names, closing brackets, digits and quoted text must repeat, so heavy penalties damage code, JSON and math. Modern post-trained models need them less, and shipped defaults are mild (Qwen2.5-7B-Instruct uses a repetition penalty of 1.05).

The whole sampler fits in a screen. This is the core of the drill in exercises/solutions/sampling.py:

import torch
import torch.nn.functional as F

def top_k_filter(z, k):                                   # z: (..., V) logits
    kth = torch.topk(z, k, dim=-1).values[..., -1:]       # k-th largest logit per row
    return z.masked_fill(z < kth, float("-inf"))          # ties with the k-th value survive

def top_p_filter(z, p):
    probs = z.softmax(-1)
    sp, order = probs.sort(dim=-1, descending=True, stable=True)
    before = F.pad(sp.cumsum(-1)[..., :-1], (1, 0))       # probability mass strictly before each token
    drop = torch.zeros_like(probs, dtype=torch.bool).scatter(-1, order, before >= p)
    return z.masked_fill(drop, float("-inf"))             # keep a token only while the mass so far is < p

def min_p_filter(z, p_min):
    probs = z.softmax(-1)
    return z.masked_fill(probs < p_min * probs.amax(-1, keepdim=True), float("-inf"))

def sample(z, gen, temperature=1.0, top_k=None, top_p=None, min_p=None):
    if temperature == 0:
        return z.argmax(-1)                               # greedy
    z = z / temperature                                   # 1) temperature first (Hugging Face order)
    if top_k: z = top_k_filter(z, top_k)                  # 2) each filter renormalizes over survivors
    if top_p: z = top_p_filter(z, top_p)                  # 3)
    if min_p: z = min_p_filter(z, min_p)                  # 4)
    probs = z.softmax(-1)
    ids = torch.multinomial(probs.reshape(-1, probs.size(-1)), 1, generator=gen)
    return ids.reshape(probs.shape[:-1])

Beam search, and why chat models rarely use it

Beam search 束搜索 is a deterministic search for a high-probability sequence. It keeps \(b\) partial hypotheses (the beam). At each step it expands every hypothesis by all \(V\) tokens, scores each candidate by its cumulative log-probability \(\sum_t \log p(x_t \mid x_{\lt t})\), and keeps the best \(b\) of the \(bV\) candidates. Hypotheses that end in EOS are set aside as finished. It costs \(b\) times the compute and \(b\) times the KV cache per request, and each step must reorder the cache so that every surviving hypothesis points at its parent's entries.

Because every extra token adds a negative log-probability, raw scores favor short outputs. GNMT's fix divides by a length penalty, \(s(Y,X) = \log P(Y \mid X) / lp(Y) + cp(X;Y)\) with \(lp(Y) = (5 + |Y|)^\alpha / 6^\alpha\), where \(\alpha \in [0.6, 0.7]\) was usually best on their development sets and \(cp\) is an NMT-specific coverage penalty. On WMT'14 En-Fr, tuning both terms raised BLEU from 30.3 (pure log-probability) to 31.4 [Wu et al. 2016, §7, Tab. 2].

Where it works. In translation, summarization and speech recognition the input nearly determines the output, so the mode of the distribution is what you want. GNMT used beams of 8 to 12 hypotheses, and Shazeer's translation experiments used beam 4 with \(\alpha = 0.6\) [Shazeer 2019, §4.2].

Why it fails for chat and open-ended text, in order of importance:

  1. Mode-seeking output is bland and loops. In Table 1 above, beam search with \(b = 16\) has perplexity 1.48 (human text: 12.38) and 28.94% looped generations. With \(b = 32\), GPT-2 Large loops on an institution's name, and for \(b \ge 64\) both GPT-2 Large and XL "prefer to stop generating immediately after the given context" [Holtzman et al. 2019, Fig. 1]. Fan et al. saw the same: beam output is "short and generic" [Fan et al. 2018, §5.4].
  2. The beam search curse. Larger beams find higher-probability outputs that are worse translations. Koehn and Knowles found the optimal beam between 4 and about 30 (30 to 50 with length normalization), with quality falling beyond it, mainly because outputs get shorter [Koehn and Knowles 2017, §3.6, Fig. 10]. Stahlberg and Byrne then ran exact search under a Transformer model and found that for 51.8% of sentences the highest-scoring output is the empty string (BLEU 2.1 with exact search against 30.3 for beam 10). Beam search works only because it makes search errors [Stahlberg and Byrne 2019, Tab. 1]. The model's probability is a poor objective, and better search makes it worse.
  3. Cost and systems friction. \(b\) sequences per request multiply memory traffic and complicate continuous batching. PagedAttention shares prompt blocks across beams, saving 37.6% to 55.2% of KV memory for beam width 2 to 6 on their Alpaca trace [Kwon et al. 2023, §6.3], but the compute multiplier remains.

In current practice, open-ended and reasoning models are sampled, often several times, with the answers filtered or aggregated (page 24), rather than beam-searched.

Reproducibility: seeds and nondeterministic GPUs

There are two separate sources of randomness. Sampling randomness is controlled by a seed: the same logits and the same generator state give the same token. Serving engines keep a generator per seeded request (vLLM passes per-request generators to its sampler). Numerical randomness is subtler, and it is why "temperature 0" is not a reproducibility guarantee.

  • Floating-point addition is not associative: \((a+b)+c \ne a+(b+c)\) after rounding, and bf16 keeps only about three decimal digits.
  • GPU kernels choose a reduction order from the input shape (tile sizes, split-K, split-KV attention). The same request lands in different batches on different runs, so its logits differ in the last bits.
  • When the top two logits are closer than that rounding noise (two synonyms, say), the argmax flips. The new token changes the context, and the two continuations then diverge for the rest of the text.

The Thinking Machines analysis argues that the usual explanation (concurrent atomic adds) is not the main cause, since a typical LLM forward pass contains no atomic adds and a fixed batch gives deterministic output. The cause is a lack of batch invariance: results depend on batch size, which varies with server load. Their test sent one prompt 1,000 times at temperature 0 to Qwen3-235B and got 80 unique completions. With batch-invariant kernels all 1,000 were identical, at some cost in speed [He and Thinking Machines Lab 2025].

PyTorch's own documentation adds that results are not guaranteed to reproduce across releases, commits or platforms, or between CPU and GPU, even with identical seeds. torch.use_deterministic_algorithms(True) removes nondeterministic PyTorch ops [PyTorch reproducibility notes], but it does not control how a serving engine composes batches. This matters for evaluation, for debugging, and for RL, where the trainer and the inference engine can disagree on log-probabilities (page 25). Even speculative decoding, whose guarantee is about the output distribution, is not bitwise reproducible: Chen et al. note that "a single token deviating due to numerics could result in two sequences diverging wildly" [Chen et al. 2023, §Evaluation].

The KV cache

Why the cache is exact

In layer \(\ell\), token \(t\) contributes a query, key and value (row vectors, per head): \(q_t = x_t W^Q\), \(k_t = x_t W^K\), \(v_t = x_t W^V\), and its attention output is

\[ o_t = \sum_{j \le t} \softmax_j\!\left(\frac{q_t \cdot k_j}{\sqrt{d_h}}\right) v_j . \]

Causal masking means the hidden state of token \(j\) at every layer depends only on tokens \(1..j\). By induction over layers, \(k_j^{(\ell)}\) and \(v_j^{(\ell)}\) for \(j \lt t\) do not change when token \(t\) is appended. So we compute each key and value once and store it. The KV cache 键值缓存 is therefore exact, not an approximation. A bidirectional encoder, like the one in your tagger, has no such cache: adding one input changes every position's representation.

What is stored, and what is not

Per layer and per KV head the cache holds \(K\) and \(V\) after the linear projections. Keys are stored after RoPE (page 05): the rotation of a key depends only on that key's own position, so it can be applied once at write time, while each new query is rotated at its own position when used. Not stored: queries (used once and discarded), attention scores, FFN activations, and earlier tokens' hidden states, none of which later tokens need.

Why cache \(K, V\) rather than the layer input \(x_j\)? Caching \(x_j\) (\(d\) numbers per layer) would force us to redo the \(K\) and \(V\) projections for every past token at every step, roughly \(2\,t\,d \cdot 2 n_{kv} d_h\) FLOPs per layer. The cache trades memory for compute. DeepSeek's MLA caches a compressed latent, which changes that trade (page 07).

How big is it

\[ \text{KV bytes per token} = 2 \cdot L \cdot n_{kv} \cdot d_h \cdot b \]
2 for K and V; \(b\) = bytes per element (2 for bf16). Page 07 derives the MQA, GQA and MLA variants.

Llama-3-8B (\(L = 32\), \(n_{kv} = 8\), \(d_h = 128\), bf16): \(2 \cdot 32 \cdot 8 \cdot 128 \cdot 2 = 131{,}072\) B = 128 KiB per token. At 32K tokens (a valid length for Llama 3.1, not the 8K base model) that is \(128 \text{ KiB} \times 32{,}768 = 4\) GiB per sequence, and 16 GiB at 128K. A batch of 32 sequences at 4K tokens is \(32 \times 4096 \times 128 \text{ KiB} = 16\) GiB. For comparison, OPT-13B costs \(2 \cdot 5120 \cdot 40 \cdot 2 = 819{,}200\) B per token (the vLLM paper writes 800 KB), or 1.6 GB for a 2,048-token sequence [Kwon et al. 2023, §3].

Per-step cost with and without it

Let \(N_{\text{mm}}\) be the parameters that take part in matmuls (7.50B for Llama-3-8B: the layers plus the output head, without the embedding lookup). Without a cache, producing the token after \(t\) tokens re-runs the forward pass over all \(t\) tokens: about \(2 N_{\text{mm}}\, t\) matmul FLOPs. With a cache it processes one token: \(2 N_{\text{mm}}\) FLOPs plus attention over the cache, \(4 L\, n_h d_h\, t\) FLOPs. Summed over a generation, the cache turns the weight-matmul work from quadratic in length to linear. Example: prompt \(P = 2048\), \(n = 256\) new tokens. Without a cache the loop pushes \(\sum_{i=0}^{255} (2048 + i) = 556{,}928\) token-positions through the network. With one it pushes \(2048 + 255 = 2{,}303\), a factor of 242.

Attention itself is still quadratic in total (each step touches \(t\) entries), but in FLOPs it is minor: at \(t = 2048\) it is \(4 \cdot 32 \cdot 128 \cdot 2048 \cdot 32 = 1.07\) GFLOP per new token against 15.0 GFLOP for the weights. What the cache does not remove is the bytes: every step reads the whole cache. That is the subject of the next section.

Causal masking makes earlier keys and values independent of later tokens, so the cache is exact.
Evidence
242 times fewer token-positions in the example above. Shazeer's incremental-attention analysis shows the total arithmetic stays \(\Theta(b n d^2)\) across \(n\) steps [Shazeer 2019, §2.4.1].
Cost
Memory of \(2 L\, n_{kv}\, d_h\, b\) bytes per token per sequence, reread in full at every step, so it limits both batch size (capacity) and speed (bandwidth). Sequences of unknown length also fragment memory.
Used by
Every autoregressive inference stack. Hugging Face has a dynamic cache (torch.cat each step) and a static one (preallocated, written with index_copy_) [cache_utils.py]. vLLM pages it (below).

Implementation: preallocate, do not concatenate

The simplest cache appends with torch.cat at every step. That allocates a new tensor and copies all \(t\) existing entries, so each step moves the cache bytes twice more (read old, write new) on top of the attention read, and repeated reallocation fragments memory. The alternative is to allocate \((B, n_{kv}, S_{\max}, d_h)\) once per layer, write the new entries in place, and hand attention a view of the filled prefix. Tensor shapes then stay fixed, which graph capture (CUDA graphs, torch.compile) requires. This is the drill in exercises/solutions/kv_cache.py:

class KVCache:
    def __init__(self, n_layers, batch, n_kv, max_len, d_h, dtype=torch.bfloat16, device="cuda"):
        shape = (batch, n_kv, max_len, d_h)                       # allocated once, never resized
        self.k = [torch.zeros(shape, dtype=dtype, device=device) for _ in range(n_layers)]
        self.v = [torch.zeros(shape, dtype=dtype, device=device) for _ in range(n_layers)]
        self.n = [0] * n_layers                                   # cached positions per layer

    def update(self, layer, k_new, v_new):                        # (B, n_kv, T, d_h); K already has RoPE
        s, T = self.n[layer], k_new.shape[2]
        self.k[layer][:, :, s:s + T] = k_new                      # in-place write: O(T) bytes moved
        self.v[layer][:, :, s:s + T] = v_new
        self.n[layer] = s + T
        return self.k[layer][:, :, :s + T], self.v[layer][:, :, :s + T]   # views, no copy

Preallocation has its own problem: reserving \(S_{\max}\) slots per sequence wastes memory when actual lengths vary. The vLLM paper measured that in earlier serving systems only 20.4% to 38.2% of KV-cache memory held actual token states [Kwon et al. 2023, Fig. 2]. That waste is what PagedAttention removes (Serving teasers).

Prefill vs decode: the performance model

Hardware assumption for all numbers below: one H100 SXM, with 80 GB of HBM3 and 3.35 TB/s of bandwidth, and 1,979 TFLOPS of BF16 tensor-core throughput "with sparsity" on NVIDIA's page [NVIDIA H100]. Dense throughput is half the sparse figure, 989.5 TFLOP/s; the same factor of two appears in the H100 NVL numbers of a recent profiling study (835 dense, 1,671 sparse) [Siavashi et al. 2026, §2.1]. Model: Llama-3-8B in bf16.

Arithmetic intensity: why the two phases differ

Arithmetic intensity 算术强度 is FLOPs performed per byte moved from memory. A kernel is memory-bound 访存受限 when its intensity is below the hardware's ridge point, and compute-bound 计算受限 above it. For an H100 the ridge is \(989.5 \text{ TFLOP/s} \,/\, 3.35 \text{ TB/s} \approx 295\) FLOPs per byte. Consider one weight matmul \(y = xW\) with \(x\) of shape \(m \times d_{\text{in}}\) and \(W\) of shape \(d_{\text{in}} \times d_{\text{out}}\) in bf16:

\[ \frac{\text{FLOPs}}{\text{bytes}} \approx \frac{2\, m\, d_{\text{in}} d_{\text{out}}}{2\, d_{\text{in}} d_{\text{out}}} = m \quad \text{(weights dominate the bytes when } m \ll d\text{)} \]

The intensity equals the number of tokens \(m\) sharing one read of the weights. In prefill, \(m\) is the prompt length, thousands of tokens, far above 295: compute-bound. In decode, \(m\) is the batch size, and at batch 1 the intensity is about 1 FLOP per byte: 0.3% of the ridge. The tensor cores idle while HBM streams the weights, so the step time is set by bytes, not FLOPs. Pope et al. state the same thing in their model: at small batch and short context the time to load weights dominates, and at large batch and long context the time to load the KV cache dominates [Pope et al. 2022, §2].

Decode: time per token is bytes over bandwidth

\[ t_{\text{step}} \;\gtrsim\; \max\!\left( \underbrace{\frac{W + B\,\bar S\,\kappa}{\text{BW}}}_{\text{memory time}},\ \underbrace{\frac{2 N_{\text{mm}} B + 4 L n_h d_h\, B \bar S}{\text{peak FLOP/s}}}_{\text{compute time}} \right) \]
\(W\) weight bytes, \(\kappa\) KV bytes per token, \(\bar S\) mean context length, \(B\) batch size. A roofline lower bound: real kernels reach a fraction of it.

Weights. From the config: per layer, attention has \(4096 \cdot 4096 \cdot 2 + 4096 \cdot 1024 \cdot 2 = 41{,}943{,}040\) parameters and the SwiGLU FFN has \(3 \cdot 4096 \cdot 14336 = 176{,}160{,}768\), plus 8,192 norm weights, for 218,112,000 per layer. Times 32 layers, plus the embedding and the untied output head (\(128{,}256 \cdot 4096 = 525{,}336{,}576\) each) and a final norm: \(N = 8{,}030{,}261{,}248\). In bf16 that is 16.06 GB.

Batch 1. Each step must read every weight once: \(16.06 \text{ GB} / 3.35 \text{ TB/s} = 4.79\) ms, so at most 208 tokens per second. Adding the KV cache of a 4K-token context (0.54 GB) gives 4.95 ms and 202 tokens/s. The bound depends slightly on what you count: the embedding table is a lookup, not a stream, so excluding it gives 15.0 GB, 4.48 ms and 223 tokens/s. The compute time is \(2 N_{\text{mm}} / 989.5\text{ TFLOP/s} = 0.015\) ms, so the model uses 0.3% of peak FLOP/s. Real engines reach a fraction of the bound. A profiling preprint measured 5.27 ms per token for Llama-3-8B at batch 1 and a 2,048-token context on an H100 NVL with vLLM and FlashAttention-3, against a roofline of 4.19 ms for that GPU's 3.9 TB/s, about 80% [Siavashi et al. 2026, §5]. It is one measurement on a different SKU, so treat it as a sanity check, and expect roughly 150 to 180 tokens/s on an SXM part.

Batching: weights are shared, caches are not

With batch \(B\), one read of the weights serves \(B\) tokens, so the weight term \(W\) is amortized. Each sequence has its own cache, so the KV term grows linearly with \(B\). Take 4K-token contexts. The capacity limit is what fits in HBM: with 90% of 80 GB usable (vLLM's current default gpu_memory_utilization is 0.92 [cache.py]), \((72 - 16.06) \text{ GB} / 0.537 \text{ GB} = 104\) sequences.

Read the table three ways.

  • Latency versus throughput. From \(B = 1\) to \(B = 32\), total throughput rises 16 times while per-user speed falls by half (202 to 101 tokens/s). Batching trades individual latency for aggregate throughput, and the first steps of the trade are nearly free: going from 1 to 8 sequences adds 23% to the step time and gives 6.5 times the throughput, because the KV slice is still small next to the weight slice.
  • The ceiling is the KV cache. As \(B \to \infty\), the weight term vanishes and throughput approaches \(\text{BW} / (\bar S \kappa) = 3.35 \text{ TB/s} / 0.537 \text{ GB} = 6{,}240\) tokens/s per GPU at 4K context. This is Shazeer's \(n/d\) term made numeric: attention re-reads a per-sequence cache that no batching can share [Shazeer 2019, §2.4.1].
  • It never becomes compute-bound at this context. Compute time stays below 2 ms against 21 ms of memory time, and MFU is only 8% at \(B = 104\). For a large batch, per-sequence intensity is \((2 N_{\text{mm}} + 4 L n_h d_h \bar S) / (\kappa \bar S) = 4 + 2N_{\text{mm}} / (\kappa \bar S)\). The 4 is \(n_h / n_{kv}\), page 07's attention intensity. That crosses the 295 ridge only when \(\bar S \lesssim 390\) tokens. Above that, GQA-8 decode stays memory-bound at any batch size.

The same effect appears in PaLM 540B with multi-query attention (a tiny KV cache): decode reached 33% MFU at batch 512 and only 14% at batch 64, while prefill reached 76% at batch 512 and 43% at batch 1 on the same hardware [Pope et al. 2022, Tab. 2]. The levers to raise the ceiling are architectural (fewer or smaller KV heads, page 07), numeric (KV quantization) and systemic (page 17).

Prefill: the compute-bound side

A forward pass over \(T\) tokens costs about \(2 N T\) FLOPs (each parameter does one multiply-add per token) [Pope et al. 2022, §2]. For \(T = 2048\): \(2 \times 8.03 \times 10^9 \times 2048 = 3.29 \times 10^{13}\) FLOPs. At 100% of peak that is \(3.29 \times 10^{13} / 989.5 \times 10^{12} = 33.2\) ms. Nobody reaches peak, and 50% MFU (model FLOPs utilization) is a fair planning number, giving 66.5 ms, or 30,800 prompt tokens per second, about 150 times the token rate of one decode stream. The weights are still read once, 4.8 ms, which is small against 33 ms, so the pass is compute-bound. Pope et al. report prefill MFU between 43% and 76% on PaLM (Tab. 2).

The rule \(2NT\) is a good estimate here, and a slight overestimate. Counting exactly (no FLOPs for the embedding lookup, the output head on the last position only, causal attention over half the score matrix) gives \(2.97 \times 10^{13}\) FLOPs, 10% less. At long contexts the quadratic attention term matters: at \(T = 32{,}768\), attention is 38% of the FLOPs and the total is \(7.4 \times 10^{14}\) (0.75 s at peak, 1.5 s at 50% MFU), 40% more than \(2NT\) predicts.

Metrics and the trade-off

Serving is judged on four numbers, defined the way NVIDIA's benchmarking tools define them [NVIDIA benchmarking guide]:

  • Time to first token (TTFT, 首 token 延迟): request arrival to the first output token. It includes queueing, prefill and network. For the 2,048-token prompt on an idle H100 it is about 70 ms, and it grows linearly (then quadratically) with prompt length.
  • Time per output token (TPOT, also called inter-token latency): \((\text{e2e latency} - \text{TTFT}) / (\text{output tokens} - 1)\). At batch 1 it is one decode step.
  • End-to-end latency \(= \text{TTFT} + (n-1)\cdot\text{TPOT}\).
  • Throughput: output tokens per second across all requests.

Batch size moves TPOT and throughput in opposite directions (Table above). Pope et al. show the same trade on PaLM: cost per token is lowest at batches above about 512, while shrinking the batch improves latency at a higher cost per token [Pope et al. 2022, §4.4]. A long prefill also stalls the decode steps that share its GPU, which spikes TPOT for everyone else. Chunked prefill and disaggregating prefill from decode address that (page 17).

Serving teasers

One paragraph each. Page 17 treats them properly.

Continuous batching 连续批处理. A static batch runs until its longest sequence finishes, so short requests wait and the GPU idles. Orca schedules at the granularity of a single model iteration: finished sequences leave and waiting requests join at every step, and batching is applied only to a selected set of operations ("selective batching") so that sequences at different positions can share a step [Yu et al. 2022, OSDI]. Orca reported 36.9 times the throughput of FasterTransformer at the same latency on GPT-3 175B. Every modern engine schedules this way.

PagedAttention. Contiguous per-sequence reservations waste most of the cache (20.4% to 38.2% useful, above). PagedAttention splits each sequence's cache into fixed-size blocks (16 tokens by default) allocated on demand, and a per-sequence block table maps logical positions to physical blocks, exactly like virtual memory. Waste is limited to the last partial block, blocks can be shared across sequences with copy-on-write, and vLLM reports 2 to 4 times the throughput of FasterTransformer and Orca at the same latency. The price is a slower attention kernel: 20% to 26% higher kernel latency than FasterTransformer's [Kwon et al. 2023, Abstract, §7.1].

Prefix caching 前缀缓存. A token's keys and values depend only on the tokens before it, so two requests that start with the same tokens (a system prompt, few-shot examples, earlier chat turns) can share those cache entries and skip that part of prefill. SGLang's RadixAttention keeps cached prefixes in a radix tree with LRU eviction. The system reports up to 6.4 times higher throughput on its workloads (the gain combines several optimizations), with cache hit rates of 50% to 99% across its benchmarks. Its Chatbot Arena deployment saw hit rates of 52.4% and 74.1% on two models and a 1.7 times lower first-token latency for Vicuna-33B [Zheng et al. 2023, §3, §6]. It helps TTFT and capacity, not the per-token decode cost.

Speculative decoding
Problem
Decode is memory-bound: each step reads all weights and the whole cache to produce one token, and steps are sequential.
Idea
A cheap draft distribution \(q\) proposes \(\gamma\) tokens. The target model scores all \(\gamma + 1\) positions in one forward pass. Accept draft token \(x\) with probability \(\min(1, p(x)/q(x))\). At the first rejection, resample from \(\text{norm}(\max(0, p - q))\) and discard the rest. If all are accepted, sample one bonus token from the target.
Why it works
Scoring \(\gamma + 1\) tokens is one pass with intensity \(\gamma + 1\) FLOPs per byte, still far below the 295 ridge, so it costs about one decode step while yielding several tokens. Exactness: \(P(x) = q(x)\min(1, p/q) + (1-\alpha)\cdot\text{norm}(\max(0,p-q))(x) = p(x)\), where \(\alpha = \sum_x \min(p, q)\) is the acceptance rate.
Evidence
2.3 to 3.4 times faster on T5-XXL at batch 1 with the best draft (T5-small), with identical outputs [Leviathan et al. 2022, Tab. 2]. Chinchilla 70B: 1.92 to 2.46 times on XSum and HumanEval [Chen et al. 2023, Tab. 1].
Cost
Wasted compute on rejected tokens, a draft model to host, and shrinking gains as the batch grows and decode approaches compute-bound. The distribution is preserved, but the bits are not identical to plain decoding.
Used by
Both original papers (Google and DeepMind). Variants that drop the separate draft model, and deployment details, are on page 17.

The expected number of tokens per target pass is \((1 - \alpha^{\gamma+1}) / (1 - \alpha)\), and the wall-clock speedup is that divided by \(1 + \gamma c\), where \(c\) is the draft-to-target cost ratio [Leviathan et al. 2022, Eq. 1, Thm. 3.8]. With \(\alpha = 0.8\), \(\gamma = 4\) and \(c = 0.05\), that is 3.36 tokens per pass and a 2.8 times speedup. In a memory-bound decoder \(c\) is close to the ratio of bytes read, so a draft with 1/16 of the target's weights has \(c \approx 0.06\).

Common misconceptions

  • "Temperature 0 gives the same output on every run." Not on GPUs. Kernel reduction order depends on the batch, logits differ in the last bits, near-ties flip the argmax, and the text diverges from there.
  • "Top-p 0.9 keeps 90% of the tokens" or "removes 10% of tokens". It keeps the smallest set holding at least 90% of the probability mass. That set can be one token or thousands, depending on the distribution.
  • "Top-k, top-p and min-p compose in any order." Order and renormalization matter, and Hugging Face, vLLM and llama.cpp differ (temperature first in the first two, last in llama.cpp). The min-p authors also warn against stacking truncations.
  • "The KV cache is an approximation that skips attention." It is exact. It removes the recomputation of earlier tokens' projections and FFNs. Attention still reads every cached key and value at every step.
  • "A bigger batch fixes memory-bound decoding." It amortizes the weight reads only. Each sequence's KV cache is its own, so the per-sequence bytes stay, and throughput saturates near \(\text{BW}/(\bar S \kappa)\).
  • "Beam search finds the best answer, so wider is better." Model probability is a poor objective. Wider beams give shorter outputs and lower BLEU, and exact search returns the empty string for half the sentences in one study.
  • "Decode is slow because it needs many FLOPs." It needs few. At batch 1 an H100 uses 0.3% of its FLOP/s while streaming 16 GB of weights each step.
  • "Speculative decoding is an approximation, like using a smaller model." With the correct accept and resample rule the output distribution equals the target's exactly. What it does not promise is bitwise-identical text.

Interview questions

Warm-up Walk through the generation loop. How does the first step differ from the rest?

Tokenize the prompt. Prefill: one forward pass over all \(P\) prompt tokens in parallel with a causal mask. It writes every layer's keys and values into the KV cache and produces logits for the last position, from which the first token is chosen. Then repeat decode steps: feed the newest token only, compute its \(q, k, v\), append \(k, v\) to the cache, attend over the cache, get logits, choose the next token. Stop on EOS, a stop string or the length limit.

The first step processes \(P\) tokens per weight read (compute-bound) and determines time to first token. Every later step processes one token per sequence (memory-bound) and determines time per output token.

Warm-up What does temperature do? What happens as \(\tau \to 0\) and \(\tau \to \infty\)?

It divides the logits by \(\tau\) before the softmax, so \(p_i \propto \exp(z_i/\tau) \propto p_i^{1/\tau}\). For \(\tau < 1\) the distribution sharpens, for \(\tau > 1\) it flattens. As \(\tau \to 0^+\), \(p_i/p_{\max} = e^{-(z_{\max}-z_i)/\tau} \to 0\) for every non-maximal token, so the limit is greedy (uniform over exact ties). As \(\tau \to \infty\) all ratios tend to 1 and the distribution is uniform over the vocabulary. Entropy increases monotonically with \(\tau\). Implementations treat \(\tau = 0\) as an explicit greedy branch because the formula divides by zero.

Warm-up What exactly is stored in the KV cache, and how big is it for Llama-3-8B at 32K tokens?

For every layer, every KV head and every past token: the key (after projection and after RoPE) and the value. Queries, scores, FFN activations and hidden states are not stored. It is exact because causal masking makes earlier keys and values independent of later tokens.

Size per token \(= 2 L\, n_{kv}\, d_h\, b = 2 \cdot 32 \cdot 8 \cdot 128 \cdot 2 = 131{,}072\) B = 128 KiB. At 32,768 tokens: \(128 \text{ KiB} \times 32{,}768 = 4\) GiB per sequence. (With 32 MHA-style KV heads it would be 16 GiB.) Note the base Llama-3-8B has an 8K window; 32K needs Llama 3.1.

Warm-up Why does greedy decoding repeat itself?

Two effects. (1) Repetition is self-reinforcing: the more often a phrase appears in the context, the higher the probability the model assigns to continuing it (Holtzman et al., Fig. 4), and greedy always follows the highest probability, so once it enters a loop it cannot leave. (2) Likelihood-trained models put their highest probability on generic, predictable continuations, but human text is not the most probable text (per-token probability of human text is far lower; perplexity 12.4 versus 1.5 for greedy output in Holtzman's Table 1). In their GPT-2 Large experiment, 73.66% of greedy generations ended in a loop. Sampling with truncation (top-p, min-p) injects controlled randomness to escape it.

Core Explain temperature, top-k, top-p and min-p. When would you use each?

Temperature raises probabilities to the power \(1/\tau\) and renormalizes: a global knob for randomness. Top-k keeps the \(k\) most likely tokens: simple, but a fixed \(k\) is too large when the model is confident and too small when many continuations are valid. Top-p keeps the smallest set with cumulative mass \(\ge p\): the set size adapts to confidence. Min-p keeps tokens with \(p_i \ge p_{\text{base}} p_{\max}\): the threshold scales with the top token's probability, needs no sort, and is meant to be robust at high temperature.

Usage: greedy or \(\tau \le 0.3\) for tasks with a checkable answer; \(\tau \approx 0.6\) to 1 with top-p 0.9 to 0.95, or min-p 0.05 to 0.1, for chat and creative writing; \(\tau = 1\) untruncated when you need samples from the model's own distribution (RL rollouts). Use one truncation method, not all. Be honest about evidence: nucleus sampling is well supported (Holtzman), while min-p's advantage is disputed by an independent re-analysis.

Core Why is beam search rare for chatbots even though it finds higher-probability sequences?

Because probability is not quality for open-ended text. Mode-seeking output is generic and repetitive: with \(b = 16\), GPT-2 Large has perplexity 1.48 against 12.38 for human text and 28.94% looped outputs. Larger beams make it worse (the "beam search curse"): Koehn and Knowles saw BLEU fall beyond beams of 4 to 50 because outputs get shorter, and Stahlberg and Byrne showed that exact search picks the empty output for 51.8% of sentences, so beam search only works thanks to its search errors. Length normalization (GNMT's \(lp = (5+|Y|)^\alpha/6^\alpha\)) helps but does not fix the model bias.

Beam search is still right when the output is nearly determined by the input (translation, summarization, ASR) and you want the mode. For chat it also costs \(b\) times the compute and KV cache, and it complicates batching. Sampling plus selection is used instead.

Core Does it matter whether temperature is applied before or after top-p (or min-p)?

Yes for top-p and min-p, no for top-k. Top-k depends only on rank order, which \(\tau \gt 0\) preserves. Top-p's cumulative mass and min-p's ratio \(p_i/p_{\max}\) are computed from the probabilities, which temperature changes. With temperature first (Hugging Face, vLLM), higher \(\tau\) flattens the distribution and enlarges the nucleus, so \(\tau\) and \(p\) interact. With temperature last (llama.cpp default), the candidate set is independent of \(\tau\). On the toy logits of Figure 2 with top-k 5, top-p 0.9, min-p 0.2, Hugging Face's order keeps 2 tokens at \(\tau = 0.5\) and 5 at \(\tau = 2\); llama.cpp's keeps 4 in both cases.

Also mention renormalization: each Hugging Face filter takes a softmax over survivors, so top-p after top-k sees renormalized mass (top-p 0.5 on \([0.4,0.3,0.2,0.1]\) keeps two tokens, but after top-k 2 it keeps one). Min-p is a ratio test and is unaffected. Always check the order and defaults (Hugging Face silently applies top-k 50 when unset).

Core Why is decoding memory-bandwidth-bound while prefill is compute-bound?

For a weight matmul, FLOPs per byte of weights read \(\approx m\), the number of tokens sharing that read (bf16: \(2md_{\text{in}}d_{\text{out}}\) FLOPs over \(2d_{\text{in}}d_{\text{out}}\) bytes). Prefill has \(m\) equal to the prompt length, in the thousands, far above the H100's ridge of about 295 FLOPs/byte (989.5 TFLOP/s over 3.35 TB/s): compute-bound. Decode has \(m = B\), and at batch 1 that is about 1 FLOP/byte: the tensor cores wait while HBM streams 16 GB of weights.

Attention makes it worse. Each sequence's KV cache is read once per step and used for only \(n_h/n_{kv}\) FLOPs per byte (4 for Llama-3-8B), whatever the batch size. So step time is about (weight bytes + KV bytes) over bandwidth.

Core Estimate tokens per second for an 8B model at batch 1 on an H100.

Decode is bandwidth-bound, so tokens/s \(\approx\) bandwidth / bytes read per token. Weights: 8.03B parameters in bf16 is 16.06 GB. H100 SXM bandwidth is 3.35 TB/s. Time per token \(\ge 16.06 / 3350 = 4.79\) ms, so at most about 208 tokens/s. Add the KV cache (0.54 GB at 4K context) and it is 4.95 ms, about 202 tokens/s.

Reality is 70 to 85% of that, so quote 150 to 180 tokens/s. One profile of Llama-3-8B on an H100 NVL measured 5.27 ms per token against a 4.19 ms bound. Sanity check: FP8 weights halve the bytes and so roughly double the bound. State the assumptions: bf16, batch 1, weights dominate, no speculation.

Core How does increasing the batch size affect latency and throughput during decode?

One weight read now serves \(B\) tokens, so throughput rises almost linearly while the weight term dominates. Latency per token rises slowly, because each sequence adds its own KV bytes. For Llama-3-8B at 4K context on an H100: \(B = 1\) gives 4.95 ms per step (202 tokens/s); \(B = 32\) gives 9.92 ms per step, 3,225 tokens/s total (16 times) but 101 tokens/s per user (half); \(B = 104\) fills the GPU at 21.5 ms and 4,846 tokens/s.

Throughput saturates at \(\text{BW}/(\bar S\kappa) \approx 6{,}240\) tokens/s because the KV bytes scale with \(B\) too. Attention's intensity is only \(n_h/n_{kv}\) regardless of batch, and for contexts above about 390 tokens the whole step stays memory-bound. Batch size is limited by KV capacity (104 here), and by any TPOT target.

Core Why can two runs with the same seed and temperature 0 give different outputs on GPUs?

Temperature 0 removes sampling randomness, but the logits themselves are not bit-identical. Floating-point addition is not associative, and GPU kernels pick reduction orders (tiling, split-K, split-KV) from the input shape. In a server the same request is batched with different neighbors each time, so its shapes and therefore its rounding change. When the top two logits are within that noise, argmax flips, and autoregression amplifies a single different token into a different text.

The Thinking Machines analysis argues the culprit is missing batch invariance in kernels, not atomic adds: their test gave 80 distinct completions out of 1,000 identical requests on Qwen3-235B, and 1 with batch-invariant kernels, at a speed cost. PyTorch also documents no bitwise guarantee across releases, platforms or CPU versus GPU. Consequences: flaky evals and a trainer-versus-rollout log-probability mismatch in RL.

Core Compare the per-step cost of decoding with and without a KV cache.

Without a cache, each new token re-runs the network over the whole prefix of length \(t\): \(\approx 2N_{\text{mm}}\, t\) FLOPs, so a whole generation costs \(O(n^2)\) in weight-matmul FLOPs. With a cache, a step processes one token: \(2N_{\text{mm}}\) FLOPs plus \(4Ln_hd_h\,t\) for attention over the cache, so the weight work is \(O(n)\) overall. Example: prompt 2,048 plus 256 new tokens. Token-positions processed: 556,928 without the cache against 2,303 with it, a factor of 242.

The cost moves to memory: \(2Ln_{kv}d_hb\) bytes per token (128 KiB for Llama-3-8B), all of it read every step. At \(t = 2048\) attention is only 1.07 GFLOP against 15 GFLOP for the weights, but at large batch and long context the bytes dominate.

Deep-dive How does speculative decoding speed up generation without changing the output distribution?

Decode is memory-bound, so scoring \(\gamma + 1\) tokens in one pass costs about the same as scoring one: the weights and cache are read once, and intensity only rises to \(\gamma + 1\) FLOPs/byte. A cheap draft \(q\) proposes \(\gamma\) tokens; the target computes \(p\) at all \(\gamma+1\) positions in one pass. Accept draft token \(x\) with probability \(\min(1, p(x)/q(x))\); at the first rejection resample from \(\text{norm}(\max(0, p-q))\) and stop; if all are accepted, take a free bonus token from the target.

Exactness: the chance of emitting \(x\) is \(q(x)\min(1, p/q) + (1-\alpha)\,\text{norm}(\max(0,p-q))(x) = \min(p,q) + (p - \min(p,q)) = p(x)\), with \(\alpha = \sum_x \min(p,q)\). Toy check: \(p = (0.6, 0.3, 0.1)\), \(q = (0.4, 0.4, 0.2)\) gives \(\alpha = 0.8\), residual \((1, 0, 0)\), and token 0 is emitted with probability \(0.4 + 0.2 = 0.6\). Expected tokens per pass \(= (1-\alpha^{\gamma+1})/(1-\alpha)\); speedup divides that by \(1+\gamma c\). Top-k, top-p and temperature are folded into \(p\) and \(q\) before the test. Caveats: wasted FLOPs on rejections, gains shrink as batch grows, and the guarantee is distributional, not bitwise.

Deep-dive Design question: serve Llama-3-8B chat on one H100 with 4K contexts and a 20 ms TPOT target. What batch size, and what limits you?

Step time must be at most 20 ms. With \(t_{\text{step}} = (16.06 + 0.537 B)\text{ GB} / 3.35\text{ TB/s}\), we need \(B \le (67.0 - 16.06)/0.537 \approx 94\). That gives about \(94/0.020 = 4{,}700\) tokens/s. Capacity allows 104 sequences at 90% memory use, so here the TPOT target binds first. With a 30 ms target, \(B\) would be 157 and capacity (104) would bind instead.

Levers, in order of cost: (1) shrink the KV term: FP8 KV halves the KV slice, shorter or sliding-window contexts, prefix caching so shared prompts are stored once; (2) continuous batching plus PagedAttention to avoid fragmentation and keep the batch full; (3) speculative decoding to gain tokens per step at low batch; (4) chunked prefill so long prompts do not spike TPOT; (5) a second GPU with tensor parallelism if the target is still missed, at the price of communication. Say what you would measure: TTFT and TPOT percentiles at your real length distribution, since the mean context, not the maximum, sets the KV traffic.

Deep-dive How would you implement a KV cache, and what are the failure modes of concatenation, preallocation and paging?

Concatenation (torch.cat per step, as in Hugging Face's dynamic cache): trivial, but each step allocates a new tensor and copies all \(t\) entries, adding roughly two extra passes over the cache to the attention read, and it fragments memory as shapes change every step. Preallocation \((B, n_{kv}, S_{\max}, d_h)\) per layer with in-place writes: \(O(1)\) bytes per step, static shapes for CUDA graphs and torch.compile, and the attention kernel gets a view of the filled prefix. Its failure mode is internal waste: you reserve \(S_{\max}\) per sequence, and vLLM measured only 20.4% to 38.2% of reserved cache holding real tokens in earlier systems.

Paging (PagedAttention): fixed-size blocks (16 tokens by default) plus a block table per sequence. Waste is confined to the last block, blocks are shareable with copy-on-write (parallel sampling, beam search, common prefixes), at the price of an indirection in the attention kernel (20% to 26% slower kernel in vLLM's measurement) and more complex scheduling and eviction. Details to state: store keys after RoPE, keep per-layer lengths (or one length updated after the last layer), and check capacity before writing so an overflow cannot leave a half-written cache.

Deep-dive What do repetition, frequency and presence penalties do to the logits, and when do they backfire?

With \(c_j\) the number of times token \(j\) has occurred: frequency subtracts \(\alpha_f c_j\), so probability is multiplied by \(e^{-\alpha_f c_j}\) and each repeat costs more; presence subtracts \(\alpha_p\) once if \(c_j \gt 0\), discouraging any reuse; both are additive in logit space and scale-free. The repetition penalty of CTRL is multiplicative: logits of tokens already seen are divided by \(\theta\) (around 1.2). Because dividing a negative logit by \(\theta \gt 1\) would increase it, implementations such as Hugging Face's multiply negative logits and divide positive ones, apply it once per distinct token, and include the prompt by default. vLLM counts only generated tokens for frequency and presence.

They backfire because they cannot separate harmful repetition from required repetition: identifiers, brackets, digits, quoted text, names, and repeated tags in JSON or code. Heavy penalties therefore corrupt structured output and can push the model toward rare, wrong tokens. Repetition is better treated at its source (better data and post-training, sampling with truncation), and shipped defaults are mild, for example 1.05 for Qwen2.5-7B-Instruct.

Cheat sheet

  • Loop: prefill (\(P\) tokens, parallel, fills the cache) then decode (1 token per step). \(n\) new tokens need \(n\) forward passes.
  • Temperature: \(p_i \propto \exp(z_i/\tau) \propto p_i^{1/\tau}\). \(\tau \to 0\): greedy. \(\tau \to \infty\): uniform. \(\tau = 0\) means greedy in APIs.
  • Top-k: keep \(k\) largest. Top-p: smallest set with mass \(\ge p\) (0.9 to 0.95). Min-p: keep \(p_i \ge p_{\text{base}}\,p_{\max}\) (0.05 to 0.1). All renormalize. Order matters: Hugging Face is temperature, top-k, top-p, min-p; llama.cpp puts temperature last; unset Hugging Face top-k defaults to 50.
  • Greedy on GPT-2 Large: 73.66% looped, perplexity 1.50 (human 12.38). Nucleus 0.95: 0.36% looped, perplexity 13.13.
  • Penalties: repetition (divide positive, multiply negative logits, \(\theta \approx 1.2\)); frequency \(-\alpha_f c_j\); presence \(-\alpha_p \mathbf{1}[c_j>0]\). They hurt code and structured output.
  • Beam search: keep \(b\) best cumulative log-probs; normalize by \(lp = (5+|Y|)^\alpha/6^\alpha\). Good for translation. Bland, looping and cursed at large \(b\) for open-ended text.
  • Temperature 0 is not deterministic on GPUs: non-associative floats, shape-dependent reductions, batch variance, argmax flips, divergence.
  • KV cache is exact (causal). Bytes per token \(= 2 L n_{kv} d_h b\): Llama-3-8B 128 KiB, so 4 GiB at 32K, 16 GiB at 128K. Store K after RoPE. Preallocate, do not concatenate.
  • Weight matmul intensity \(\approx m\) tokens per read. H100 ridge \(= 989.5/3.35 \approx 295\) FLOPs/byte. Decode at \(B=1\): about 1.
  • Llama-3-8B on H100: weights 16.06 GB, so 4.79 ms and about 208 tokens/s at \(B=1\) (about 202 with a 4K cache). Prefill 2,048 tokens: \(2NT = 3.29\times10^{13}\) FLOPs, 33 ms at peak, 66 ms at 50% MFU.
  • Batching: \(t_{\text{step}} \approx (W + B\bar S\kappa)/\text{BW}\). At 4K: \(B = 32\) gives 3,225 tokens/s at 101 per user. Ceiling \(\text{BW}/(\bar S\kappa) = 6{,}240\) tokens/s. Large-batch intensity \(= 4 + 2N_{\text{mm}}/(\kappa\bar S)\), memory-bound above about 390 tokens.
  • TTFT (queue + prefill), TPOT \(= (\text{e2e} - \text{TTFT})/(n-1)\). Serving: continuous batching (per-iteration scheduling), PagedAttention (16-token blocks), prefix caching (radix tree), speculative decoding (accept \(\min(1,p/q)\), resample \(\text{norm}(\max(0,p-q))\)).
