KV-efficient attention: MQA, GQA, MLA

P0 ~70 min Prereqs: 03 Attention, 05 RoPE, 06 KV cache

During generation, a transformer's speed and batch size are limited mostly by how many bytes of keys and values it must keep and re-read for every new token. This page covers the three main architectural answers: share keys and values across heads (MQA), share them within groups (GQA), or cache one small latent vector per token and rebuild every head's keys and values from it (DeepSeek's MLA).

What interviewers probe
  • Back-of-envelope: "How big is the KV cache for model X at 128K context?" Expect to produce bytes per token from a config in under a minute.
  • Why decoding is bandwidth-bound, and why a bigger batch does not fix the attention part of it.
  • GQA details: what is shared, how to convert an MHA checkpoint, and why 8 KV heads is so common.
  • MLA end to end: the equations, what is cached (576 numbers per layer for DeepSeek-V3), weight absorption, and why RoPE forces the decoupled design.
  • Trade-off reasoning: quality vs. cache size vs. FLOPs, prefill vs. decode, and how parallelism interacts with each design.

Why the KV cache is the bottleneck

Recall from page 06 that autoregressive generation produces one token per forward pass. Each layer's attention needs the keys and values of every earlier token. Recomputing them at every step would cost \(O(T)\) extra matmuls per token, so we store them in the KV cache 键值缓存. Standard multi-head attention (MHA) caches one key and one value of size \(d_h\) per head, per layer, per token:

\[ \text{KV bytes per token} = L \cdot \underbrace{2 \, n_{kv} \, d_h}_{\text{elements per layer}} \cdot b \]
b = bytes per element (2 for bf16); nkv = nh for MHA

Plug in our reference model Llama-3-8B (\(L=32\), \(n_{kv}=8\), \(d_h=128\), bf16): \(32 \cdot 2 \cdot 8 \cdot 128 \cdot 2 = 131{,}072\) bytes, exactly 128 KiB per token. At a 128K-token context (131,072 tokens), one sequence needs \(128\text{ KiB} \times 131{,}072 = 16\) GiB of cache, which is more than the model's own weights (8.03B params × 2 bytes ≈ 15 GiB). With plain MHA (32 KV heads) it would be 64 GiB for a single sequence.

def kv_bytes_per_token(n_layers, cached_elems_per_layer, bytes_per_el=2):
    return n_layers * cached_elems_per_layer * bytes_per_el

llama3_8b = kv_bytes_per_token(32, 2 * 8 * 128)   # GQA, 8 KV heads: 131,072 B = 128 KiB
dsv3_mla  = kv_bytes_per_token(61, 512 + 64)      # MLA latent + RoPE key: 70,272 B ≈ 68.6 KiB
print(llama3_8b * 131_072 / 2**30)                # 16.0 GiB for one 128K-token sequence

Capacity is only half the problem: bandwidth

Memory capacity limits how many sequences fit. Memory bandwidth 内存带宽 limits how fast each one runs. At every decode step, attention must stream the entire cache of that sequence from HBM to the compute units, do a little math with it, and throw it away. The useful measure is arithmetic intensity 算术强度: FLOPs performed per byte read.

For one new query token and one cached token, one layer of GQA attention does \(2 n_h d_h\) FLOPs for the scores (\(q \cdot k\) for every query head) and \(2 n_h d_h\) for the weighted sum of values, so \(4 n_h d_h\) FLOPs in total. It reads \(2 n_{kv} d_h\) elements, which is \(4 n_{kv} d_h\) bytes in bf16. So:

\[ \text{intensity}_{\text{decode attn}} \approx \frac{4 n_h d_h}{4 n_{kv} d_h} = \frac{n_h}{n_{kv}} \ \text{FLOPs/byte (bf16)} \]

That is 1 for MHA and 4 for Llama-3-8B's GQA (\(32/8\)). An H100/H800 SXM does roughly 989 dense bf16 TFLOP/s against about 3.35 TB/s of HBM bandwidth, so it needs about 295 FLOPs per byte to be compute-bound. Decode attention with MHA or typical GQA runs about two orders of magnitude below that: the tensor cores sit idle while HBM streams the cache.

Key idea: batching does not help here

For the weight matmuls, batching B sequences reuses each loaded weight B times, so intensity grows with B. For attention, every sequence has its own cache, so nothing is shared across the batch and intensity stays at \(n_h/n_{kv}\). Shazeer made exactly this point in 2019: for incremental MHA decoding, the ratio of memory access to arithmetic is \(\Theta(n/d + 1/b)\), and the \(n/d\) term (sequence length over width, from re-reading K and V) cannot be batched away [Shazeer 2019, §2.4.1].

There are two levers, and every design on this page pulls one or both:

  1. Fewer bytes per token: this raises capacity (longer contexts, bigger batches) and cuts the time to stream the cache.
  2. More FLOPs per byte: let many query heads reuse each loaded key and value.

Multi-query attention (MQA)

Multi-query attention 多查询注意力 [Shazeer 2019] keeps \(n_h\) query heads but uses a single key head and a single value head shared by all of them. In code it is the MHA einsum with the head index removed from \(K\), \(V\), \(W^K\), \(W^V\):

\[ o_{t,i} = \sum_{j \le t} \softmax_j\!\left(\frac{q_{t,i} \cdot k_j}{\sqrt{d_h}}\right) v_j, \qquad k_j = x_j W^K,\ v_j = x_j W^V \in \R^{d_h} \]

The cache shrinks by \(n_h\times\) and the decode intensity rises to \(n_h\) FLOPs/byte. Shazeer's WMT14 En-De experiments show both sides of the bargain: amortized decoder cost fell from 46 µs to 3.8 µs per token (and from 203 to 32 µs with beam 4), while dev log-perplexity went from 1.424 to 1.439 and dev BLEU from 26.7 to 26.5. To keep parameter counts equal, the FFN was widened from 4096 to 5440 [Shazeer 2019, Tables 1-2].

Multi-query attention
Problem
Incremental decoding re-reads \(2 n_h d_h\) cached elements per token per layer. That is memory-bound, and batching cannot amortize it.
Idea
Share one key head and one value head across all query heads.
Why it works
Query heads still differ, so heads can still attend to different positions. They only lose separate "views" of the keys and values. Much of what makes heads useful survives, because the query projections carry most of the head diversity.
Evidence
12× cheaper decoder steps with a small quality drop on translation [Shazeer 2019]. Later work found more significant degradation, plus loss spikes when training MQA models from scratch and divergence when fine-tuning them on long-input tasks [Ainslie et al. 2023, App. A].
Cost
Capacity loss that grows with model size, since big models have many heads and MQA cuts them all to one. It also shards badly under tensor parallelism: with 8 GPUs splitting heads, the single KV head must be replicated on every GPU (see Systems consequences).
Used by
PaLM; Gemma 1 2B ("num_kv_heads = 1") [Gemma 2024, Table 1].

Grouped-query attention (GQA)

Grouped-query attention 分组查询注意力 [Ainslie et al. 2023] interpolates between the two. Split the \(n_h\) query heads into \(n_{kv}\) groups of size \(g = n_h / n_{kv}\). Each group shares one key head and one value head. GQA-\(n_h\) is MHA and GQA-1 is MQA. Query head \(i\) reads KV head \(\lfloor i/g \rfloor\):

\[ o_{t,i} = \sum_{j \le t} \softmax_j\!\left(\frac{q_{t,i} \cdot k_{j,\lfloor i/g\rfloor}}{\sqrt{d_h}}\right) v_{j,\lfloor i/g \rfloor} \]

The cache is \(2 n_{kv} d_h\) elements per layer and the decode intensity is \(g\). GQA changes neither the number of attention score computations (every query head still scores every position) nor the FLOPs of \(QK^\top\). It only removes redundant K/V projections and cache entries. The implementation is a few lines. The subtle part is the end-aligned causal mask: during decoding or chunked prefill, the \(T\) new queries are the last \(T\) of \(S\) positions.

import torch

def gqa_attention(q, k, v):
    # q: (B, n_h, T, d_h)   k, v: (B, n_kv, S, d_h), S >= T (cached + new tokens)
    B, n_h, T, d_h = q.shape
    n_kv, S = k.shape[1], k.shape[2]
    g = n_h // n_kv                                    # query heads per KV head
    k = k.repeat_interleave(g, dim=1)                  # (B, n_h, S, d_h); real kernels index head i // g instead of copying
    v = v.repeat_interleave(g, dim=1)
    scores = q @ k.transpose(-1, -2) / d_h**0.5        # (B, n_h, T, S)
    qpos = torch.arange(T)[:, None] + (S - T)          # absolute position of each new query
    kpos = torch.arange(S)[None, :]
    scores = scores.masked_fill(kpos > qpos, float("-inf"))
    return scores.softmax(-1) @ v                      # (B, n_h, T, d_h)

Recent PyTorch versions expose the same thing as F.scaled_dot_product_attention(q, k, v, enable_gqa=True), which avoids the copy.

Converting an MHA checkpoint: mean-pool, then uptrain

The GQA paper's second contribution is cheap conversion. Take a trained MHA model and build each group's K (and V) projection as the mean of the original heads' projections in that group. Then continue pretraining for a fraction \(\alpha\) of the original steps. Mean-pooling beat both "keep the first head" and random initialization. With \(\alpha = 0.05\) (about 600 TPUv3 chip-days for T5-XXL), GQA-8 recovered almost all of MHA's quality [Ainslie et al. 2023, §2.1, Fig. 4-5]:

Why so many models use exactly 8 KV heads

Llama 2 used GQA only for its 34B and 70B models. The paper gives two reasons [Llama 2, App. A.2.1]. First, in a 30B ablation trained on 150B tokens, GQA matched MHA on most tasks and beat MQA on average (Table 18). Second, and decisive in practice, they serve the largest models with 8-way tensor parallelism 张量并行 across the 8 GPUs of a node, splitting heads across GPUs. MQA's single KV head cannot be split, so it must be duplicated on all 8 GPUs, which makes the actual cache the same size as GQA-8's. Eight KV heads gives one per GPU. The GQA paper adds a scaling argument: because \(n_h\) grows with model size, MQA is an ever more aggressive cut, while a fixed group size keeps the proportional reduction constant [Ainslie et al. 2023, §2.2].

MQA saves the most memory but loses quality and destabilizes training. MHA is the reverse.

Keys and values across heads are partly redundant, so a few KV heads retain most of the diversity. Choosing \(n_{kv}\) equal to the TP degree makes the cache shard perfectly.

T5-XXL: 47.1 vs 47.2 (MHA) at close to MQA speed [Ainslie et al., Tab. 1]. Llama 2 30B ablation: GQA ≈ MHA, better than MQA on average [Llama 2, Tab. 18].

Multi-head latent attention (MLA)

DeepSeek-V2 introduced multi-head latent attention 多头潜在注意力 with a stronger claim: a KV cache smaller than GQA's and quality better than MHA's [DeepSeek-V2, §2.1]. DeepSeek-V3, R1 and V3.2 keep it unchanged, and Kimi K2 adopts it. MLA is the single most "DeepSeek" idea in modern architecture, and it rewards understanding line by line.

All equations below use row vectors (\(x W\)) and DeepSeek-V3's dimensions: \(d = 7168\), \(n_h = 128\), per-head content dimension \(d_h = 128\), KV latent \(d_c = 512\), query latent \(d_c' = 1536\), decoupled RoPE dimension \(d_h^R = 64\).

Step 1: low-rank joint compression of K and V

Instead of projecting \(h_t\) directly to \(n_h\) keys and values, first project it down to one small latent vector, then up to per-head keys and values:

\[ c^{KV}_t = h_t W^{DKV} \in \R^{d_c}, \qquad k^C_{t,i} = c^{KV}_t W^{UK}_i \in \R^{d_h}, \qquad v^C_{t,i} = c^{KV}_t W^{UV}_i \in \R^{d_h} \]

with \(W^{DKV} \in \R^{d \times d_c}\) and \(W^{UK}_i, W^{UV}_i \in \R^{d_c \times d_h}\). This is low-rank compression 低秩压缩. The stacked key and value projection of MHA, a \(7168 \times 32{,}768\) matrix, is factored as \(W^{DKV} [W^{UK}\ W^{UV}]\) with rank at most 512. The bet is that the joint K/V information a token contributes, across all 128 heads, fits in 512 dimensions. If you cache \(c^{KV}_t\) instead of the keys and values, the cache is \(d_c = 512\) numbers per layer instead of \(2 \cdot 128 \cdot 128 = 32{,}768\).

Queries get the same treatment, \(c^Q_t = h_t W^{DQ} \in \R^{1536}\), \(q^C_{t,i} = c^Q_t W^{UQ}_i\). This does not shrink the cache (queries are never cached). DeepSeek does it to cut activation memory during training [DeepSeek-V2, §2.1.2]. In the real models, an RMSNorm is applied to both latents and extra scaling factors sit at the bottlenecks for training stability [DeepSeek-V2, §3.1.2]. The cache stores the normalized latent. None of this changes the algebra below.

Step 2: weight absorption, or why you never decompress

Caching \(c^{KV}\) would be pointless if every decode step had to rebuild all past keys and values from it: that is \(2 \cdot 512 \cdot 32{,}768 \approx 33.5\)M FLOPs per cached token per layer. The trick is associativity. For one head, ignoring position for a moment:

\[ q^C_{t,i} \cdot k^C_{j,i} = q^C_{t,i} \big(c^{KV}_j W^{UK}_i\big)^{\!\top} = \underbrace{\big(q^C_{t,i}\, W^{UK\top}_i\big)}_{\tilde q_{t,i} \,\in\, \R^{d_c}} \cdot\, c^{KV}_j \]

Map the query into latent space once per step (a \(128 \to 512\) product per head), then dot it directly with the cached latents. The same trick works on the value side, because the attention-weighted sum is linear:

\[ o_{t,i} = \sum_j a_{t,j,i}\, c^{KV}_j W^{UV}_i = \Big(\underbrace{\textstyle\sum_j a_{t,j,i}\, c^{KV}_j}_{\tilde o_{t,i} \,\in\, \R^{d_c}}\Big) W^{UV}_i \]

This is weight absorption 权重吸收: \(W^{UK}\) is "absorbed" into the query side and \(W^{UV}\) into the output side [DeepSeek-V2, App. C]. Look at what remains. Every head computes scores against the same vectors \(c^{KV}_j\), and takes a weighted sum of the same vectors \(c^{KV}_j\). That is multi-query attention with head dimension 512.

Key idea

At decode time, MLA is MQA in a learned latent space. One shared "key" (the latent, plus the RoPE key below) serves all 128 query heads. So MLA gets MQA's bandwidth profile, a tiny cache read once per step and reused by every head, while keeping 128 genuinely different per-head keys and values in the math. DeepSeek itself describes the two execution paths as the "MHA mode" and "MQA mode" of MLA [DeepSeek-V3.2, App. A].

Absorption is reordering, not merging

You could precompute \(W^{UQ}_i W^{UK\top}_i \in \R^{1536 \times 512}\) per head, but that is about 100M parameters per layer, larger than the two factors it replaces (25.2M + 8.4M). Real implementations keep the factors and only change the order of multiplication. For example, DeepSeek-V3's reference inference code caches the normalized latent and the RoPE key, and multiplies \(q^C\) by \(W^{UK}\) with an einsum at runtime.

Step 3: why RoPE breaks absorption, and the decoupled fix

DeepSeek wanted RoPE 旋转位置编码 (page 05). RoPE multiplies a query or key at position \(t\) by a block-diagonal rotation \(R_t\), with the property \(R_t R_j^\top = R_{t-j}\). Suppose we rotate the content keys as usual, \(k_{j,i} = c^{KV}_j W^{UK}_i R_j\). Then:

\[ (q_{t,i} R_t) \cdot (c^{KV}_j W^{UK}_i R_j) = q_{t,i}\, R_{t-j}\, W^{UK\top}_i\, c^{KV\top}_j \]

The position-dependent rotation \(R_{t-j}\) now sits between the query and \(W^{UK}_i\), and it changes with every cached position \(j\). You can no longer form one \(\tilde q_{t,i}\) and reuse it across the cache. You would need a different absorbed query for each \(j\), which costs as much as decompressing every key [DeepSeek-V2, §2.1.3].

The fix is to decouple position from content. Keep the compressed path completely position-free, and add a small separate path that carries RoPE:

\[ \begin{aligned} q^R_{t,i} &= \RoPE_t\!\big(c^Q_t W^{QR}_i\big) \in \R^{d_h^R} &&\text{(one per head)}\\ k^R_t &= \RoPE_t\!\big(h_t W^{KR}\big) \in \R^{d_h^R} &&\text{(one per token, shared by all heads)}\\ \text{score}_{t,j,i} &= \frac{q^C_{t,i}\cdot k^C_{j,i} \;+\; q^R_{t,i}\cdot k^R_j}{\sqrt{d_h + d_h^R}} \end{aligned} \]
Decoupled RoPE: absorbable content term + small MQA-style positional term

The content term absorbs as before. The positional term is itself MQA-shaped: 128 per-head RoPE queries against one shared 64-dim RoPE key. So the per-token cache is \(c^{KV}_t\) plus \(k^R_t\): \(512 + 64 = \mathbf{576}\) numbers per layer, and the score scale is \(1/\sqrt{128+64} = 1/\sqrt{192}\). Because position lives only in those 64 dimensions, DeepSeek-V3's YaRN context extension is applied only to the decoupled key \(k^R\) [DeepSeek-V3, §4.3].

Step 4: two execution modes for the same weights

Absorption trades bytes for FLOPs. In absorbed form, each head's score is a 576-dim dot product (instead of 192) and its weighted sum is over 512-dim latents (instead of 128-dim values). Per cached token per layer, the attention FLOPs are \(2 \cdot 128 \cdot (576 + 512) = 278{,}528\) versus \(2 \cdot 128 \cdot (192 + 128) = 81{,}920\) in decompressed form: 3.4× more compute, in exchange for reading 576 instead of 40,960 elements, 71× fewer bytes. Which side of that trade you want depends on whether you are bandwidth-bound or compute-bound:

  • Decode is bandwidth-bound (one query token per sequence), so use the absorbed MQA mode.
  • Training and prefill process many query tokens at once and are compute-bound, so the extra FLOPs would hurt. Use MHA mode: decompress \(k^C, v^C\) once for the whole chunk and run ordinary multi-head attention with 192-dim query/key heads and 128-dim value heads. DeepSeek states that V3.1-Terminus trains and prefills in MHA mode and decodes in MQA mode [DeepSeek-V3.2, App. A, Fig. 7].

The absorbed decode step fits in about 25 lines. This is the core of the drill in exercises/solutions/mla.py, tested against the decompressed form:

def mla_decode_step(h_t, w, cache_c, cache_kr, pos):
    """h_t: (B, 1, d); cache_c: (B, S, d_c); cache_kr: (B, S, d_r). Absorbed ("MQA mode")."""
    B = h_t.shape[0]
    n_h, d_nope, d_r, d_v = w.n_h, w.d_nope, w.d_r, w.d_v
    d_c = w.W_dkv.shape[1]
    p = torch.tensor([pos])
    # 1) append this token's cache entries: the ONLY per-token state MLA keeps
    cache_c  = torch.cat([cache_c,  h_t @ w.W_dkv], dim=1)                # (B, S+1, d_c)
    cache_kr = torch.cat([cache_kr, rope(h_t @ w.W_kr, p)], dim=1)        # (B, S+1, d_r)
    # 2) queries
    c_q = h_t @ w.W_dq                                                    # (B, 1, d_cq)
    q_c = (c_q @ w.W_uq).view(B, n_h, d_nope)
    q_r = rope((c_q @ w.W_qr).view(B, 1, n_h, d_r), p).view(B, n_h, d_r)
    # 3) absorb W_uk into the query: q_lat[h] = q_c[h] @ W_uk[h]^T  (latent space)
    q_lat = torch.einsum("bhn,chn->bhc", q_c, w.W_uk.view(d_c, n_h, d_nope))
    # 4) MQA over the latent cache: shared key [c; k_r], shared value c
    scores = (torch.einsum("bhc,bsc->bhs", q_lat, cache_c)
              + torch.einsum("bhr,bsr->bhs", q_r, cache_kr)) / (d_nope + d_r) ** 0.5
    o_lat = torch.einsum("bhs,bsc->bhc", scores.softmax(-1), cache_c)     # (B, n_h, d_c)
    # 5) absorb W_uv on the way out, then the output projection
    o = torch.einsum("bhc,chv->bhv", o_lat, w.W_uv.view(d_c, n_h, d_v))   # (B, n_h, d_v)
    return o.reshape(B, 1, n_h * d_v) @ w.W_o, cache_c, cache_kr

Read this critically, as an interviewer will expect:

  • MLA beats MHA on 7 of 8 comparisons, with 14% (small) and 4% (large) of MHA's cache. That is the headline claim, and it is consistent with DeepSeek's later results, but it comes from one lab's ablations. C-Eval on the small MoE favors MHA.

There is also a theoretical argument. At an equal cache budget, any GQA layer can be rewritten exactly as an MLA layer: let the latent be the concatenated GQA keys and values, and let the up-projections be 0/1 selector matrices. The converse does not hold, so MLA's function class strictly contains GQA's [TransMLA, App. A]. The same paper converts pretrained GQA models (Llama, Qwen and others) into MLA form, compressing Llama-2-7B's cache by 93% and recovering performance with about 6B tokens of training. Expressiveness is not the same as trained quality, but it explains why MLA is not merely a lossy approximation of MHA.

Multi-head latent attention
Problem
GQA/MQA shrink the cache by removing per-head keys and values, which loses capacity. DeepSeek wanted a cache smaller than GQA-8's with MHA-level (or better) quality.
Idea
Cache one low-rank latent per token (plus a small shared RoPE key). Reconstruct 128 distinct per-head keys and values from it by linear maps, and absorb those maps so decoding never actually reconstructs them.
Why it works
K/V information per token is highly compressible. Heads stay distinct because each has its own up-projection. Absorption turns decode into MQA over the latent, so each cached byte is reused by all heads. Decoupled RoPE keeps position out of the absorbable path.
Evidence
Beats MHA at 16B and 250B MoE scale with 4 to 14% of the cache [V2, Tab. 9]. Kept through V3, R1, V3.2, and adopted by Kimi K2.
Cost
More complex kernels and two execution modes. 3.4× more attention FLOPs per cached token when absorbed, which matters at long context. The latent is shared by all heads, so head-sharded tensor parallelism cannot split the cache. RoPE covers only 64 of each head's 192 query-key dimensions.
Used by
DeepSeek-V2, V2.5, V3, R1, V3.1, V3.2 (with DSA sparse attention on top, page 09); Kimi K2 (64 heads instead of 128) [Kimi K2, §2.3]. DeepSeek-V4 (2026) moved on to compressed shared-KV attention, described next.

What came next: DeepSeek-V3.2 and V4

MLA shrank the cache along the feature axis: 576 numbers per token per layer instead of 40,960. DeepSeek's next two steps attack the sequence axis.

  • DeepSeek-V3.2 (December 2025) keeps MLA unchanged and adds DeepSeek Sparse Attention on top of its MQA mode. A small "lightning indexer" scores every previous token, and each query attends to only the top 2,048 cached latents [DeepSeek-V3.2, §2.1]. The cache itself is the same size. What shrinks is the bytes read and the attention FLOPs per step.
  • DeepSeek-V4 (preview, April 2026: V4-Pro with 1.6T total and 49B activated parameters, V4-Flash with 284B and 13B, both with 1M-token context) replaces MLA with interleaved layers of Compressed Sparse Attention (CSA) and Heavily Compressed Attention (HCA) [DeepSeek-V4, §2.3]. Three details are worth knowing:
    1. It keeps the MQA view and drops the up-projections. Each token produces one 512-dim KV entry per layer that serves as both key and value for all query heads ("shared key-value MQA"). That is the same shape that absorbed MLA attends over at decode time. Because the values now carry RoPE on their last 64 dimensions, V4 also rotates those dimensions of each attention output by the query's negative position, so the position signal becomes relative again (page 05).
    2. It compresses along the sequence. CSA merges the entries of every 4 consecutive tokens into one, using learned softmax weights over overlapping windows, and then runs DSA-style top-k selection over the compressed entries (top 1,024 in V4-Pro). HCA merges every 128 tokens and attends densely over the result. A 128-token uncompressed sliding window keeps local detail, and learned attention sinks let a head attend to "nothing".
    3. It lowers precision. KV entries are stored in FP8 except the RoPE dimensions (BF16), and the indexer runs in FP4.
    DeepSeek reports that at 1M tokens V4-Pro needs 27% of V3.2's single-token inference FLOPs and 10% of its KV cache, and about 2% of the cache of a BF16 GQA-8 baseline with 128-dim heads [DeepSeek-V4, Abstract, §2.3.4].
The pattern to remember

KV bytes = layers × tokens × features per token × bytes per feature, and each generation attacked a different factor. MQA and GQA cut the number of distinct K/V heads (features). MLA compressed every token's K/V into one shared latent (features). DSA reads only a subset of tokens per step (bandwidth, not capacity). CSA/HCA merge the tokens themselves (tokens), and FP8/FP4 storage cuts the last factor.

Other levers on the KV cache (covered elsewhere)

  • Cross-layer sharing (CLA): adjacent layers reuse one layer's K/V. With MQA, sharing across pairs halves the cache again with a small perplexity cost at 1B and 3B scale. Note that it reduces capacity, not per-step bandwidth, because each layer still re-reads the shared cache [Brandon et al. 2024, §2.3].
  • KV quantization to FP8 or INT4 halves or quarters bytes at any architecture: page 17.
  • Sliding-window / local layers cap the cache for most layers at a window size: page 09.
  • Sparse attention such as DeepSeek Sparse Attention keeps the full cache but reads only the top-k entries per query, cutting bandwidth and FLOPs rather than capacity: page 09 and page 28.
  • Linear attention / SSM hybrids replace the growing cache with a fixed-size state in most layers: page 09.

Systems consequences

Tensor parallelism and the cache

Tensor parallelism for attention usually splits heads across GPUs (page 15). The cache follows the KV heads:

  • GQA with \(n_{kv}\) ≥ TP degree shards cleanly. Llama-3-70B has 8 KV heads, so 8 GPUs hold one each.
  • MQA, or GQA with \(n_{kv}\) below the TP degree, must replicate KV heads, so the real cache is larger than the formula says [Llama 2, App. A.2.1].
  • MLA: every head reads every latent, so head-sharded TP replicates the whole latent cache on each rank. Consistent with this, DeepSeek-V3's decode deployment keeps attention TP small (TP4 with sequence parallelism) and scales out with 80-way data parallelism (different requests on different GPUs), while the MoE layers use 320-way expert parallelism [DeepSeek-V3, §3.4.2].

Head count becomes a cost knob

In absorbed MLA, attention FLOPs per cached token scale with \(n_h\) (each head does 576 + 512 dims of work against every cached latent), while the bytes read do not. DeepSeek-V3 uses 128 heads for 61 layers. Kimi K2's report says DeepSeek chose roughly twice as many heads as layers "to better utilize memory bandwidth", and that at 128K context going from 64 to 128 heads (with 384 experts) raises inference FLOPs by 83% for a validation-loss gain of only 0.5 to 1.2%. K2 therefore uses 64 heads [Kimi K2, §2.3]. Our intensity estimate says the same thing: 128 heads gives ≈242 FLOPs/byte, near the H800's ≈295 balance point, so more heads would make decode attention compute-bound.

From your jet tagger

Your tagger ran one forward pass over a whole jet: every particle's keys and values were computed, used once, and discarded, so there was no cache and no "decode" regime. That is exactly the compute-bound "prefill" regime. Everything on this page is about the other regime, generating one token at a time, which is what makes KV memory, not FLOPs, the binding constraint for serving LLMs.

Common misconceptions

  • "GQA reduces attention FLOPs." Barely. Every query head still scores every position. GQA cuts K/V projection parameters, cache size and bytes read per step.
  • "MQA/GQA mainly speed up training." Training is compute-bound and changes little. The win is in decode, which is bandwidth- and capacity-bound.
  • "A bigger batch fixes memory-bound decoding." Only for the weight matmuls. Each sequence has its own KV cache, so attention's FLOPs per byte do not improve with batch size.
  • "MLA caches 512 numbers per token." It caches 576 per layer: the 512-dim latent plus the 64-dim decoupled RoPE key. And it is per layer, so multiply by 61.
  • "MLA is just low-rank K and V." Low-rank K/V alone would force you to decompress the whole cache every step. The contributions are absorption (turning decode into latent-space MQA) and decoupled RoPE (which makes absorption possible with rotary positions).
  • "Absorption merges matrices into one." Merging \(W^{UQ}W^{UK\top}\) per head would increase parameters. Implementations reorder the multiplications instead.
  • "MLA is always run in absorbed form." Absorbed form costs 3.4× more attention FLOPs. Training and prefill use the decompressed MHA mode.
  • "Cross-layer KV sharing also cuts bandwidth." It cuts memory capacity. Each layer still re-reads the shared cache during decode.

Interview questions

Warm-up Why do we need a KV cache, and what is its size per token?

In autoregressive decoding, each new token attends to all previous tokens' keys and values at every layer. They don't change once computed (causal attention), so we store them instead of recomputing them. Recomputing would add \(O(T)\) work per step, \(O(T^2)\) per sequence.

Size per token = \(L \cdot 2 \cdot n_{kv} \cdot d_h \cdot b\) bytes (\(n_{kv}=n_h\) for MHA, 1 for MQA; \(b\)=2 for bf16). Total = that × tokens × batch.

Warm-up Define MHA, MQA and GQA in one sentence each.

MHA: every query head has its own key and value head. MQA: all query heads share one key head and one value head. GQA: query heads are split into \(n_{kv}\) groups, each sharing one key/value head. GQA-1 = MQA, GQA-\(n_h\) = MHA.

Warm-up Compute Llama-3-8B's KV cache for a batch of 16 sequences at 8K context.

Per token: \(32 \times 2 \times 8 \times 128 \times 2 = 131{,}072\) B = 128 KiB. Tokens: \(16 \times 8192 = 131{,}072\). Total: \(128\text{ KiB} \times 131{,}072 = 16\) GiB, about the size of the bf16 weights (~15 GiB). With MHA (32 KV heads) it would be 64 GiB and would not fit next to the weights on an 80 GB GPU.

Core Why is decode attention memory-bandwidth bound, and why doesn't a larger batch help it?

Per cached token per layer, one query token does \(4 n_h d_h\) FLOPs (scores plus weighted sum) and reads \(2 n_{kv} d_h\) elements (\(4 n_{kv} d_h\) bytes in bf16). That is \(n_h/n_{kv}\) FLOPs/byte: 1 for MHA, 4 to 16 for GQA. An H100 needs about 295 FLOPs/byte to be compute-bound, so the kernel is limited by how fast HBM streams the cache.

Batching helps weight matmuls because one loaded weight matrix is reused by all B sequences. KV caches are per sequence, so B sequences mean B times the bytes and B times the FLOPs, and the ratio is unchanged. The fix has to be architectural (share K/V across heads, compress, quantize, sparsify) or amortize reads over multiple query tokens (for example, speculative decoding verifies several tokens per cache read).

Core How would you convert a trained MHA model to GQA, and how much does it cost?

Following Ainslie et al.: for each group of \(g\) heads, set the new K projection to the mean of the group's K projections (same for V). Leave queries and output unchanged. Then continue pretraining ("uptrain") on the original recipe for a fraction \(\alpha\) of the original steps. \(\alpha = 5\%\) recovered nearly all quality for T5-XXL GQA-8 (47.1 vs 47.2), with diminishing returns by 10%. Mean-pooling beat keeping the first head, which beat random init: the more pretrained information you keep, the better. GQA is already reasonable right after conversion, while MQA needs uptraining to be useful.

Core Why do so many models use 8 KV heads?

(1) Quality: 8 groups recovers nearly MHA quality in the GQA and Llama 2 ablations, and inference cost rises only modestly going from 1 to 8 groups, with steeper cost beyond (GQA paper, Fig. 6). (2) Serving: large models are served with 8-way tensor parallelism inside an 8-GPU node, sharding heads. With 8 KV heads each GPU holds exactly one, so the cache shards perfectly. With MQA the single KV head would be replicated 8×, so the real footprint would equal GQA-8's anyway (Llama 2, App. A.2.1). (3) As \(n_h\) grows with scale, a fixed \(n_{kv}\) keeps a sensible group size.

Core Write down MLA's equations. What exactly is cached, and how big is it for DeepSeek-V3?

\(c^{KV}_t = h_t W^{DKV}\) (512); \(k^C_{t,i} = c^{KV}_t W^{UK}_i\), \(v^C_{t,i} = c^{KV}_t W^{UV}_i\) (128 each per head); \(c^Q_t = h_t W^{DQ}\) (1536); \(q^C_{t,i} = c^Q_t W^{UQ}_i\); decoupled RoPE: \(q^R_{t,i} = \RoPE(c^Q_t W^{QR}_i)\) (64, per head), \(k^R_t = \RoPE(h_t W^{KR})\) (64, shared). Head \(i\)'s query is \([q^C; q^R]\), key \([k^C; k^R]\), value \(v^C\), scale \(1/\sqrt{192}\), then \(W^O\).

Cached: \(c^{KV}_t\) and \(k^R_t\), so 576 elements per layer. × 61 layers × 2 bytes = 70,272 B ≈ 68.6 KiB per token, about 8.6 GiB for a 128K-token sequence.

Core Derive weight absorption. What does MLA look like at decode time?

Scores: \(q^C_{t,i}\cdot k^C_{j,i} = q^C_{t,i}(c_j W^{UK}_i)^\top = (q^C_{t,i}W^{UK\top}_i)\cdot c_j\). So project each head's query into the 512-dim latent space once per step and dot it with cached latents directly. Outputs: \(\sum_j a_{j} c_j W^{UV}_i = (\sum_j a_j c_j)W^{UV}_i\), so take the weighted sum of latents first and up-project once.

Result: every head scores against the same vectors \([c_j; k^R_j]\) (576-dim) and averages the same vectors \(c_j\) (512-dim). That is MQA with a 576-dim shared key and 512-dim shared value, over 128 query heads. It has MQA's bandwidth efficiency but MHA-like expressiveness, because the per-head maps are folded into the queries and outputs.

Core Why is RoPE incompatible with absorption, and how does decoupled RoPE fix it?

RoPE rotates query and key by position-dependent \(R_t, R_j\). With RoPE applied to \(k^C = c_j W^{UK}_i\), the score becomes \(q R_{t-j} W^{UK\top}_i c_j^\top\). The rotation sits between \(q\) and \(W^{UK}\) and depends on \(j\), so there is no single absorbed query. You would need one per cached position, which is equivalent to decompressing all keys every step.

Fix: keep the compressed content path position-free and add a separate small path for position. Each head gets a 64-dim RoPE query, and all heads share one 64-dim RoPE key per token (cached). The score is (absorbable content term) + (small MQA-style positional term). Cost: 64 extra cached numbers per layer and a 192-dim scale.

Core MLA has an "MHA mode" and an "MQA mode". Which is used when, and why?

Absorbed (MQA) mode costs \(2n_h(576+512)\) vs \(2n_h(192+128)\) attention FLOPs per cached token, 3.4× more, but reads 576 instead of 40,960 elements. In decode, one query token per sequence makes attention bandwidth-bound, so fewer bytes wins: use MQA mode. In training and prefill, thousands of query tokens share each K/V, so attention is compute-bound. Decompress K and V once for the chunk and run standard MHA (MHA mode) to avoid the 3.4× FLOP penalty. DeepSeek documents exactly this split for V3.1 (V3.2 report, App. A).

Deep-dive Compute the decode-attention arithmetic intensity for Llama-3-8B, DeepSeek-V3 with MLA, and Kimi K2. What does this say about choosing the number of heads?

Llama-3-8B (GQA, 32/8): 4 FLOPs/byte. DeepSeek-V3 absorbed MLA: \(2\cdot128\cdot1088 / (576\cdot2) \approx 242\). Kimi K2 (64 heads): ≈121. The H800/H100 balance point is ≈295 (989 TFLOP/s ÷ 3.35 TB/s).

So MLA with 128 heads pushes decode attention close to compute-bound: bytes are nearly fully used. Adding heads adds FLOPs per cached token without adding bytes, so beyond the balance point it only costs time. This is why head count becomes a real cost knob at long context. Kimi reports that 128 vs 64 heads (at 384 experts, 128K context) is +83% inference FLOPs for a 0.5 to 1.2% validation-loss gain, and chose 64. Also note these are attention-only numbers. The projection matmuls are weight-bound and improve with batch.

Deep-dive Is MLA more expressive than GQA at the same cache size? Sketch the argument.

Yes (TransMLA, App. A). Given GQA with \(n_{kv}\) KV heads, set MLA's latent to the concatenated GQA keys and values (\(r = 2 n_{kv} d_h\), the same cache) and make each head's \(W^{UK}_i, W^{UV}_i\) a 0/1 selector picking its group's key/value. That reproduces GQA exactly. A general MLA has dense learned up-projections and can produce \(n_h\) distinct keys per token, while GQA can only produce \(n_{kv}\) distinct ones replicated. So GQA ⊂ MLA. With RoPE present, the equivalence needs the absorbed form. Caveat: containment of function classes says nothing about optimization or trained quality at a given compute budget. That part is empirical (DeepSeek-V2 Table 9).

Deep-dive How does tensor parallelism interact with MQA and MLA caches, and what do deployments do about it?

Head-sharded TP gives each GPU a subset of heads. With GQA and \(n_{kv}\) ≥ TP degree, each GPU stores only its KV heads. With MQA the one KV head is needed by every GPU, so it is replicated. With MLA, every query head reads every latent, so each TP rank needs the full latent cache, also replicated. That wastes capacity and makes large TP pointless for attention. Deployments therefore keep attention TP small and scale with data parallelism over requests. DeepSeek-V3 decodes with attention at TP4 + sequence parallelism and DP80, combined with EP320 for the MoE layers (V3 report, §3.4.2). Llama 2 chose GQA-8 over MQA partly for this reason.

Deep-dive Design question: a 70B dense GQA-8 model must serve 4× more concurrent 128K-token sessions per node. What are your options?

First quantify: Llama-3-70B-like (80 layers, 8 KV heads × 128, bf16) is \(80\cdot2\cdot8\cdot128\cdot2\) = 327,680 B = 320 KiB/token, so 40 GiB per 128K session. Options, roughly in order of risk:

  • KV quantization to FP8 (2×) or INT4 (4×): no retraining, needs quality evaluation especially at long context.
  • Prefix caching / paged KV if sessions share long prompts (system prompts, documents).
  • Architectural changes that need training: convert to MLA (TransMLA-style, a few billion tokens of recovery training), convert most layers to sliding-window attention (cache capped at the window), or cross-layer KV sharing (2×, capacity only).
  • Sparse attention (DSA-style top-k) cuts per-step bandwidth and FLOPs but not capacity, unless paired with offloading the cold part of the cache to CPU.

A strong answer states what each option saves (capacity, bandwidth, or both), what it risks (long-context recall is most sensitive), and how to evaluate it (RULER/needle tests at full length, not just short-context benchmarks).

Deep-dive DeepSeek-V2's ablation shows MHA far ahead of GQA-8 at 7B, but Llama 2's shows them roughly equal. How would you reconcile this?

The setups differ in ways that matter. (1) Parameter matching: DeepSeek matched parameters by changing the number of layers, Llama 2 by widening the FFN, and depth versus width changes quality differently. (2) Scale and data: 7B on 1.33T tokens versus 30B on 150B tokens. The larger 30B model has more heads, so the relative loss from grouping may be smaller. (3) Benchmarks: DeepSeek chose four "hard" knowledge benchmarks, including Chinese ones, while Llama 2 averaged many easier tasks where differences wash out. (4) Single runs with no reported variance. The defensible conclusion is that GQA has a real but setup-dependent quality cost, and that lab ablations motivating a new method deserve independent replication.

Cheat sheet

  • KV bytes/token = \(L \cdot (\text{cached elems per layer}) \cdot b\). MHA \(2n_hd_h\), GQA \(2n_{kv}d_h\), MQA \(2d_h\), MLA \(d_c + d_h^R\).
  • Llama-3-8B: 128 KiB/token → 16 GiB at 128K. DeepSeek-V3 (MLA): 576 × 61 × 2 B = 68.6 KiB/token → 8.6 GiB at 128K.
  • Decode attention intensity ≈ \(n_h/n_{kv}\) FLOPs/byte in bf16. H100/H800 balance point ≈ 295. Batching does not raise it.
  • GQA: \(g = n_h/n_{kv}\) query heads per KV head. Convert MHA by mean-pooling each group's K/V projections, then uptrain about 5%. 8 KV heads matches 8-way TP.
  • MQA: one KV head. Fastest and smallest, but loses quality, can destabilize training, and replicates under TP.
  • MLA: \(c^{KV} = hW^{DKV}\) (512) → per-head \(k^C, v^C\) by up-projection. Absorb \(W^{UK}\) into queries and \(W^{UV}\) into outputs. Decode becomes MQA over latents (576-dim key, 512-dim value).
  • RoPE breaks absorption (\(R_{t-j}\) lands between \(q\) and \(W^{UK}\)). Decoupled RoPE adds a 64-dim per-head \(q^R\) and one shared cached \(k^R\). Scale \(1/\sqrt{192}\).
  • Absorbed mode: 3.4× attention FLOPs, 71× fewer bytes. Decode uses MQA mode, training and prefill use MHA mode.
  • Evidence: MLA ≥ MHA with 4 to 14% of the cache (DeepSeek-V2 App. D). Treat single-lab ablations with care.
  • Head count is a cost knob for absorbed MLA: Kimi K2 uses 64 heads vs V3's 128 (+83% inference FLOPs at 128K for 128 heads).
  • After MLA: V3.2 adds top-2,048 sparse reads (DSA). V4 (2026) uses one shared 512-dim KV entry per token (MQA-style), merged 4× (CSA, plus top-k) or 128× (HCA): about 10% of V3.2's KV cache at 1M tokens.
