Memory, precision & parallelism

P0 ~80 min Prereqs: 04 Transformer block, 08 Mixture of Experts, 14 Optimization

Research-engineer loops always include "how would you train model X on N GPUs?" This page teaches the whiteboard answer: count the bytes (model states and activations), choose number formats, price every collective, and place data, tensor, pipeline, expert and context parallelism on the network hierarchy so that model FLOPs utilization lands near 40%. Every number below is derived from a stated config or taken from a primary source.

Where the memory goes

A training step holds four kinds of data in GPU memory 显存: model states (weights, gradients, optimizer state), which scale with the parameter count \(N\); activations, which scale with tokens in flight times layers times width; temporary buffers; and fragmentation, memory that is free but unusable [ZeRO, §3]. Units: 1 GB = \(10^9\) bytes (page 04 quotes some numbers in GiB; 1 GiB = 1.074 GB).

Model states: 16 bytes per parameter

Mixed-precision training 混合精度训练 runs the forward and backward passes in a 16-bit format but keeps an fp32 master copy for the update [Micikevicius et al. 2017, §3.1]. With Adam, that means five tensors per parameter. ZeRO counts them as \(2N + 2N + KN\) with \(K = 12\) [ZeRO, §3.1]:

Three-quarters of the bytes (\(12/16\)) are optimizer state, so sharding it (ZeRO-1, below) is the cheapest big win. An 8B model does not fit on an 80 GB H100 before a single activation is stored. The number 16 is specific to this recipe: Llama 3 accumulates and reduce-scatters gradients in fp32 [Llama 3, §3.3.2], which makes 18 bytes, while DeepSeek-V3 keeps fp32 master weights and gradients but bf16 Adam moments [DeepSeek-V3, §3.3.3], about 14 by my count (2 + 4 + 4 + 2 + 2).

def states_gb(N, stage, Nd, K=12, w=2, g=2):
    """Per-GPU model-state GB with the ZeRO accounting: stage 0 = DDP, 1/2/3 = ZeRO-1/2/3."""
    p  = w * N / (Nd if stage >= 3 else 1)     # working weights
    gr = g * N / (Nd if stage >= 2 else 1)     # gradients
    o  = K * N / (Nd if stage >= 1 else 1)     # fp32 master + Adam m, v
    return (p + gr + o) / 1e9

Activations: Korthikanti's per-layer formula

Backpropagation needs the tensors the forward pass produced. Korthikanti et al. count, for a GPT-style layer, every tensor that must be kept, in bytes, using 16-bit values (dropout masks take one byte per element) [Korthikanti et al. 2022, §4.1]. In their symbols, which we adopt in this section, \(s\) is the sequence length (our \(T\)), \(b\) the micro-batch size, \(h\) the hidden size (our \(d\)) and \(a\) the number of attention heads (our \(n_h\)). Read the two terms separately. The \(34\,sbh\) part is linear in sequence length. The \(5as^2b\) part comes from the \(s \times s\) score matrix of every head and is quadratic. Since \(5as/h = 5s/d_h\) with \(d_h = h/a\) the head dimension, it does not depend on model width: it exceeds 34 once \(s > 6.8\,d_h\), about 870 tokens for \(d_h = 128\). At 8K context the quadratic term is 90% of the total. The formula assumes GPT-2-style blocks (GeLU, \(4h\) MLP, dropout, full multi-head attention); Llama's SwiGLU, GQA and lack of dropout change both constants. Counting bf16 tensors for a Llama-3-8B layer with a fused attention kernel, I get \(9\,sbh\) for attention (input 2, normed input 2, \(Q\) 2, \(K\) and \(V\) 0.5 each, output 2) plus \(25\,sbh\) for the SwiGLU MLP (residual 2, normed 2, gate, up and \(\text{silu}(\text{gate}) \odot \text{up}\) at \(2 \cdot 3.5 = 7\) each): 34 again, by coincidence. A plain eager PyTorch layer stores 41 (my measurement), since autograd also keeps \(\text{silu}(\text{gate})\), while a fused SwiGLU that recomputes the product saves only gate and up and gives 27. Without dropout, an unfused softmax adds only \(2as/h\) (the softmax output) instead of \(5as/h\), which is 128 instead of 320 at \(s = 8192\): the "store everything" row below is the GPT-style upper bound, and a dropout-free Llama layer would store roughly 160 to 170. The scaling with \(s\), \(b\) and \(L\) is what matters.

What parallelism does to it. Tensor parallelism of degree \(t\) divides the tensors inside the attention and MLP blocks, but the layer-norm inputs, dropout masks and block inputs are replicated, which leaves a \(10\,sbh\) term. Sequence parallelism 序列并行 shards those replicated regions along the sequence, and everything is divided by \(t\). Pipeline parallelism does not shrink activation memory: under 1F1B the first stage keeps \(p\) micro-batches of \(L/p\) layers, so it stores \(L\) layers' worth regardless of \(p\) [Korthikanti et al. 2022, §4.2, Eq. 2, 4, 5]. Activation checkpointing

Activation recomputation 激活重计算 (gradient checkpointing) trades FLOPs for memory: keep some tensors and rerun part of the forward pass inside the backward pass. Splitting an \(n\)-layer network into \(\sqrt{n}\) segments costs \(O(\sqrt{n})\) memory for one extra forward pass [Chen et al. 2016, §4.3]. For a transformer, full recomputation stores each layer's input (\(2sbh\)) and redoes the layer's forward. The step executes \(2N + 2N + 4N = 8N\) FLOPs per token instead of \(6N\): +33% (Korthikanti et al. observed 30 to 40% [§5]).

Selective recomputation is smarter: recompute only the tensors that are large but cheap to regenerate. The \(5as/h\) term consists of \(QK^\top\), softmax, dropout and attention-over-\(V\) tensors, which have huge sizes but few FLOPs per element. For GPT-3 (\(a = 96\), \(s = 2048\), \(h = 12288\), so \(5as/h = 80\)) recomputing only those saves 70% of activation memory for 2.7% extra FLOPs; for MT-NLG it saves 65% for 1.6% [Korthikanti et al. 2022, §5]. Fused attention kernels (FlashAttention, page 16) build the same idea into the kernel: the score matrix is never written to HBM and is recomputed in the backward pass.

Temporary buffers and fragmentation

Fused communication buffers are a classic hidden cost: an fp32 flattened gradient buffer for a 1.5B-parameter model is 6 GB, so ZeRO uses constant-size buffers. Fragmentation comes from mixing long-lived and short-lived tensors: ZeRO saw out-of-memory failures with over 30% of memory still free [ZeRO, §3.2], and PyTorch FSDP found that for GPT-175B on 128 A100s with batch size 2, defragmentation made the backward pass 85.6% of iteration time instead of the usual 67% [FSDP, §5.4]. Also budget the fp32 logits: \(8192 \times 128{,}256 \times 4\) bytes = 4.2 GB per sequence (page 04).

fp16 and loss scaling

fp16 has 10 mantissa bits (good) but only 5 exponent bits: nothing below \(2^{-24} \approx 6\times10^{-8}\) survives, and gradient values are dominated by tiny magnitudes. In Micikevicius et al.'s histogram of activation gradients for a Multibox SSD detector (collected during fp32 training), much of fp16's representable range sat unused while many values fell below it, yet values in \([2^{-27}, 2^{-24})\) still mattered: the network diverged without scaling, and a scale of 8 (three binades) was enough. A bigLSTM language model needed a scale of 128 [§3.2, §4]. Loss scaling 损失缩放 multiplies the loss by \(S\) before backpropagation, so by the chain rule every gradient is scaled by \(S\) and shifts into range. Then unscale the gradients in fp32 before clipping or the optimizer, and if any gradient is inf or NaN, skip the step and reduce \(S\); grow \(S\) again after a run of clean steps (dynamic loss scaling).

bf16: why it needs no scaling, and what it still needs

bf16 keeps fp32's 8 exponent bits, so it has fp32's range (max \(3.4\times10^{38}\), min normal \(1.2\times10^{-38}\)). Any gradient that fp32 can represent is essentially representable in bf16, so nothing flushes to zero and loss scaling disappears. The price is precision: 7 stored mantissa bits (8 significant), a relative step of \(2^{-7} = 0.78\%\). That has two consequences:

  • Small updates vanish. If an update is smaller than half the spacing of the weight, round-to-nearest returns the old weight. Micikevicius et al. give two fp16 failure modes: updates below \(2^{-24}\) become zero (about 5% of weight-gradient values in their Mandarin speech model), and updates more than about 2048 times smaller than the weight are shifted out; updating fp16 weights directly cost that model 80% relative accuracy [§3.1]. For bf16 the second threshold is roughly 256 to 512 times. Hence an fp32 master copy stays even when loss scaling goes.
  • Accumulations must be fp32: matmul accumulators, gradient accumulation across micro-batches, and gradient reduction (Llama 3 does both of the latter [§3.3.2]).
import torch
w = torch.tensor(0.02, dtype=torch.bfloat16)          # stored as 0.02001953125; spacing (ulp) here is 2**-13 = 1.22e-4
u = torch.tensor(3e-5, dtype=torch.bfloat16)          # an Adam step of order lr = 3e-5, below half an ulp (6.1e-5)
print(bool(w + u == w))                               # True: the update rounds away
wb, wf = w.clone(), torch.tensor(0.02)                # bf16 weight vs fp32 master weight
for _ in range(10_000):
    wb = wb + u; wf = wf + 3e-5
print(float(wb), float(wf))                           # 0.02001953125 vs 0.32001...: bf16 never moved

An Adam update is of order the learning rate per coordinate, so late in a cosine schedule (learning rates near \(3\times10^{-5}\)) updates to weights of size 0.02 fall below bf16's half-spacing: pure-bf16 training without stochastic rounding or a master copy stalls (my illustration; the arithmetic is exact).

FP8 training

FP8 halves the bytes and (on Hopper) doubles tensor-core FLOP/s relative to bf16, with a very narrow format. The standard recipe [Micikevicius et al. 2022, §3] uses E4M3 for weights and activations and E5M2 for gradients (gradients need range, activations precision) and a per-tensor scaling factor that puts the tensor's maximum magnitude (amax) near the format's maximum (448 or 57,344), saturating overflows. In delayed scaling (the Transformer Engine style) the scale comes from a history of amax values from previous steps, avoiding a second pass over the tensor [DeepSeek-V3, §3.3.2].

The weakness is outliers: one large element sets the scale for the whole tensor and pushes everything else toward the bottom of a 3-bit-mantissa format. DeepSeek-V3's answer is fine-grained scaling, presented in the report as the first validation of FP8 training on an extremely large model [DeepSeek-V3, §3.3]:

  • Granularity: one scale per 1×128 tile of activations (one token, 128 channels) and per 128×128 block of weights, computed online from the current tile's amax (no history).
  • Format: E4M3 for all tensors, including gradients. Sharing an exponent per small group gives back the dynamic range that E5M2 would provide, so they spend the bits on mantissa.
  • All three GEMMs of a linear layer (Fprop, Dgrad, Wgrad) run in FP8 with BF16 or FP32 outputs.
  • Higher-precision accumulation: on H800 the tensor cores keep only about 14 bits when accumulating FP8 products, and a preliminary test at inner dimension \(K = 4096\) showed a maximum relative error near 2%. Every \(N_C = 128\) elements along \(K\), partial sums are promoted to FP32 registers on CUDA cores, where the per-tile scales are also applied.
  • What stays high precision: embeddings, output head, MoE gating, normalizations and attention operators (BF16/FP32); master weights and gradients (FP32); Adam moments (BF16). Cached activations are FP8 (E5M6 for one exception); MoE dispatch is FP8, combine BF16.
  • Result: relative loss error against a BF16 baseline stayed below 0.25% over about 1T tokens at two model scales.

Microscaling and FP4

Microscaling 微缩放 (MX) formats make DeepSeek's idea a hardware standard: a block of \(k = 32\) elements shares one 8-bit power-of-two scale (E8M0), and the elements are FP8, FP6, FP4 (E2M1) or INT8, giving MXFP8, MXFP6, MXFP4 and MXINT8 [Rouhani et al. 2023, Tab. 1]: \(4 + 8/32 = 4.25\) bits per element for MXFP4 (my arithmetic). DeepSeek-V3 notes that its tile and block scaling is "highly consistent" with microscaling.

NVFP4 uses 16-element blocks, an E4M3 block scale (not restricted to powers of two) and an FP32 per-tensor scale: 4.5 bits per element (my arithmetic). NVIDIA trained a 12B hybrid Mamba-Transformer on 10T tokens in NVFP4: validation loss stayed within about 1% of an FP8 run in the stable phase and widened to a little over 1.5% during learning-rate decay, with MMLU-Pro 62.58 versus 62.62 [NVFP4 report, §3]. The recipe: random Hadamard transforms on weight-gradient inputs, 2D 16×16 weight scaling, stochastic rounding of gradients, and about 16% of the linear layers (the first 2 and last 8 blocks) kept in BF16. In an 8B, 1T-token comparison it beat MXFP4, which needed 36% more tokens to match [§5]. Caveats: at most 12B parameters, no mixture of experts, and the report is about algorithms, not speed.

DeepSeek-V4 (April 2026) uses FP4 for the MoE expert weights and the CSA indexer's query-key path, as quantization-aware training in post-training [DeepSeek-V4, §5.2.1]. FP32 master weights are quantized to MXFP4 and dequantized to FP8 for the matmul. That is lossless because E4M3 has two more exponent bits than E2M1 and the 1×32 FP4 scales inside a 128×128 FP8 block fit in FP8's range, so the FP8 stack is reused unchanged (straight-through estimator in the backward pass), and rollouts use native FP4 weights so sampling matches deployment. FP4×FP8 peak throughput currently equals FP8×FP8 [§1], so today the gain is memory capacity and traffic, not FLOP/s.

Determinism and batch invariance

DeepSeek-V4 also treats numerics as a reproducibility problem: its kernels are batch-invariant (a token's output is bitwise identical wherever it sits in the batch) and deterministic in the backward pass, so pretraining, post-training and inference agree bit for bit [DeepSeek-V4, §3.3]. That rules out the usual split-KV attention (replaced by a dual-kernel decoding scheme with one fixed accumulation order), most split-\(k\) matmuls, and atomicAdd accumulation (replaced by per-SM buffers and a fixed-order sum); the paper reports negligible overhead for batch-invariant decoding attention. The payoff is that a loss spike can be replayed exactly and the trainer and sampler agree, which matters for reinforcement learning (page 25).

Collectives, data parallelism, ZeRO and FSDP

Collectives and what they cost

A collective 集合通信 is an operation in which all ranks (one process per GPU) exchange data together. Four of them cover nearly everything on this page. With \(n\) ranks and a message of \(S\) bytes, a bandwidth-optimal ring implementation sends the following from each rank:

The ring all-reduce derivation fits on a whiteboard. Cut the tensor into \(n\) chunks of \(S/n\) bytes. In \(n-1\) reduce-scatter steps every rank sends one chunk to its right neighbor, which adds it to its own copy; afterward rank \(r\) holds the fully summed chunk \((r+1) \bmod n\). In \(n-1\) all-gather steps the finished chunks circulate. Each step moves \(S/n\) per rank, so the total is \(2(n-1)S/n \to 2S\), independent of \(n\): adding ranks adds no bytes per rank and no rank is a bottleneck. ZeRO states it as: reduce-scatter and all-gather each move \(N\) elements, so standard data parallelism moves \(2N\) [ZeRO, §7.1], and NCCL's benchmarks use these same factors to convert time to bus bandwidth [nccl-tests]. With per-hop latency \(\alpha\) and link bandwidth \(B\), time is about \(2(n-1)\alpha + 2\frac{n-1}{n}S/B\): latency-bound for small messages, so libraries fuse tensors into big buckets (FSDP saw total time for a fixed volume rise quickly once each all-gather fell below about 33M elements [FSDP, §3.2.1]).

def ring_allreduce(chunks):                       # chunks[r][c]: rank r's chunk c; n ranks, n chunks each
    n = len(chunks)
    buf = [[c.clone() for c in rank] for rank in chunks]
    for s in range(n - 1):                        # reduce-scatter: rank r sends chunk (r - s) % n to rank r + 1
        msgs = [buf[r][(r - s) % n].clone() for r in range(n)]      # every rank sends its start-of-step value
        for r in range(n):
            buf[(r + 1) % n][(r - s) % n] += msgs[r]                # the receiver adds
    # rank r now holds the full sum of chunk (r + 1) % n
    for s in range(n - 1):                        # all-gather: rank r sends chunk (r + 1 - s) % n
        msgs = [buf[r][(r + 1 - s) % n].clone() for r in range(n)]
        for r in range(n):
            buf[(r + 1) % n][(r + 1 - s) % n] = msgs[r]             # the receiver overwrites
    return buf                                    # each rank sent 2 (n - 1) chunks = 2 (n-1)/n of the tensor

Data parallelism, and why it is not enough

Data parallelism 数据并行 replicates the model on every GPU, gives each replica a different slice of the batch, and all-reduces the gradients. It is compute-efficient (nothing is split, so matmuls stay big) and communicates once per step. Two limits force everything else on this page. Memory: every replica holds all \(16N\) bytes, so DDP runs out of memory beyond 1.4B parameters on 32 GB GPUs [ZeRO, §1]. Batch: replicas cannot outnumber the sequences in the global batch, and that batch cannot grow indefinitely without hurting optimization (page 14) [Narayanan et al. 2021, §1].

ZeRO-1, ZeRO-2 and ZeRO-3

The Zero Redundancy Optimizer 零冗余优化器 starts from an observation: the \(N_d\) replicas store identical optimizer states, gradients and parameters, which is pure redundancy. It removes the redundancy in three cumulative stages by sharding across the \(N_d\) data-parallel ranks [ZeRO, §5].

  • ZeRO-1 (\(P_{os}\), optimizer states). Each rank owns \(1/N_d\) of the optimizer state and updates only that \(1/N_d\) of the parameters. Gradients are reduce-scattered so each rank receives the sum for its shard, it updates its slice of the fp32 master weights, then all-gathers the new bf16 weights. That is a reduce-scatter plus an all-gather, exactly the two halves of the all-reduce it replaces: same \(2N\) volume. Memory: \(4N + 12N/N_d\).
  • ZeRO-2 (\(P_{os+g}\), plus gradients). As soon as a layer's gradients are computed in the backward pass they are reduce-scattered to their owner (in buckets) and the non-owned copies are freed. Still \(2N\). Memory: \(2N + 14N/N_d\).
  • ZeRO-3 (\(P_{os+g+p}\), plus parameters; PyTorch calls it FSDP). Every rank stores only its parameter shard. Each layer's parameters are all-gathered just before use in the forward pass and freed afterward, gathered again in the backward pass, and gradients are reduce-scattered: \(N + N + N =\) \(3N\), 1.5 times DDP [ZeRO, §7.2]. Memory: \(16N/N_d\).

Llama 3 does exactly that: its FSDP shards optimizer states and gradients, but "for model shards we do not reshard after forward computation to avoid an extra all-gather communication during backward passes" [Llama 3, §3.3.2]. FSDP

PyTorch's fully sharded data parallel 完全分片数据并行 implements the ZeRO-3 idea with three engineering ideas [Zhao et al. 2023, §3-4]:

  • FlatParameter units. The parameters of one wrapped module are flattened into one padded 1D tensor and cut into equal shards, so all-gather and reduce-scatter run on large, even buffers without copies. Peak parameter memory is \(O(\sum_i \psi_i/F + \max_i \psi_i)\): the shards plus the one unit currently gathered, so wrapping granularity trades memory for the number of collectives.
  • Sharding factor \(F\). \(F = 1\) is DDP, \(F = W\) (world size) is full sharding, and in between is hybrid sharding: shard inside a group (say a node), replicate across groups; gradients are reduce-scattered inside the group, then all-reduced across replicas. For a bf16 8B model (\(M = 16.06\) GB) on \(W = 64\) GPUs in 8-GPU nodes, cross-node traffic per GPU is about \(2M(W-G)/(GW) = 3.5\) GB with \(F = G = 8\), against 31.6 GB for DDP and 47.4 GB for full sharding (\(3M(W-1)/W\)). The paper quotes \(2M(W-1)/(GW)\) for the hybrid case, which is 3.95 GB here.
  • Overlap and memory control. All-gathers run on a separate CUDA stream with prefetching (backward prefetch sped up GPT-175B by about 18%). A rate limiter stops the CPU queueing all-gathers so eagerly that the allocator fragments: up to 5× faster on T5-11B, about 5% slower on DeepViT, so measure. Native mixed precision keeps the sharded fp32 master copy and gathers low-precision parameters.

FSDP trained GPT-175B on up to 512 A100s at more than 173 and 186 TFLOP/s per GPU for batch sizes 1 and 2 (55% and 60% of 312), scaling linearly from 128 to 512 GPUs; activation checkpointing was on, so this is nearer hardware than model utilization (my reading) [FSDP, §5.4].

Tensor and sequence parallelism

Tensor parallelism 张量并行 splits each weight matrix of a layer across \(t\) GPUs, so every GPU does \(1/t\) of the layer's FLOPs and holds \(1/t\) of its parameters. It needs communication inside every layer, on the critical path, so it only pays off on the fastest links. Megatron-LM's design makes it cost one all-reduce per block [Shoeybi et al. 2019, §3].

The MLP: column-parallel, then row-parallel

An MLP block computes \(Z = \text{act}(XA)\,B\) with \(A \in \R^{d \times \dff}\), \(B \in \R^{\dff \times d}\). Consider splitting \(A\) by rows: then \(XA = X_1 A_1 + X_2 A_2\), and because the activation is nonlinear, \(\text{act}(X_1A_1 + X_2A_2) \ne \text{act}(X_1A_1) + \text{act}(X_2A_2)\): the partial products must be summed (an all-reduce) before the activation. Now split \(A\) by columns, \(A = [A_1, A_2]\): each GPU computes its own slice \(\text{act}(XA_i)\) independently, with no communication, because the activation is elementwise. The second matrix is then split by rows, \(B = \begin{bmatrix} B_1 \\ B_2 \end{bmatrix}\), so each GPU can multiply its slice directly: \(Z = Y_1B_1 + Y_2B_2\), a sum of partial results. One all-reduce at the end, none in the middle. For SwiGLU, the gate and up projections are both column-parallel (their elementwise product is local) and the down projection is row-parallel: the same single all-reduce.

def tp_mlp(x, W1, W2, tp, act=F.gelu):            # x: (..., d), W1: (d, d_ff), W2: (d_ff, d)
    s = W1.shape[1] // tp                          # columns of W1 (= rows of W2) per rank
    partials = [act(x @ W1[:, r*s:(r+1)*s]) @ W2[r*s:(r+1)*s] for r in range(tp)]   # local work only
    return sum(partials)                           # the all-reduce (operator g)

Attention and the embedding

Attention splits by heads: the \(Q\), \(K\), \(V\) projections are column-parallel so each GPU owns whole heads and computes their attention locally, and the output projection \(W^O\) is row-parallel, again ending in one all-reduce. So a transformer layer costs two all-reduces in the forward pass and two in the backward pass (operators \(g\) and \(f\)) [Shoeybi et al. 2019, §3]. Constraints: \(t\) must divide the number of heads, and with GQA the KV heads must not be fewer than \(t\), or they get replicated, which is one reason GQA models use 8 KV heads to match 8-GPU nodes (page 07). The embedding table is sharded along the vocabulary, and the output logits are fused with the cross-entropy so that ranks exchange a scalar loss per token instead of all-gathering \(b \times s \times V\) logits.

What tensor parallelism costs, and why it stays in the node

Each all-reduce moves a \(b \times s \times h\) tensor. Four per layer (two forward, two backward), each costing \(2(t-1)/t\) times the tensor per rank, give \(8\,bsh\,(t-1)/t\) elements per device per layer per micro-batch [Narayanan et al. 2021, §3.2]. In bf16 that is \(16\,bsh\,(t-1)/t\) bytes. The layer's compute per device is \(72\,bsh^2/t\) FLOPs (\(3 \times 24bsh^2\) for a GPT-style layer, divided by \(t\); Korthikanti App. A). Dividing bytes by link bandwidth \(B_\ell\) and FLOPs by achieved throughput \(C\):

\[ \frac{t_{\text{comm}}}{t_{\text{compute}}} \approx \frac{16\,bsh\,\frac{t-1}{t} \big/ B_\ell}{72\,bsh^2/(t\,C)} = \frac{2}{9}\,(t-1)\,\frac{C}{B_\ell\,h} \]
Tensor-parallel traffic relative to compute (not overlapped): independent of \(b\) and \(s\), grows with \(t\) and with C/B, shrinks with width \(h\)

Worked number (Llama-3-70B layer, \(t = 8\), \(s = 8192\), \(b = 1\), bf16). Traffic: \(8 \times 8192 \times 8192 \times \tfrac{7}{8} \times 2\) B \(= 939.5\) MB per layer per micro-batch. Compute: \(6 \times 855.65\text{M} \times 8192 / 8 = 5.26\) TFLOP per GPU, which takes 13.3 ms at 40% of 989.4 TFLOP/s. Over NVLink at 450 GB/s the traffic takes 2.1 ms, 16% of compute if not overlapped. Over 50 GB/s InfiniBand it takes 18.8 ms, 1.41 times the compute. Tensor parallelism across nodes would leave the GPUs idle more than half the time. Empirically, ZeRO's authors ran a 40B Megatron model across two DGX-2 nodes and saw about 5 TFLOP/s per V100, under 5% of peak [ZeRO, §1], and Megatron's first takeaway is to use tensor parallelism up to the GPUs-per-node count and pipeline parallelism beyond [Narayanan et al. 2021, §3.2]. A second reason is arithmetic efficiency: splitting matrices by \(t\) also makes the GEMMs smaller and less efficient.

Sequence parallelism

After tensor parallelism the layer norms, dropouts and residual additions are still replicated on all \(t\) GPUs: cheap in FLOPs but the source of the \(10\,sbh\) memory term. They are independent across the sequence dimension, so Korthikanti et al. shard them along \(s\). The boundary operators change: \(f\) becomes an all-gather in the forward pass and a reduce-scatter in the backward pass, and \(g\) the reverse (Korthikanti et al. name the new pair \(g\) and \(\bar g\)). An all-reduce is a reduce-scatter followed by an all-gather, so the same bytes move and "sequence parallelism does not introduce any communication overhead" [Korthikanti et al. 2022, §4.2.2]. Per-layer activation memory drops to \(sbh(34 + 5as/h)/t\) (table in Activations). The full input of the first linear layer is stored sharded and re-gathered in the backward pass, with the all-gather overlapped with the computation of the gradient with respect to that input (the weight gradient is what needs the gathered tensor).

Three things called "sequence parallelism"

Megatron sequence parallelism (above) shards only the non-tensor-parallel regions, inside the tensor-parallel group. Context parallelism (below) shards the whole model's activations along the sequence and needs a scheme for attention. DeepSpeed-Ulysses is another sequence-sharding scheme for attention, built on all-to-all. Ask which one an interviewer means.

Pipeline parallelism

Pipeline parallelism 流水线并行 cuts the layers into \(p\) contiguous stages, one per GPU group. Stage \(i\) sends its output activations to stage \(i+1\) and, in the backward pass, receives gradients back. The traffic is a single \(b \times s \times h\) tensor per stage boundary per micro-batch per direction, point-to-point, which is small enough to cross InfiniBand: 134 MB for \(s = h = 8192\) in bf16, 2.7 ms at 50 GB/s, against 266 ms of compute per stage (numbers from the 70B plan below). The catch is the dependency chain: with one batch, only one stage is busy at a time and utilization is \(1/p\). The fix is to split the batch into \(m\) micro-batches and stream them.

Deriving the bubble

Let each stage take \(t_f\) for one micro-batch's forward pass and \(t_b\) for its backward pass. In the GPipe schedule all forwards run first, then all backwards [Huang et al. 2018]. The last stage cannot start until the first micro-batch has crossed \(p-1\) earlier stages, and in the same way the backward wave takes \(p-1\) extra steps to drain. The whole step takes

\[ T = (m + p - 1)(t_f + t_b), \qquad T_{\text{ideal}} = m\,(t_f + t_b), \qquad T_{\text{bubble}} = (p-1)(t_f + t_b). \]

Two ratios are in circulation and interviewers mix them up. Relative to the ideal compute time the bubble is \(\dfrac{p-1}{m}\) [Narayanan et al. 2021, §2.2.1]. As the fraction of wall-clock time each GPU sits idle it is \(\dfrac{p-1}{m+p-1}\), GPipe's \(O\big(\tfrac{K-1}{M+K-1}\big)\). State which you mean. The drill in exercises/drills/parallel.py simulates the schedule event by event and reproduces \((m+p-1)(t_f+t_b)\) exactly, for any ratio \(t_b/t_f\).

1F1B: same bubble, less memory

GPipe must keep the activations of all \(m\) micro-batches until the backward passes start. The one-forward-one-backward (1F1B, "PipeDream-Flush") schedule starts backward passes as early as possible: stage \(i\) (0-indexed) runs \(p-1-i\) warm-up forwards, then alternates one forward and one backward, then drains the remaining backwards. The bubble is identical, but a stage never holds more than \(p-i\) micro-batches of activations (the first stage \(p\), the last stage 1), instead of \(m\) [Narayanan et al. 2021, §2.2.1]. 1F1B is a memory optimization, not a bubble optimization.

def one_f_one_b(p, m, i):                            # operation order of stage i (0-indexed)
    warm = min(p - 1 - i, m)
    ops = [("F", j) for j in range(warm)]            # warm-up forwards
    f, b = warm, 0
    while f < m:                                     # steady state: one forward, one backward
        ops += [("F", f), ("B", b)]; f += 1; b += 1
    return ops + [("B", j) for j in range(b, m)]     # cool-down: drain the remaining backwards

Reducing the bubble

  • More micro-batches. Bubble \(\to 0\) as \(m \gg p\). GPipe reports the overhead as negligible for \(m \ge 4p\), helped by scheduling recomputation early [GPipe, §2.3]; the formula still gives 19% at \(p = 16\), \(m = 64\), so treat \(4p\) as a minimum. But \(m = B_{\text{global}}/(N_d\,b)\): raising data parallelism shrinks \(m\) and grows the bubble.
  • Interleaved 1F1B. Give each device \(v\) non-contiguous model chunks (device 1 holds layers 1, 2, 9, 10 instead of 1 to 4). Each chunk is \(1/v\) as long, the bubble becomes \(\frac{1}{v}\cdot\frac{p-1}{m}\), but every micro-batch now crosses \(v\) times more stage boundaries, so communication also grows by \(v\) [Narayanan et al. 2021, §2.2.2]. Llama 3 uses it with a bubble ratio \(\frac{p-1}{v\cdot m}\) and makes the number of consecutive micro-batches tunable so the batch size need not be divisible by \(p\) [Llama 3, §3.3.2].
  • Zero-bubble schedules. Split each backward pass into \(B\) (gradient with respect to the input, needed by the previous stage) and \(W\) (gradient with respect to the weights, needed only by the optimizer). \(W\) has no downstream dependency, so it can fill what would be idle time. For a transformer layer \(T_W \lt T_F \lt T_B\) and \(T_B + T_W = 2T_F\) [Qi et al. 2023, Tab. 1]. ZB-H1 has bubble \((p-1)(T_F + T_B - T_W)\), one third of 1F1B's when all three are equal, at 1F1B's memory; ZB-H2 is near zero but holds \(2p-1\) micro-batches of activations. Reported gains over 1F1B: up to 23% throughput at similar memory, up to 31% with more. The optimizer step is an obstacle, since global gradient-norm clipping and NaN checks synchronize all stages; they use an optimistic step with post-validation and rollback, because clipping and NaNs rarely trigger [Zero Bubble PP, abstract, §2, §4].
  • DualPipe (DeepSeek-V3). Feed micro-batches from both ends at once and overlap each forward chunk with a backward chunk so the expert all-to-all hides behind compute (below; cost accounting in page 27).

Expert and context parallelism

Expert parallelism

In a mixture-of-experts layer (page 08) each token is routed to a few of many expert MLPs. Expert parallelism 专家并行 places different experts on different GPUs (GShard introduced it at scale [Lepikhin et al. 2021]). A token's hidden state travels to its expert's GPU (an all-to-all dispatch), is processed, and returns (an all-to-all combine): two all-to-alls per MoE layer forward and two backward. Attention and dense parts stay data-parallel (or tensor-parallel), so EP is "sharding for the experts, data parallelism for everything else"; expert gradients reduce only among ranks holding the same expert.

EP is unavoidable for large MoEs because experts are almost all the parameters: 654B of 671B (97%) in DeepSeek-V3 (my count from the published config, which reproduces the 671B total). The cost is bandwidth. Per token and selected expert, DeepSeek-V4 sends the hidden state in FP8 on dispatch and BF16 on combine, \(d + 2d = 3d\) bytes, against \(6\,d\,d_e\) FLOPs for the three expert matrices (\(d_e\) is the expert hidden width) [DeepSeek-V4, §3.1]. Communication can be fully hidden when \(C/B \le V_{\text{comp}}/V_{\text{comm}} = 2d_e\), 6,144 FLOP per byte for V4-Pro (\(d_e = 3072\)). By my arithmetic a GPU with 1,979 TFLOP/s of dense FP8 then needs about \(1979/6144 = 322\) GB/s of dispatch and combine bandwidth, far above one 50 GB/s network port, so tokens must cross the network as few times as possible.

DeepSeek's engineering shows how far this can be pushed:

  • Node-limited routing. V3 limits each token to at most 4 nodes (V2: at most 3 devices), so a token crosses the slow network at most 4 times. It is sent once over InfiniBand to the GPU with the same in-node index on each target node, then forwarded over NVLink (160 GB/s versus 50 GB/s) to the GPUs hosting its experts; on average 3.2 experts per node are served without extra NVLink overhead. Only 20 of an H800's 132 SMs are enough to saturate both links [DeepSeek-V3, §3.2.2].
  • Overlap. Cross-node EP gave a computation-to-communication ratio of about 1:1, so DualPipe overlaps one micro-batch's all-to-all with another's compute [§3.2.1].
  • One fused kernel (DeepSeek-V4). Experts are split into waves: a wave's GEMMs start as soon as its tokens arrive, while the next wave's tokens are in flight and the previous wave's results are sent back. Theoretical speedup over compute-then-communicate is 1.92× for the V4-Flash shape (1.42× for a coarser overlap scheme); measured, 1.50 to 1.73× for general inference and up to 1.96× for latency-sensitive uses such as RL rollouts. It is open-sourced as MegaMoE in DeepGEMM [DeepSeek-V4, §3.1].

Routing and load balancing are page 08's subject; note that an unbalanced router makes some GPUs' compute and all-to-all volume larger, and every step waits for the slowest.

Context parallelism

At long context the activations dominate: at \(s = 131{,}072\) even the linear \(34\,sbh\) term is \(34 \times 131{,}072 \times 4096 = 18.3\) GB per layer for a Llama-3-8B-shaped model (the long-context recipes themselves are on page 10). Context parallelism 上下文并行 shards the sequence over \(c\) ranks: every rank holds \(s/c\) tokens, norms and MLPs are token-wise so they need no communication, and only attention has to see the other ranks' keys and values. Four ways to do that:

  • Ring attention [Liu et al. 2023]. Each rank keeps its query block while key/value blocks rotate around a ring and each rank computes blockwise attention (online-softmax rescaling, page 16). Communication hides if computing a block takes at least as long as sending it. For block length \(\beta\) and hidden size \(d\), one block pair costs \(4d\beta^2\) FLOPs and the key and value blocks are \(4\beta d\) bytes in bf16, so \(\beta \ge F/B\) (peak FLOP/s over link bandwidth) [§3]. For an A100 that is 1.0K tokens on NVLink but 24.5K over InfiniBand [Tab. 2]; my H100 numbers are \(989.4\text{T}/450\text{G} = 2.2\)K on NVLink and \(989.4\text{T}/50\text{G} = 19.8\)K over a 50 GB/s port. GQA shrinks the transferred bytes by \(d/d_{kv}\) (4× for Llama-3-8B, 8× for 70B); a causal mask halves the FLOPs and doubles the requirement.
  • All-gather context parallelism (Llama 3). All-gather \(K\) and \(V\), then attend with the local queries. The latency is exposed, but small: GQA makes \(K\) and \(V\) far smaller than \(Q\), and attention compute is \(O(S^2)\) against \(O(S)\) communication. Any mask works (Llama 3 uses a document mask). The sequence is cut into \(2c\) chunks and rank \(i\) takes chunks \(i\) and \(2c-1-i\), balancing causal work [Llama 3, §3.3.2].
  • DeepSpeed-Ulysses [Jacobs et al. 2023]. Inputs are sharded along the sequence; an all-to-all before attention swaps to "full sequence, subset of heads", each GPU attends for its heads, and a second all-to-all swaps back. Communication per link is \(4Nh/P\) for sequence length \(N\) on \(P\) GPUs, constant when both grow together (Megatron's sequence parallelism stays at \(4Nh\)). Head-parallel attention in the middle caps the degree at the number of heads (my inference).
  • Two-stage CP for compressed attention (DeepSeek-V4). CSA and HCA compress every \(m\) consecutive KV entries into one, and a group can straddle two ranks. Stage 1: each rank sends its last \(m\) uncompressed KV entries to the next rank, which compresses them with its own \(s\) entries into a fixed \(s/m + 1\) entries (padded). Stage 2: an all-gather plus a fused select-and-pad kernel yields \(c \cdot s/m\) entries [DeepSeek-V4, §3.4.3].

Putting it together: layouts and worked plans

A real job uses several dimensions at once: 3D parallelism (data, tensor, pipeline), 4D with context parallelism (Llama 3), or 5D with experts. The dimensions multiply: \(\text{GPUs} = t \cdot c \cdot p \cdot N_d\) (with EP folded inside the data-parallel dimension for the experts). The order matters because the mapping onto the network is what makes it fast. Llama 3 places them [TP, CP, PP, DP] from innermost to outermost: the innermost dimension "requires the highest network bandwidth and lowest latency" and is confined to a server, while data parallelism, outermost, "can tolerate longer network latency by asynchronously prefetching sharded model weights and reducing gradients" [Llama 3, §3.3.2].

The whiteboard procedure

  1. Count the states: \(16N\) bytes (or 14 to 18 for your recipe). If ZeRO-1 or ZeRO-2 over the whole cluster fits with activations, stop: no model parallelism is the fastest layout.
  2. Count the activations at your sequence length and micro-batch (\(34\,sbhL/t\) with sequence parallelism and selective recomputation, then adjust for your architecture).
  3. Add tensor parallelism up to the node size (8) only if layers are wide enough to keep GEMMs efficient and you need the memory; respect \(t \le n_{kv}\).
  4. Add pipeline parallelism across nodes until states plus activations fit and DP traffic stops dominating. Pick \(m\) and \(v\) so the bubble is a few percent, with \(m = B_{\text{global}}/(N_d b) \ge 4p\).
  5. Fill the cluster with data parallelism: \(N_d = \text{GPUs}/(t\,p\,c)\); ZeRO-1 first, FSDP if parameters still do not fit.
  6. MoE: expert parallelism across nodes with node-limited routing. Long context: context parallelism only for the training phases that need it.
  7. Price the communication of each dimension against step time, estimate MFU, and iterate.

Measuring efficiency: MFU and HFU

Model FLOPs utilization 模型浮点运算利用率 (MFU) is the ratio of observed throughput to the theoretical maximum throughput of a system running at peak FLOP/s, where the FLOPs counted are only those the model needs, "and not rematerialization" [PaLM, §4.1]. For a dense decoder with \(N\) matmul parameters, \(L\) layers, width \(d\) (more precisely heads times head dimension) and sequence length \(T\), per token:

\[ \text{MFU} = \frac{\text{tokens/s per GPU} \times \big(6N + 12\,L\,d\,T\big)}{\text{peak FLOP/s per GPU}} \]
PaLM Appendix B; the attention term \(12LdT\) counts the full \(T\times T\) scores, causal counting halves it. For MoE use activated parameters

Hardware FLOPs utilization (HFU) counts what the chip executes, including recomputation. With full recomputation the step runs \(8N\) instead of \(6N\) FLOPs per token, so \(\text{HFU} \approx \tfrac{4}{3}\,\text{MFU}\). PaLM recomputes about 75% of its non-attention forward FLOPs plus all attention forward FLOPs (App. B): 46.2% MFU, 57.8% HFU. With Korthikanti's selective recomputation the ratio is about \(1 + s/(6h)\) [§6, App. A, Eq. 9]: for the 175B model \(2048/(6 \cdot 12288) = 0.028\), and 51.4% MFU is indeed 52.8% HFU. By my count the recomputed attention forward adds only \(s/(18h)\), a third of that, so the reported HFU may be about 1 point too high; MFU is unaffected. PaLM introduced MFU because HFU rewards wasteful recomputation and depends on how operations are counted.

def mfu(tokens_per_s_per_gpu, n_params, peak, n_layers=0, d=0, T=0, causal=True):
    flops_per_token = 6 * n_params + (6 if causal else 12) * n_layers * d * T   # 6N + attention (12 L d T, halved if causal)
    return tokens_per_s_per_gpu * flops_per_token / peak

What holds MFU down

  • Exposed communication: tensor-parallel all-reduces, unhidden DP or FSDP collectives, expert all-to-all.
  • Pipeline bubbles and stage imbalance (the LM-head stage).
  • Small kernels: narrow layers, small micro-batches, grouped expert GEMMs with few tokens, memory-bound norms and elementwise ops (page 16).
  • Stragglers and failures: Llama 3 saw 466 job interruptions in 54 days on 16K GPUs (419 unexpected, about 78% hardware) yet kept more than 90% effective training time [Llama 3, §3.3.4]. MFU measures steady-state math, not this.
  • Recomputation is not counted as useful work, so it lowers MFU while raising HFU.

For planning, invert the definition: training time \(= 6ND / (G \cdot \text{peak} \cdot \text{MFU})\), as in the 181-day estimate above. Page 34 collects the whiteboard formulas.

Common misconceptions

  • "ZeRO-3 sends 3× the data." It sends \(3N\) against DDP's \(2N\): 1.5×. ZeRO-1 and ZeRO-2 send exactly \(2N\), so they are free memory savings (per step with one micro-batch; with many, ZeRO-2 and ZeRO-3 communicate more often).
  • "bf16 is more precise than fp16." It has less precision (8 versus 11 significant bits) and far more range. That is why it needs no loss scaling, and why fp32 master weights and accumulation remain: near learning rates of \(10^{-5}\), updates to weights of size 0.02 round away in bf16.
  • "1F1B reduces the pipeline bubble." Its bubble equals GPipe's; it reduces activation memory (\(p\) micro-batches in flight instead of \(m\)). The bubble shrinks with more micro-batches, interleaving (÷\(v\), \(v\times\) the communication) or a \(B\)/\(W\) split.
  • "The bubble is \((p-1)/(m+p-1)\)." That is the idle fraction of wall-clock time; \((p-1)/m\) is relative to ideal compute. At \(p = 16\), \(m = 64\): 19.0% and 23.4%. Say which you mean.
  • "Tensor parallelism across nodes is fine with InfiniBand." For a 70B layer at \(t = 8\), its traffic takes 1.4 times the compute time over a 50 GB/s port, against 16% over NVLink. Keep \(t \le\) GPUs per node.
  • "Activation checkpointing is free memory." Full recomputation adds a forward pass (+33% FLOPs), lowering MFU and raising HFU. Selective recomputation costs 1.6 to 2.7%.
  • "Sequence parallelism and context parallelism are the same." Megatron's shards only the norm and dropout regions inside a tensor-parallel group. Context parallelism shards the whole model's activations along the sequence and needs a scheme (ring, all-gather, all-to-all) for attention.
  • "FP8 training means everything is FP8." DeepSeek-V3 runs the three matmuls per linear layer in FP8, but embeddings, head, MoE gating, norms and attention stay BF16/FP32, master weights and gradients are FP32, and Adam moments BF16.

Interview questions

Warm-up How much memory does it take to train a 7B model with AdamW in mixed precision? Where does it go?

Sixteen bytes per parameter before activations: bf16 weights (2), bf16 gradients (2), an fp32 master copy (4), and Adam's two fp32 moments (4 + 4). For 7B parameters that is 14 GB + 14 GB + 28 GB + 28 GB + 28 GB = 112 GB (104 GiB), of which 75% is optimizer state. It does not fit on an 80 GB GPU, so the states must be sharded: ZeRO-1 over 8 GPUs gives \(4N + 12N/8 = 28 + 10.5 = 38.5\) GB per GPU, ZeRO-3 gives 14 GB.

Activations come on top and scale with tokens in flight: for a 32-layer, 4096-wide model they are tens of GB per 8K-token sequence unless you recompute (see the activation question). Recipes shift the constant: fp32 gradient accumulation (Llama 3) makes it 18 bytes, bf16 Adam moments (DeepSeek-V3) about 14.

Warm-up Why can bf16 skip loss scaling when fp16 cannot? What does bf16 still need?

The issue with fp16 is range: 5 exponent bits, so values below \(2^{-24} \approx 6\times10^{-8}\) flush to zero, and gradients are dominated by tiny values. Loss scaling multiplies the loss by \(S\) so backpropagation produces gradients \(S\) times larger, shifting them into range; you unscale in fp32 before clipping and skip the step on inf or NaN (Micikevicius et al.: an SSD detector diverged without it and a scale of 8 sufficed; a big LSTM needed 128). bf16 keeps fp32's 8 exponent bits, so its range is fp32's (\(3.4\times10^{38}\) max, \(1.2\times10^{-38}\) min normal) and nothing needs shifting.

bf16 pays with precision: 7 stored mantissa bits, relative step \(2^{-7}\). So it still needs (1) an fp32 master copy, because updates smaller than about 1/256 to 1/512 of a weight round to zero (bf16(0.02) has spacing \(1.2\times10^{-4}\), so an update of \(3\times10^{-5}\) vanishes, and 10,000 of them leave it unchanged while an fp32 copy reaches 0.32), and (2) fp32 accumulation for matmuls, gradient accumulation across micro-batches and gradient reduction.

Warm-up What is MFU and how do you compute it? A Llama-3-8B run on 64 H100s reports 500,000 tokens/s at sequence length 8192. What is its MFU?

MFU is achieved model FLOP/s divided by the hardware's peak FLOP/s, counting only the FLOPs the model needs (\(6N\) per token plus attention) and not recomputation. Per GPU: \(500{,}000/64 = 7{,}812.5\) tokens/s. FLOPs per token: \(6 \times 7.505\text{B}\) matmul parameters \(+ 6 \cdot 32 \cdot 8192 \cdot 4096\) causal attention \(= 45.03 + 6.44 = 51.47\) GFLOPs. Achieved \(= 402.1\) TFLOP/s. Against the H100 dense bf16 peak of 989.4 TFLOP/s: 40.6%. With plain \(6N = 48.18\) GFLOPs it is 376.4 TFLOP/s, 38.0%.

State your conventions: dense peak (989.4, not the 1,979 sparsity number), which \(N\), whether attention is counted and whether causally. HFU additionally counts recomputed FLOPs (\(\approx \tfrac{4}{3}\) MFU with full recomputation). For a mixture of experts, use activated parameters.

Warm-up Name the main collectives and say which parallelism uses each. What does a ring all-reduce cost per GPU?

All-reduce (everyone gets the sum): DDP gradients, tensor-parallel outputs. Reduce-scatter (everyone gets one shard of the sum) and all-gather (everyone gets all shards): ZeRO/FSDP, sequence parallelism, all-gather context parallelism. All-to-all: MoE dispatch and combine, Ulysses. Send/receive: pipeline activations.

Ring all-reduce over \(n\) ranks of \(S\) bytes: cut into \(n\) chunks; \(n-1\) reduce-scatter steps and \(n-1\) all-gather steps each move \(S/n\), so each GPU sends \(2\frac{n-1}{n}S\), tending to \(2S\) whatever \(n\) is. Reduce-scatter and all-gather cost \(\frac{n-1}{n}S\) each. Example: 16 GB of bf16 gradients over 64 ranks: \(2 \cdot \tfrac{63}{64} \cdot 16.06 = 31.6\) GB per GPU, 0.63 s at 50 GB/s.

Core Explain ZeRO-1, ZeRO-2 and ZeRO-3 and their communication costs.

All three shard, across the \(N_d\) data-parallel ranks, what plain DP replicates. ZeRO-1 shards optimizer state: memory \(4N + 12N/N_d\). Reduce-scatter gradients so each rank gets the sum for its shard, update that shard's fp32 master weights, all-gather the new weights: \(N + N = 2N\) elements, the same as the all-reduce it replaces. ZeRO-2 also shards gradients (reduce-scatter as they are produced, free the rest): \(2N + 14N/N_d\), still \(2N\). ZeRO-3 also shards parameters: each layer is all-gathered before forward, freed, gathered again for backward, and gradients reduce-scattered: \(3N\), 1.5× DDP, memory \(16N/N_d\).

Numbers (7.5B, \(N_d = 64\), ZeRO Table 1): 120, 31.4, 16.6, 1.9 GB. Caveats an interviewer likes: these volumes assume one micro-batch per step; with \(m\) micro-batches ZeRO-2 reduce-scatters and ZeRO-3 re-gathers every micro-batch unless parameters stay resident (Llama 3 keeps them), and ZeRO-3's collectives span the whole DP group, so across nodes it needs prefetch and overlap. Megatron's PTD-P beat ZeRO-3 by 70% at 175B and 530B for that reason, when the GPU count was doubled at a fixed global batch.

Core How does tensor parallelism split an MLP and attention? Why keep it within a node?

MLP: split \(A\) (\(d \times \dff\)) by columns and \(B\) by rows. Each GPU computes \(\text{act}(XA_i)\) locally (the activation is elementwise, so no synchronization is needed; splitting \(A\) by rows would need a sum before the nonlinearity) and then \(Y_iB_i\), a partial sum of the output. One all-reduce combines them. SwiGLU: gate and up column-parallel, down row-parallel. Attention: whole heads per GPU (Q, K, V column-parallel, output projection row-parallel), one all-reduce. So two all-reduces per layer forward and two backward. Embedding is vocabulary-sharded and the loss is fused with the logits to avoid all-gathering \(b \times s \times V\) values.

Cost: \(8\,bsh\,(t-1)/t\) elements per device per layer per micro-batch, on the critical path. Relative to compute it is \(\tfrac{2}{9}(t-1)C/(B_\ell h)\). For a Llama-70B layer at \(t = 8\), \(s = 8192\): 940 MB per layer, 2.1 ms over NVLink against 13.3 ms of compute (16%), 18.8 ms over a 50 GB/s port (141%). Hence \(t \le\) GPUs per node; ZeRO's authors measured about 5 TFLOP/s per V100 for 40B across two nodes. Also \(t\) must divide the heads, and with GQA \(t\) should not exceed the KV-head count.

Core Derive the pipeline bubble fraction. How do you reduce it?

With \(p\) stages, \(m\) micro-batches, forward time \(t_f\) and backward time \(t_b\) per stage per micro-batch, GPipe (all forwards, then all backwards) needs \(p-1\) extra steps to fill and \(p-1\) to drain: \(T = (m+p-1)(t_f+t_b)\). Ideal is \(m(t_f+t_b)\), so the bubble is \((p-1)(t_f+t_b)\): \(\tfrac{p-1}{m}\) of ideal time, or \(\tfrac{p-1}{m+p-1}\) of wall-clock time. For \(p = 16\), \(m = 64\): 23.4% and 19.0%.

Reduce it by (1) more micro-batches (\(m \ge 4p\)), limited by \(m = B_{\text{global}}/(N_d b)\); (2) interleaving \(v\) chunks per device: bubble \(\div v\), communication \(\times v\) (\(v = 4\): 5.9%); (3) zero-bubble schedules that split backward into \(B\) and \(W\) and use \(W\) to fill gaps (ZB-H1: one third of the bubble at 1F1B memory; ZB-H2: near zero at about twice the activation memory); (4) DualPipe's bidirectional feeding. 1F1B does not reduce the bubble; it caps in-flight micro-batches at \(p\) instead of \(m\), a memory saving.

Core How does DeepSeek-V3 train in FP8, and what does it keep in higher precision?

All three matmuls of each linear layer (Fprop, Dgrad, Wgrad) run in FP8 E4M3, with BF16 or FP32 outputs. Instead of one scale per tensor, it uses 1×128 tiles for activations and 128×128 blocks for weights, each with its own online-computed scale, so an outlier only damages its own group and E4M3 (3 mantissa bits) can be used for gradients too, in place of the usual E5M2. Hopper tensor cores accumulate FP8 products with only about 14 bits (about 2% error at \(K = 4096\) in their test), so every 128 elements along \(K\) the partial sums are promoted to FP32 on CUDA cores, where the scales are also applied.

Kept in BF16/FP32: embeddings, output head, MoE gating, normalizations, attention operators. Master weights and gradients FP32, Adam moments BF16. Cached activations FP8 (E5M6 for one), MoE dispatch FP8 and combine BF16. Result: relative loss error under 0.25% versus BF16 at about 1T tokens. For comparison, the hybrid recipe (E4M3 forward, E5M2 gradients, per-tensor delayed scaling) keeps one scale per tensor, which is simpler but more outlier-sensitive; V3 notes that the limited Hopper accumulation is still the default in such frameworks.

Core A 32-layer, 4096-wide model with 32 heads trains at sequence length 8192 and micro-batch 1. Estimate activation memory and say how you would reduce it.

Use Korthikanti's per-layer \(sbh(34 + 5as/h)\) bytes with \(sbh = 8192 \cdot 1 \cdot 4096 = 33.55\)M: the factor is \(34 + 5 \cdot 32 \cdot 8192/4096 = 354\), so 11.9 GB per layer and 380 GB for 32 layers, 90% of it from the \(s^2\) attention-score terms. Options:

  • Selective recomputation or a fused attention kernel that never stores scores: factor 34, 1.14 GB per layer, 36.5 GB, for a few percent of FLOPs.
  • Full recomputation: keep each layer's input, \(2sbh\): 2.1 GB, but +33% FLOPs.
  • Tensor parallelism \(t = 8\) with sequence parallelism and selective recomputation: \(34/8 = 4.25\), 4.6 GB per GPU. Tensor parallelism alone leaves \(10 + 24/8 = 13\) because norms and dropouts are replicated; sequence parallelism shards those too at no extra bytes.

Pipeline parallelism does not help: the first stage holds \(p\) micro-batches of \(L/p\) layers, \(L\) layers' worth. Caveat: these constants are for GPT-style blocks (GeLU, 4h MLP, dropout); SwiGLU/GQA shift the 34, and dropping dropout turns the \(5as/h\) into \(2as/h\), but the scaling is unchanged.

Core FSDP (ZeRO-3) sends 1.5× the data of DDP. When does that hurt, and how do you mitigate it?

It hurts when gathers cannot hide behind compute: (1) many micro-batches: with reshard-after-forward, each micro-batch does two all-gathers and a reduce-scatter; Llama-3-8B on 64 GPUs with 8 micro-batches would move about 379 GB per GPU per step (7.6 s at 50 GB/s) against an 8 s step; (2) slow links: collectives span all \(N_d\) ranks, across nodes; (3) small micro-batches or models: too little compute per gathered byte.

Mitigations: keep gathered parameters after forward (Llama 3's variant); hybrid sharding, sharding inside a node over NVLink and replicating across nodes (cross-node traffic falls from 47 GB to about 3.5 GB in the 8B example); prefetching and a rate limiter; bigger micro-batches; ZeRO-1 or ZeRO-2 if states fit; or pipeline parallelism, which shrinks each rank's shard so DP collectives are smaller and once per step.

Core Llama 3 405B uses TP8 × CP × PP16 × DP with FSDP. Why that order, and what changes for 128K context?

[TP, CP, PP, DP] runs from most to least communication-intensive, mapped from fastest to slowest links. TP (per-layer all-reduces) and CP (per-layer all-gathers) need NVLink inside a node. PP sends only activations between stages, tolerable over the network. DP/FSDP does bulk collectives once per step, which prefetching and overlap can hide on the slowest links. Phase 1 is TP8 × PP16 × DP64 = 8,192 GPUs at 43% MFU (430 TFLOP/s per GPU); DP128 on 16,384 GPUs gives 41% because the batch per DP group shrinks.

At 128K one sequence's activations no longer fit, so CP goes from 1 to 16 and DP drops to 8 (TP8 × CP16 × PP16 × DP8 = 16,384), at 38% MFU. Llama 3 uses all-gather CP: \(K\) and \(V\) are small thanks to GQA, attention compute is \(O(S^2)\) against \(O(S)\) communication, and document masks are easy. It cuts the sequence into \(2\,\text{CP}\) chunks and gives rank \(i\) chunks \(i\) and \(2\,\text{CP}-1-i\) to balance causal work.

Core Explain expert parallelism, and why DeepSeek-V3 caps each token at 4 nodes.

Experts live on different GPUs. Each MoE layer does an all-to-all dispatch (tokens travel to their experts' GPUs), expert compute, and an all-to-all combine, twice in forward and twice in backward. Attention and dense parts stay data-parallel; expert gradients reduce only among replicas of the same expert. It is needed because experts are almost all the parameters (654B of 671B in V3) and the cost is bandwidth: per token and selected expert, \(d\) bytes in FP8 out and \(2d\) in BF16 back.

V3's cluster has NVLink at 160 GB/s and InfiniBand at 50 GB/s (3.2×). Limiting each token to at most 4 nodes bounds IB traffic: a token goes once over IB to the GPU with the same in-node index on each target node, then fans out over NVLink (3.2 experts per node on average at no extra NVLink overhead), and 20 SMs suffice to saturate both links. Even so the all-to-all is about as long as the compute, so DualPipe overlaps them. V4 goes further with a fused kernel that splits experts into waves so compute, dispatch and combine pipeline across waves (1.50 to 1.73× measured for inference workloads).

Deep-dive Plan the parallelism for training a 70B dense model on 1,024 H100s with 8K context.

Config (Llama-3-70B): \(L = 80\), \(d = 8192\), 64 heads, 8 KV heads, \(N = 70.55\)B. Batch \(2^{24}\) tokens = 2,048 sequences.

  1. States: \(16N = 1.13\) TB, impossible to replicate.
  2. TP = 8 in the node, with sequence parallelism: 940 MB per layer per micro-batch, 2.1 ms on NVLink versus 13.3 ms compute (16%); 141% over IB, so never wider than a node. At 8K context no context parallelism is needed.
  3. PP = 4 (20 layers per stage): DP \(= 32\), \(m = 2048/32 = 64\), bubble \(3/64 = 4.7\%\) (2.3% with \(v = 2\)); activations cross stage boundaries as 134 MB per micro-batch, 1% of stage compute on IB.
  4. ZeRO-1 over DP = 32: RS + AG of 4.4 GB each per step, 0.17 s of a 17.5 s step.

Memory per GPU: 4.4 (weights) + 4.4 (grads) + 0.8 (ZeRO-1 optimizer) + 22.8 (first-stage activations, \(34\,sbhL/t\) with sequence parallel and selective recompute) = 32.5 GB, plenty of slack. PP = 2 (41 GB) or 1 (59 GB) also fit and remove the bubble, but the DP shard grows 2 to 4× and FSDP-only variants gather 17.6 GB per micro-batch. Estimated time: 17.5 s per step at 40% MFU; 15T tokens would take about 181 days. What I would check on hardware: bubble and stage imbalance (the embedding and LM-head stages: move one layer off the first and last stage, as Llama 3 does), exposed TP traffic, straggler and restart behavior, and whether MFU is near 40% or the bubble or all-reduce is bigger than modeled.

Deep-dive DeepSeek-V3 trains without tensor parallelism. Reconstruct why that works, and what would break for a dense model of the same total size.

Layout: 2,048 GPUs = 16 pipeline stages × 128 GPUs, experts sharded 64 ways (4 per MoE layer per GPU), ZeRO-1. Parameters per GPU: routed experts \(654\text{B}/16/64 = 0.64\)B plus everything else \(17.1\text{B}/16 = 1.07\)B, about 1.7B in total, 31 GB even at 18 B per parameter unsharded. So memory needs no tensor parallelism. Communication is all-to-all (overlapped by DualPipe) and small point-to-point pipeline traffic, not per-layer all-reduces on the critical path, and the expert GEMMs (\(d_e = 2048\)) are already small enough that splitting them would hurt efficiency. Recomputing RMSNorm and MLA up-projections trims activations.

A dense 671B model has none of this. With no expert dimension to absorb 97% of the parameters, PP16 alone leaves \(671\text{B}/16 = 41.9\)B parameters per GPU: bf16 weights and gradients are \(4 \times 41.9 = 168\) GB, and ZeRO-1 over the 128 replicas adds only 3.9 GB, so it does not fit in 80 GB. You would need TP8 as well (5.2B parameters per GPU, 24.9 GB with ZeRO-1 over the remaining 16 replicas), which brings back the per-layer all-reduces (affordable for wide layers, traffic \(\propto 1/h\)), or FSDP gathers of enormous tensors. Sparsity turns a memory problem into an all-to-all bandwidth problem, which DeepSeek solved with node-limited routing, DualPipe and custom kernels.

Deep-dive How do zero-bubble pipeline schedules work? What do they cost?

Split each stage's backward pass into \(B\) (gradient with respect to the input, which the previous stage waits for) and \(W\) (gradient with respect to the weights, needed only by the optimizer). \(F\) and \(B\) keep their cross-stage dependency chain, but \(W\) can run any time after its \(B\) on the same stage, so a scheduler drops \(W\) into would-be bubbles. For a transformer layer \(T_B + T_W = 2T_F\). ZB-H1 starts \(B\) earlier and fills the tail with \(W\): bubble \((p-1)(T_F + T_B - T_W)\), one third of 1F1B's for equal times, at 1F1B's peak memory. ZB-H2 adds warm-up forwards to get near zero bubble but peaks at \(2p-1\) micro-batches of activations. Reported: up to 23% more throughput than 1F1B at similar memory, 31% with more, and bubble rates under 1% in most settings once a search fits the schedule to profiled \(T_F, T_B, T_W\).

Costs: memory (ZB-H2), and the optimizer step. Global gradient-norm clipping and NaN checks synchronize all stages and would rebuild the bubble, so the paper takes an optimistic step, validates afterward and rolls back if needed. DualPipe builds on the \(B\)/\(W\) split (bubble \((PP/2-1)(F\&B + B - 3W)\)) and adds bidirectional feeding with forward/backward overlap to hide expert all-to-alls, at the price of two parameter copies.

Deep-dive The same model and data give different loss curves on an 8-GPU tensor-parallel run and a 512-GPU FSDP plus pipeline run. How do you debug it?

Separate bugs from numerics. Semantics first: same global batch, learning-rate schedule and data order; loss normalized by the global token count (not per-micro-batch or per-rank means, which reweight sequences); dropout RNG seeded correctly per tensor-parallel rank; identical document and padding masks; clipping on the true global norm; sharded optimizer state not dropping padded or unassigned parameters.

Numerics: floating-point addition is not associative, so reduction order matters, and low-precision reductions amplify it. Llama 3 compared loss across parallelism setups and fixed numerical issues by accumulating gradients in FP32 across micro-batches and reduce-scattering in FP32 across data-parallel ranks. DeepSeek-V4 goes to batch-invariant, deterministic kernels so runs can be compared bit for bit. Procedure: from identical weights, run one step in fp32 or fp64 and compare loss, per-layer activations and gradient norms between layouts (the first divergent layer localizes the bug); then repeat in bf16, and if only that diverges, inspect accumulation and reduction precision before touching hyperparameters.

Cheat sheet

  • States: \(16N\) bytes = 2 (bf16 weights) + 2 (grads) + 12 (fp32 master, Adam \(m\), \(v\)). 7B: 112 GB; Llama-3-8B: 128.5 GB. 18 with fp32 grads (Llama 3), about 14 with bf16 moments (V3).
  • ZeRO (\(N_d\) ranks): DDP \(16N\), comm \(2N\). Z1 \(4N + 12N/N_d\), \(2N\). Z2 \(2N + 14N/N_d\), \(2N\). Z3/FSDP \(16N/N_d\), \(3N\) (1.5×), per micro-batch for Z2/Z3 unless parameters stay resident. 7.5B at \(N_d = 64\): 120 / 31.4 / 16.6 / 1.9 GB.
  • Activations per layer: \(sbh(34 + 5as/h)\) bytes, with \(5as/h = 5s/d_h\). TP: \(10 + 24/t + 5as/(ht)\); TP+SP: \(/t\); selective: 34; full: 2. Llama-3-8B, \(s = 8192\): 354 (380 GB) → 34 (36.5 GB) → 2 (2.1 GB). Pipeline does not reduce it.
  • Recompute: full = +33% FLOPs (\(8N\) vs \(6N\)); selective = 1.6 to 2.7%. HFU ≈ 4/3 MFU (full), MFU × (1 + \(s/6h\)) (selective, the paper's Eq. 9).
  • Formats: bf16 = fp32 range, 8 significant bits; fp16 min \(2^{-24}\), needs loss scaling; E4M3 max 448, E5M2 max 57,344, E2M1 max 6. bf16 drops updates below about \(|w|/256\): keep fp32 masters and accumulation.
  • DeepSeek-V3 FP8: E4M3 everywhere, 1×128 activation tiles and 128×128 weight blocks (online scales), FP32 promotion every 128 elements of \(K\), BF16/FP32 for embeddings, head, gating, norms, attention; loss error under 0.25%. V4: FP4 QAT for experts and indexer QK, dequantized to FP8 losslessly.
  • Collectives (ring): all-reduce \(2\frac{n-1}{n}S\); reduce-scatter, all-gather, all-to-all \(\frac{n-1}{n}S\). Links: HBM 3.35 TB/s, NVLink 900 GB/s aggregate, IB 400 Gbps = 50 GB/s per GPU (V3's H800: NVLink 160 vs 50).
  • TP: column then row split, heads split; 2 all-reduces forward + 2 backward per layer; \(8bsh(t-1)/t\) elements; comm/compute \(\approx \tfrac{2}{9}(t-1)C/(B_\ell h)\). 70B layer at \(t = 8\): 16% on NVLink, 141% on IB. SP: same bytes, activations \(/t\).
  • Pipeline: \(T = (m+p-1)(t_f+t_b)\); bubble/ideal \((p-1)/m\), idle \((p-1)/(m+p-1)\): 23.4% / 19.0% at \(p = 16\), \(m = 64\). 1F1B: same bubble, \(p\) in flight. Interleaving: bubble ÷\(v\), comm ×\(v\). ZB-H1: ⅓ bubble. DualPipe: \((PP/2-1)(F\&B+B-3W)\), 2× params.
  • EP / CP: EP = 2 all-to-alls per MoE layer per direction; V3: at most 4 nodes per token, IB then NVLink. CP: ring needs blocks \(\ge F/B\) tokens; Llama 3 all-gathers K, V (GQA), \(2c\) chunks.
  • Layouts: [TP, CP, PP, DP] inner to outer. Llama 3 405B: TP8×PP16×DP64 (8,192 GPUs) 43%; DP128 41%; 128K: TP8×CP16×PP16×DP8 38%. DeepSeek-V3: PP16×EP64×ZeRO-1, no TP, about 1.7B params per GPU. PaLM: 12-way MP × 256-way FSDP, 46.2%.
  • MFU: tokens/s/GPU × (\(6N\) + attention) / peak; H100 989.4 TFLOP/s dense bf16 (1,979 with sparsity). 500K tok/s on 64 H100s, Llama-3-8B: 40.6%. Time \(= 6ND/(G \cdot \text{peak} \cdot \text{MFU})\).
