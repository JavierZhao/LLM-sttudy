Mistral, Gemma, gpt-oss

P1 ~45 min Prereqs: 07 GQA/MQA, 08 MoE, 09 Windows and sinks, 11 Stability tweaks

Three families made three different bets against the same budget: KV-cache bytes per token, FLOPs per token, and stability at scale. Mistral showed how far a sliding window and an open sparse MoE go, then moved to latent attention. Gemma turned local/global layering, QK-norm and distillation into a small-model recipe. OpenAI's gpt-oss packaged banded attention with learned sinks, a 128-expert MoE and 4-bit expert weights so a 117B-parameter model fits on one 80 GB GPU. This page tells each lineage with its reasons and links back to the mechanism pages instead of re-deriving them.

Mistral: cheap inference first, then open MoE, then latent attention

Mistral 7B: a Llama-shaped model with two inference-side changes

Mistral 7B is a Llama-style decoder (RMSNorm pre-norm, SwiGLU, RoPE) with \(d = 4096\), 32 layers, 32 query heads and 8 KV heads of dimension 128, FFN width 14,336 and a 32,000-token vocabulary [Mistral 7B, Tab. 1]. Per layer the attention has \(2 \cdot 4096 \cdot 4096 + 2 \cdot 4096 \cdot 1024 = 41{,}943{,}040\) parameters and the SwiGLU FFN \(3 \cdot 4096 \cdot 14336 = 176{,}160{,}768\). With two norms of 4,096, the 32 layers give \(6{,}979{,}584{,}000\), and untied embeddings (\(2 \cdot 32000 \cdot 4096\)) plus a final norm bring the total to 7,241,732,096, the 7.24B parameters everyone quotes. The paper's contribution is two changes that lower the cost of serving, not training [Mistral 7B, §1]. GQA with 8 KV heads cuts the cache 4× relative to MHA (page 07) and raises the batch you can hold. Sliding window attention 滑动窗口注意力 bounds what each layer reads.

Receptive field. A token at layer \(k\) attends to the previous layer's states at positions \(i-W\) to \(i\). Those states already summarize their own windows, so information moves forward by up to \(W\) positions per layer and, after \(k\) layers, up to \(k \cdot W\) tokens. With \(W = 4096\) and 32 layers the paper quotes "a theoretical attention span of approximately 131K tokens" (\(32 \times 4096 = 131{,}072\)) [Mistral 7B, §2]. This receptive field 感受野 is an upper bound, not a retrieval range: Table 1 lists an 8,192-token context, the paper reports no long-context retrieval test for the 7B, and information passed through many layers is diluted (page 09).

Rolling buffer. Because no layer reads further back than \(W\), the cache can have a fixed size of \(W\) entries per layer, with the keys and values of position \(i\) written to slot \(i \bmod W\) and overwriting the entry that just left the window. The rolling buffer cache 滚动缓冲区缓存 "stops increasing", and on a 32K-token sequence it cuts cache memory 8× "without impacting the model quality" [Mistral 7B, §2] (\(32768 / 4096 = 8\)). RoPE makes this easy: keys are rotated by their absolute position when written, and the attention score depends only on the position difference, so the buffer can stay in slot order and needs no re-rotation.

class RollingKV:
    """Per-layer cache of the last W tokens (keys are stored already RoPE-rotated)."""
    def __init__(self, W, n_kv, d_h):
        self.W, self.n = W, 0
        self.k = torch.zeros(W, n_kv, d_h)
        self.v = torch.zeros(W, n_kv, d_h)

    def append(self, k_t, v_t):                  # (n_kv, d_h) each, for absolute position self.n
        slot = self.n % self.W                   # overwrite the entry that just left the window
        self.k[slot], self.v[slot] = k_t, v_t
        self.n += 1

    def visible(self):                           # softmax is order-invariant, so slot order is fine
        m = min(self.n, self.W)
        return self.k[:m], self.v[:m]

Chunked prefill. A long prompt is pre-filled in chunks, with the window as the chunk size. For each chunk the attention runs over the cache and over the chunk: the chunk sees itself through a causal mask, sees the cache through the sliding window, and sees nothing older [Mistral 7B, §2, Fig. 3]. This is the end-aligned banded mask of the drill below, and the same idea that serving systems later generalized as chunked prefill (page 17). For a 16K sequence with \(W = 4096\) the authors report a 2× speed-up over vanilla attention after changes to FlashAttention and xFormers.

Sliding window with a rolling buffer (Mistral 7B)
Problem
Full attention makes prefill cost grow as \(T^2\) and the KV cache as \(T\). At 128 KiB per token (GQA-8, bf16) a long sequence quickly dominates memory and limits batch size.
Idea
Each layer attends to the last \(W = 4096\) tokens only. The cache is a ring buffer of \(W\) entries per layer, and the prompt is pre-filled in chunks of \(W\).
Why it works
Most of what a language model needs is local, and stacked layers pass information forward \(W - 1\) positions per layer, so depth restores some long-range reach. Decode cost per token becomes constant in \(T\).
Evidence
2× speed at 16K, cache 8× smaller at 32K, "without impacting the model quality" [Mistral 7B, §2]. The paper contains no window ablation and no long-context retrieval test for the 7B.
Cost
The 131K span is a bound. Exact retrieval beyond \(W\) depends on depth and degrades. A ring buffer also discards the early part of the sequence, which conflicts with sharing a cached prefix across requests (my inference; page 17).
Used by
Mistral 7B v0.1. Later hybrids keep a few global layers and window the rest: Gemma 2, 3, 4 and gpt-oss (below, page 09).

Worked number. One token costs \(32 \cdot 2 \cdot 8 \cdot 128 \cdot 2 = 131{,}072\) B = 128 KiB (page 07). The rolling buffer holds \(4096 \times 128\) KiB = 512 MiB per sequence, flat for any \(T \ge 4096\). A full cache at 32K would be 4 GiB (8×), at 128K it would be 16 GiB (32×).

What Mistral did next with the window

Every later Mistral config I checked sets sliding_window to null: 7B v0.2 (which also raised rope_theta from 10,000 to 1,000,000), Mixtral 8x22B, Mistral Small 3, Mistral Large 3 and Small 4 (table below). Mistral gave no reason. Plausible readings, all inference: exact retrieval at 32K to 128K wants global layers (page 09); cache pressure was attacked with other tools (GQA-8, later MLA); and pure windows are awkward for prefix caching. The hybrid that Gemma and gpt-oss ship keeps the saving and the global layers.

Mixtral: the same backbone with a sparse FFN

Mixtral 8x7B keeps Mistral 7B's attention (32 layers, 32/8 heads, GQA) and replaces every FFN with eight SwiGLU experts 混合专家 of the same width, 14,336. A linear router picks two per token and the outputs are mixed with a softmax over the two selected logits [Mixtral, §2.1]:

\[ y = \sum_{i=0}^{7} \operatorname{Softmax}\!\big(\operatorname{Top2}(x W_g)\big)_i \cdot \operatorname{SwiGLU}_i(x) \]

The result has 47B parameters of which 13B are active per token (my count from the config: 46.70B and 12.88B, page 08), a fully dense 32K context and no sliding window. Table 2 of the paper compares it to Llama 2 70B, which has 5× more active parameters: MMLU 70.6 vs 69.9, HumanEval 40.2 vs 29.3, MATH 28.4 vs 13.8, GSM8K 74.4 vs 69.6. Those are the authors' own re-runs on their pipeline. Mixtral 8x22B scales the same recipe: 56 layers, \(d = 6144\), 48 query and 8 KV heads, expert width 16,384, 64K context, 141B total and 39B active [Mistral, 17 Apr 2024]. The config gives 140.62B and 39.15B by my count (\(56 \cdot 8 \cdot 3 \cdot 6144 \cdot 16384 = 135.3\)B in experts, 4.9B attention, 0.4B embeddings).

The routing analysis (§5) is the part interviewers like, because it corrects a common belief. On subsets of The Pile, the distribution of selected experts at layers 0, 15 and 31 is "very similar" for ArXiv, PubMed abstracts and PhilPapers: no obvious topic specialization, with only DM Mathematics slightly different. What the router does track is syntax: 'self' in Python, 'Question' in English and indentation tokens tend to go to the same expert. And consecutive tokens repeat their expert far more than chance in the deeper layers. The chance level for the same first-choice expert is 1/8 = 12.5%; the measured rate is 13.6 to 14.9% at layer 0, 23.6 to 28.4% at layer 15 and 19.7 to 26.3% at layer 31, depending on the domain [Mixtral, §5, Tab. 5]. The authors draw two consequences: temporal locality makes some experts over-subscribed under expert parallelism, and it can be exploited for caching or offloading.

Coarse open top-2 MoE (Mixtral)
Problem
Dense 70B quality costs 70B parameters of compute per token. Serving cost, not training cost, was the target.
Idea
Eight full-size FFN experts per layer, two active per token, with everything else identical to Mistral 7B.
Why it works
Capacity (47B) grows with the number of experts while per-token FLOPs grow only with \(k = 2\) (13B active). The router needs no topic structure to be useful; it learns token-level and syntactic patterns.
Evidence
Matches or beats Llama 2 70B and GPT-3.5 on most benchmarks with 5× fewer active parameters [Mixtral, Tab. 2-3].
Cost
All 47B parameters must be resident: 93.4 GB in bf16, more than one 80 GB GPU, and at large batch nearly every expert is read each step (page 08). Eight coarse experts give the router fewer combinations than DeepSeekMoE's fine-grained design (page 26). The paper gives no token count and does not say whether the experts were initialized from the dense model.
Used by
Mixtral 8x7B and 8x22B. Mistral's later MoEs moved to 128 routed experts (table below).

Magistral: a reasoning model from a home-built RL stack

The one recent Mistral paper with method detail is Magistral (June 2025). Magistral Medium is trained on top of Mistral Medium 3 "with RL alone", with no distillation from an existing reasoning model, and lifts AIME-24 pass@1 from 26.8 to 73.6 (majority-of-64: 43.4 to 90.0). Magistral Small (24B, Apache 2.0) starts from SFT on Magistral Medium's traces and then runs RL, reaching 70.7 against 65.4 for SFT alone and 65.8 for RL alone [Magistral, Tab. 2-3]. The GRPO changes are the standard list of that year (page 24): drop the KL term, normalize the loss by total tokens in the group, normalize advantages per minibatch, raise the upper clip (\(\varepsilon_{\text{high}}\) between 0.26 and 0.28), and drop groups with zero advantage. Rewards cover format, correctness, length and language consistency. The asynchronous design lets generators keep sampling while trainers push new weights over NCCL, without discarding in-flight sequences (page 25). Text-only RL kept or improved multimodal and function-calling ability [Magistral, §3, §7].

Gemma: Gemini's recipe, distilled into small open models

Gemma is Google DeepMind's line of open models "built from the research and technology used to create Gemini" [Gemma, abstract]. Three habits run through the generations: a large Gemini vocabulary (256K entries, 262K from Gemma 3), a head dimension of 256 or 128 that is decoupled from \(d/n_h\), and tied input and output embeddings (in the versions whose configs I checked: Gemma 1, 2 and 4) with the input scaled by \(\sqrt{d}\). The code multiplies the embedding lookup by \(\sqrt{d_{\text{model}}}\) (embed_scale = hidden_size ** 0.5 in the Hugging Face implementations of Gemma 2 and 3). This is the "keep the shortcut large" trick of page 11: with tied embeddings the table is trained at a scale suited to the output logits, and rescaling gives the first layers a residual stream of order one. What changed between generations is mostly attention.

Every choice in Gemma 2 has a stated purpose in the report, and it is worth knowing them as a list.

  • Local/global alternation 局部注意力 / 全局注意力: "we alternate between a local sliding window attention and global attention in every other layer", window 4,096, global span 8,192 [Gemma 2, §2]. The Hugging Face config builds the layer types as sliding for even indices and full for odd, so layer 0 is local. Since the context is only 8,192, the global layers are ordinary full attention here and the saving is modest. The report's ablation (Tab. 10) shows why the window could shrink later: cutting the 9B's window at inference from 4,096 to 2,048 to 1,024 moved validation perplexity from 1.63 to 1.63 to 1.64.
  • Logit soft-capping: \(\operatorname{softcap}(z) = c \tanh(z/c)\) with \(c = 50\) on attention logits and \(c = 30\) on the final logits [Gemma 2, §2]. It bounds the range of each logit to \((-c, c)\), a stability device analyzed on page 11.
  • Pre and post norms: RMSNorm "to normalize the input and output of each transformer sub-layer", so four norms per layer (the sandwich layout of page 11).
  • GQA with two query heads per KV head "based on ablations showing increased speed at inference time while maintaining downstream performance" (9B, 4 benchmarks: MHA 50.3, GQA 50.8, Tab. 8). Deeper rather than wider: at 9B parameters a deeper network scored 52.0 against 50.8 (Tab. 9), which is why the 9B has 42 layers.

Knowledge distillation as a way to buy tokens

The report's argument starts from a diagnosis: small models are still under-trained, but simply training them longer "only scales logarithmically with dataset size", and the latest small models need up to 15T tokens for gains of under 1 to 2% [Gemma 2, §1]. Instead of more tokens, they change the target. With a larger model as teacher, the student minimizes

\[ \mathcal{L} = -\sum_{x} P_T(x \mid x_c)\,\log P_S(x \mid x_c) \]

at every position, "instead of the next token prediction" with a one-hot target. The gradient with respect to the student's logits is \(P_S - P_T\) rather than \(P_S - \mathbb{1}_{\text{next}}\): every one of the 256K vocabulary entries receives a graded signal at every position, including the plausible alternatives that the corpus did not happen to contain. In the report's words, knowledge distillation 知识蒸馏 lets them "simulate training beyond the number of available tokens": the 2B and 9B were trained on a quantity of tokens "more than 50× the compute-optimal quantity". With the rule of thumb of 20 tokens per parameter I get 38× for the 2B (2T tokens on 2.61B parameters) and 43× for the 9B, so the report must be using a fitted optimum that is smaller at small scale. The order of magnitude, 40 to 50× beyond Chinchilla, is the point.

Distillation during pretraining (Gemma 2, 3)
Problem
A small model trained far past its compute-optimal token count still improves, but only logarithmically, and unique tokens run out.
Idea
Train the student on the teacher's next-token distribution over ordinary text, for many tokens, instead of on one-hot labels.
Why it works
Each position supplies a full distribution (a richer target and a lower-variance gradient) rather than one sampled token, so each token teaches more.
Evidence
A 2B student trained on 500B tokens averages 67.7 over three benchmarks when distilled from a 7B teacher against 60.3 from scratch. Validation perplexity improves at every size: 23 to 21, 19 to 17, 17 to 15 for 200M, 400M and 1B students [Gemma 2, Tab. 6-7]. The Gemma 2 2B (2T tokens, distilled) also beats the Gemma 1 2B (3T tokens) by a wide margin, though architecture and data changed too.
Cost
A teacher forward pass per training token. With the usual \(6N\) FLOPs per token for the student and \(2N_T\) for the teacher, a 9B student with a hypothetical 27B teacher costs \(54 + 54 = 108\) GFLOPs per token, twice plain training (illustrative: the report names no teacher and does not say whether logits are precomputed). The ablations use a 7B teacher for a 2B student, which is not the production setup.
Used by
Gemma 2 (2B, 9B), all Gemma 3 models, and in post-training the "distillation from the teacher on the student's distribution" of Gemma 2's SFT stage. See page 19.

Gemma 2 post-training also uses the teacher: SFT on responses "predominantly synthetically generated by the teacher" plus on-policy distillation, then RLHF and averaging of models from different hyperparameter runs [Gemma 2, §4]. Distillation in pretraining is not training on the teacher's generated text: the corpus is fixed, and only the target changes.

QK-norm in place of soft-capping (Gemma 3)
Problem
Attention logits \(x W_q W_k^\top x^\top\) are bilinear in the weights and can grow without limit (page 11). Gemma 2 capped them with \(50 \tanh(z/50)\).
Idea
RMS-normalize each query and key per head (over \(d_h\)) before RoPE, with a learned gain, and drop the cap. The report: "we replace the soft-capping of Gemma 2 with QK-norm", citing ViT-22B, Wortsman et al. and Chameleon [Gemma 3, §2].
Why it works
With unit-RMS \(q, k\) the logit satisfies \(|z| \le g^2 \sqrt{d_h}\) for any weights, so sharpness can only grow through \(d_h\) gain scalars. A cap only bounds range: with cap 50, one key at 50 among 8,191 zeros is still a one-hot row, and past the cap the gradient of \(\tanh\) vanishes (page 11 computes both). A cap also adds a \(\tanh\) inside every attention score, which fused kernels had to learn to support (FlashAttention added a softcap argument in v2.6, README changelog).
Evidence
The Gemma 3 report gives no Gemma-specific ablation, only the citations, so the case rests on the external results (ViT-22B diverging at 8B parameters without it; Wortsman et al.'s small-proxy studies).
Cost
Two per-head norms per attention layer (\(2 d_h\) gains), and QK-norm needs materialized keys, which is why it cannot be applied to absorbed MLA (page 11). Gemma 4's released config keeps final_logit_softcapping = 30 (official 31B config) while Gemma 3's has it unset, so the final cap has returned; the attention cap has not.
Used by
Gemma 3 and 4, OLMo 2, Qwen3, DeepSeek-V4 (page 11).

Distillation in Gemma 3 is a sampled version of the loss above: "we sample 256 logits per token, weighted by teacher probabilities", the student "learns the teacher's distribution within these samples via cross-entropy", and the target is zero for non-sampled entries and renormalized [Gemma 3, §2.2]. Storing 256 of 262,144 entries per token is a 1,024× reduction in target size relative to the full distribution. The report does not say whether these targets are precomputed or produced by a live teacher. Post-training is a different recipe, with distillation from a larger instruction-tuned teacher plus RL (page 19).

Vision and Gemma 3n. The multimodal 4B, 12B and 27B share one frozen 400M SigLIP encoder that condenses an 896×896 image into 256 soft tokens, with a Pan and Scan crop scheme applied at inference for other aspect ratios. Gemma 3n (June 2025) targets phones: a MatFormer design in which a 2B-effective (E2B) model is trained nested inside the 4B-effective (E4B) one, per-layer embeddings that can be loaded and computed on the CPU (E2B has 5B raw parameters but about 2B in accelerator memory), and KV sharing in which the middle layer's keys and values are shared with the top layers for a "2x improvement on prefill performance" [Google, Gemma 3n developer guide]. Those per-layer embeddings return in Gemma 4's smallest models.

Worked numbers: Gemma 3 27B at 128K

From the released config of Gemma 3 27B (a public mirror of Google's file): 62 layers, 32 query heads, 16 KV heads, head dimension 128, window 1,024, sliding_window_pattern 6. The layer types follow (i + 1) % 6 == 0 for global, so global layers sit at indices 5, 11, ..., 59: ten global and 52 local. Per layer per token the cache holds \(2 \cdot 16 \cdot 128 = 4096\) numbers, which is 8,192 B = 8 KiB in bf16 for either layer type. At \(T = 131{,}072\) a global layer holds \(8\text{ KiB} \times 2^{17} = 1\) GiB and a local layer \(8\text{ KiB} \times 1024 = 8\) MiB.

Weights in bf16 are \(27.0\text{B} \times 2 = 54\) GB = 50.3 GiB, so on an 80 GB GPU (74.5 GiB) an all-global 128K sequence needs \(50.3 + 62 = 112\) GiB and does not fit, while the hybrid needs 60.7 GiB and leaves room for two such sequences (\(50.3 + 2 \times 10.41 = 71.1\) GiB, before activations and framework overhead). Gemma 4 (April 2026): sharing K and V, shrinking global heads, and a MoE

Google released Gemma 4 on 2 April 2026 under Apache 2.0, where Gemma 1 to 3n shipped under the custom Gemma Terms of Use. The technical report (June 2026, revised July) lists dense models with effective 2.3B (E2B) and 4.5B (E4B) parameters, a 12B, a 31B, and a 26B mixture of experts with 3.8B activated (26B-A4B) [Gemma 4, §1-2]. The E2B and E4B use per-layer embeddings, so their totals are 5B and 8B; the 12B is trained from scratch "encoder-free", projecting raw 40 ms audio chunks and 48×48 image patches into the embedding space. The model card gives layers, windows and contexts: E2B 35 layers, window 512, 128K; E4B 42 layers, 512, 128K; 12B 48 layers, 1,024, 256K; 31B 60 layers, 1,024, 256K; 26B-A4B 30 layers, 256K [Gemma 4 model card].

Attention. The 5:1 interleave stays (4:1 for E2B) and, per the model card, the last layer is always global. The KV changes are the news. Global layers use keys as values, "values = keys", except in E2B and E4B, with position handled by p-RoPE at \(p = 0.25\) (only a quarter of the dimensions are rotated) on global layers and ordinary RoPE on local ones, at bases 1M and 10K. E2B and E4B also share the KV cache across layers, with ratios given as 20/35 and 18/42. Together the report says these "reduce the global KV cache footprint by up to 37.5%" [Gemma 4, §1, §2]. The official 31B config.json shows the shapes: local layers have 16 KV heads of dimension 256, global layers only 4 KV heads of dimension 512 with attention_k_eq_v true. The report does not explain how a shared K=V tensor treats the rotated dimensions of the value, nor how it arrives at 37.5%. (DeepSeek-V4 solved the analogous problem by counter-rotating the attention output, page 07.)

Check against the report's own table. Per token per layer, a local layer caches \(2 \cdot 16 \cdot 256 = 8192\) numbers and a global layer \(4 \cdot 512 = 2048\) (one tensor). The 60 layers have global layers at 5, 11, ..., 59. At \(T = 32{,}768\) with an int8 cache that is \(50 \cdot 8192 \cdot 1024 + 10 \cdot 2048 \cdot 32768 = 419.4\text{M} + 671.1\text{M} = 1.0905\) GB, against +1.10 GB in the report's Table 3. If V were stored separately the global term would double and the total would be 1.76 GB, so the table supports the K=V reading. At 128K in bf16 the same arithmetic gives \(50 \cdot 16\text{ KiB} \cdot 1024 = 800\) MiB local plus \(10 \cdot 4\text{ KiB} \cdot 131072 = 5\) GiB global: 5.78 GiB, against 10.41 GiB for Gemma 3 27B and 62 GiB for an all-global model of that shape. At 256K the global term doubles to 10 GiB.

Stability, norms, MoE. The layers use pre-norm and post-norm RMSNorm plus QK-norm [Gemma 4, §2], and the 31B config also sets a final-logit cap of 30. The 26B-A4B has 128 experts with 8 active plus 1 shared per token (model card). A public mirror of its config gives 30 layers, \(d = 2816\), expert width 704 and a dense 2,112-wide MLP that plays the shared role. My arithmetic from it: experts \(30 \cdot 128 \cdot 3 \cdot 2816 \cdot 704 = 22.84\)B, dense MLPs 0.53B, attention (5 global layers with 2 KV heads of 512, 25 local with 8 of 256) 1.12B, plus the tied 0.74B embedding table, totals 25.23B; active parameters are \(30 \cdot 8 \cdot 3 \cdot 2816 \cdot 704 = 1.43\)B of experts plus everything else, 3.82B. Both match the reported 25.2B and 3.8B, which suggests that Google's "activated" count includes the embedding table (gpt-oss counts only the unembedding), a convention worth checking whenever active-parameter counts are compared. Compared with Mixtral this is the DeepSeekMoE design of page 08: many small experts (704 wide, top-8) plus an always-on shared MLP.

Everything else in one paragraph. Pretraining is described only as "similar" to Gemma 3's (data cutoff January 2025, 262K SentencePiece vocabulary); the report gives no token count and restates nothing about distillation. Post-training adds a thinking mode switched on by a <|think|> token in the system turn, with reasoning in a <|channel>thought block (page 19 lists the template). The MTP drafter is a 4-layer block with its own embedder that cross-attends to the main model's KV cache, so it needs no prefill and supports any draft length (page 17). Quantization-aware checkpoints ship in Q4_0 and mobile formats. On long context, RULER at 128K (no thinking) is 96.4 for the 31B against 66.0 for Gemma 3 27B, and LOFT text retrieval at 128K is 79.5 against 8.6 (Tab. 9). Arena Text Elo on 19 June 2026 was 1451 for the 31B and 1438 for the 26B-A4B against 1366 for Gemma 3 27B (Tab. 4); these are human-preference scores reported by the authors. Attention: banded and dense layers, GQA, YaRN

"Following GPT-3, attention blocks alternate between banded window and fully dense patterns, where the bandwidth is 128 tokens", with 64 query heads of dimension 64 and GQA with 8 KV heads, RoPE, and YaRN extending "the context length of dense layers to 131,072 tokens" [gpt-oss model card, §2.2]. The config makes layer 0 banded, layer 1 dense, and so on (Figure 1), so the ratio is 1:1 like Gemma 2 but with a window of 128, eight times narrower than Gemma 3's. The reason to alternate is the cost split of page 09: a banded layer costs \(O(T \cdot 128)\) in FLOPs and a constant 128 entries in cache, while a dense layer supplies exact long-range recall. With only 128 tokens in the window, long-range work falls almost entirely on the 18 dense layers, which puts more weight on the global layers than a 1,024-token window would. That is the setting where MiMo's ablation found sinks to be load-bearing (page 09).

Learned attention sinks

The card's sentence is: "Each attention head has a learned bias in the denominator of the softmax, similar to off-by-one attention and attention sinks, which enables the attention mechanism to pay no attention to any tokens" [gpt-oss model card, §2.2]. Concretely, each head \(h\) in each layer owns one scalar \(z^{(h)}\), and its attention weights are

\[ p_{t,j} = \frac{\exp(s_{t,j})}{\sum_{k \le t} \exp(s_{t,k}) + \exp(z)}, \qquad o_t = \sum_{j \le t} p_{t,j}\, v_j \]

The sink appears only in the denominator. It is a fictitious key with a zero value vector, so the real weights sum to \(1 - p_{\text{sink}} < 1\), and a head with nothing to read can send its mass to the sink and output almost nothing. In the released Hugging Face code the sink is an nn.Parameter of shape (num_attention_heads,) in each attention module, so 64 scalars per layer, 2,304 in the whole 120b, and the eager path is:

sinks = module.sinks.reshape(1, -1, 1, 1).expand(B, n_h, T, 1)      # one logit per head
logits = torch.cat([attn_weights, sinks], dim=-1)                   # (B, n_h, T, S + 1)
probs = torch.softmax(logits - logits.max(-1, keepdim=True).values, dim=-1)
scores = probs[..., :-1]                                            # drop the sink column: rows now sum to < 1
out = scores @ v

Why a logit and not a token. Softmax weights must sum to one, so a head with no relevant key still has to put mass somewhere. Trained models dump it on the first tokens, which every later query can see [StreamingLLM, §3.1]; evicting those tokens in a sliding window sends Llama-2-13B's perplexity from 5.40 (4 sink tokens + 1,020 recent) to 5,158 (a plain 1,024 window), and replacing the four tokens with newlines still gives 5.60, so what matters is position and visibility, not content (Tab. 1; page 09). StreamingLLM's own fix for new models is a dedicated learnable sink token, but that has a catch. In the 160M-parameter pretraining runs, the model with a sink token scored 18.01 with the token kept in the cache and 1,235 without it (Tab. 3), so the token must be pinned in the KV cache forever. Softmax-off-by-one, \(\operatorname{softmax}_1(x)_i = e^{x_i} / (1 + \sum_j e^{x_j})\), is a fixed zero sink ("equivalent to prepending a token with an all-zero Key and Value"), and by itself it did not remove the model's reliance on other initial tokens (29,214 without them). A learned per-head logit inside the softmax has no cache entry to lose, works the same in dense and banded layers, and costs 2,304 parameters. For banded layers there is one more reason (my inference): after 128 positions the first token is outside every window, so a token-based sink would need special cache handling in exactly the layers that have the smallest cache.

Two useful identities. Write \(Z_t = \sum_k e^{s_{t,k}}\) and \(\mathrm{LSE}_t = \log Z_t\). The sink is a sigmoid gate on the head output, because \(Z / (Z + e^z) = \sigma(\mathrm{LSE} - z)\):

\[ o^{\text{sink}}_t = o^{\text{plain}}_t \cdot \sigma\!\big(\mathrm{LSE}_t - z\big), \qquad \frac{\partial \mathcal{L}}{\partial z} = -\sum_t p_{\text{sink},t}\, \langle dO_t,\, O_t\rangle \]

The first identity says a FlashAttention-style kernel does not need to change its tiled loop: it already produces the row-wise log-sum-exp, and the sink is an epilogue that rescales each output row (page 16). The second, which I verified numerically against autograd, says the sink's gradient reuses the \(D_t = \langle dO_t, O_t\rangle\) term of the flash backward pass, so it costs one more row reduction. The drill checks the forward identity. This is also why sinks connect to gated attention (page 11): a per-head, input-dependent gate is the same family, and the sink is its cheapest member.

Learned per-head sink logits (gpt-oss)
Problem
Softmax forces each head to distribute unit mass even when no key is relevant. Models park it on early tokens, and windowed inference that evicts them breaks the model.
Idea
Add one learned scalar per head to the softmax denominator (a zero-valued key), trained from the start with the rest of the model.
Why it works
The head gets an explicit place for surplus mass, so it does not need to repurpose real tokens as dumps, and it can output nearly zero. It is available at every position and needs no cache entry.
Evidence
The card states the design and gives no ablation. Independent evidence: in MiMo-V2-Flash's 32B ablation a 128-token window without a sink loses 2.4 MMLU points against all-global (54.9 vs 57.3) and with a sink reaches 58.3 (page 09); StreamingLLM's Tab. 3 shows the token variant works but must stay in cache.
Cost
2,304 parameters and one row-wise rescale. Kernels need to support it. No fixed relation to the scores: \(z\) is per head and layer, not per query.
Used by
gpt-oss, MiMo-V2-Flash and DeepSeek-V4 (page 09). Gemma 3 and 4 have no sink; their global layers keep the full context visible.

The MoE block

Every one of the 36 layers is MoE (there is no dense prefix and no shared expert). A linear router scores the 128 experts, the top 4 are kept and the mixing weights are a softmax over only those four logits, the same rule as Mixtral [gpt-oss model card, §2.2] (page 08). The expert is a gated SwiGLU whose card footnote calls it "unconventional, including clamping and a residual connection". In the released code the gate is clamped from above at 7.0, the linear branch to \([-7, 7]\), and the output is \((\text{up} + 1) \cdot \text{gate}\cdot\sigma(1.702 \cdot \text{gate})\), with biases on the fused gate-up and down projections (my count reproduces the card's 114.71B only with them). The card does not say why the clamp is there; bounded activations are the plausible motive given the 4-bit weights, but that is my reading. What the card leaves out is any statement of balancing method, token count or expert-width ablation.

MXFP4 experts: how 117B parameters fit on one GPU

"We post-trained the models with quantization of the MoE weights to MXFP4 format, where weights are quantized to 4.25 bits per parameter. The MoE weights are responsible for 90+% of the total parameter count, and quantizing these to MXFP4 enables the larger model to fit on a single 80GB GPU and the smaller model to run on systems with as little as 16GB memory" [gpt-oss model card, §2.1]. MXFP4 is the 4-bit member of the OCP microscaling family 微缩放: blocks of 32 values share one power-of-two scale (E8M0, 8 bits) and each value is an E2M1 float (sign, 2 exponent bits, 1 mantissa bit) [Rouhani et al. 2023, Tab. 1]. Conversion follows Algorithm 1 of that paper: \(X = 2^{\lfloor \log_2 \max_i |v_i| \rfloor - 2}\), because 2 is the exponent of E2M1's largest value 6, then each \(v_i / X\) is rounded to the nearest representable magnitude (0, 0.5, 1, 1.5, 2, 3, 4, 6) with normal-range overflow clamped to 6 (page 15 and page 17 cover MX and NVFP4 in depth). Cost per weight: \((32 \cdot 4 + 8)/32 = 4.25\) bits.

Worked numbers. Experts: \(114.71\text{B} \times 4.25/8 = 60.94\) GB = 56.75 GiB. The BF16 remainder (attention 0.96B plus embedding and unembedding 1.16B) is \(2.12\text{B} \times 2 = 4.24\) GB = 3.95 GiB. Total 60.70 GiB against the card's 60.8 (routers, norms and biases account for the rest), an average of 4.46 bits per parameter and 3.58× less than the 217.6 GiB (233.7 GB) of BF16. The released config confirms the split: modules_to_not_convert lists the attention blocks, the router, the embedding and lm_head. On an 80 GB GPU, 74.5 GiB, that leaves 13.8 GiB for the KV cache and activations, and one 128K sequence needs 4.5 GiB (below), so a few long sequences fit and a BF16 copy would need three GPUs. The same calculation for the 20b gives 12.81 GiB (card: 12.8).

def weight_bytes_mxfp4(n_mx, n_bf16, block=32, scale_bits=8, elem_bits=4):
    return n_mx * (elem_bits + scale_bits / block) / 8 + n_bf16 * 2

weight_bytes_mxfp4(114.71e9, 0.96e9 + 1.16e9) / 2**30     # 60.70 GiB (card: 60.8)

The accuracy risk. A 4-bit float grid is coarse: the worst relative rounding error is about 20% in most bins (33% in the 0.5 to 1 bin), values below a quarter of the scale flush to zero, and because the scale is a power of two a block maximum in \([6, 8)\cdot X\) is clamped to 6, an error up to 25%. One large weight in a block therefore sets the scale and can erase its small neighbors. The microscaling paper's direct-cast numbers show the size of the effect on LLaMA-7B: wikitext perplexity is 9.49 in FP32, 11.48 with MXFP4 weights and MXFP8 activations, 11.15 with MXFP6 activations, and 27.20 with MXFP4 on both [Rouhani et al., Tab. 6]. Three things reduce the risk for gpt-oss. Only weights are 4-bit, and activations stay in BF16. The model was post-trained with the quantization in the loop, so it adapts to its own rounding (the card says "post-trained the models with quantization"). And the fragile tensors, attention and router, stay in BF16. What the card does not publish is a BF16-versus-MXFP4 quality comparison, so the residual loss is unquantified. Decode being bandwidth-bound, 3.58× fewer weight bytes speeds up token generation; matmul FLOPs are not reduced on hardware that lacks FP4 tensor cores, where weights are dequantized inside the kernel (page 17).

Tokenizer, the harmony format and reasoning effort

The tokenizer is o200k_harmony, a byte-level BPE with 201,088 tokens that extends the o200k vocabulary of GPT-4o and o4-mini with tokens for the harmony chat format [gpt-oss model card, §2.3]. A message is <|start|>{header}<|message|>{content}<|end|>. Roles are system, developer, user, assistant and tool, with the instruction hierarchy System > Developer > User > Assistant > Tool. The new idea is channels that mark visibility: analysis carries chain of thought, commentary function calls and preambles, final the answer shown to the user [harmony spec]:

<|start|>user<|message|>What is 2 + 2?<|end|>
<|start|>assistant
<|channel|>analysis<|message|>User asks: "What is 2 + 2?" Simple arithmetic. Provide answer.<|end|>
<|start|>assistant<|channel|>final<|message|>2 + 2 = 4.<|return|>

Generation stops at <|return|> (token 200002, the config's eos_token_id) or <|call|> (200012) for a tool call. The card warns that the format "is critical to deploy our gpt-oss models properly", and that in multi-turn use the reasoning traces of past assistant turns "should be removed" (the spec: drop them once the assistant has answered on the final channel). This is a template-mismatch failure mode of page 19 with higher stakes, because the model interleaves reasoning, tool calls and answers within one turn. Reasoning effort is a training-time behavior, not a decoding trick: the models are trained to support low, medium and high, set by a line such as "Reasoning: high" in the system prompt, and longer chains of thought raise accuracy with "smooth test-time scaling" and "log-linear returns on most tasks" (§2.5.2, §2.6.1; page 24). For AIME 2025 without tools, gpt-oss-120b scores 50.4, 80.0 and 92.5 at low, medium and high, and the 20b scores 37.1, 72.1 and 91.7; GPQA Diamond for the 120b is 67.1, 73.1 and 80.1 (Tab. 3).

What the card says about training, and what it does not

Pretraining is on "a text-only dataset with trillions of tokens, with a focus on STEM, coding, and general knowledge", with CBRN filters reused from GPT-4o and a knowledge cutoff of June 2024. Post-training uses "similar CoT RL techniques as OpenAI o3", covering reasoning, tool use (browsing, a stateful Python tool, developer functions) and safety by deliberative alignment. The 120b took 2.1 million H100-hours and the 20b almost 10× fewer (§2.4). Nothing is said about distillation, token counts, batch size or the reason for 128 experts with top-4. A back-of-envelope check of what 2.1M H100-hours could buy (my estimate, an upper bound since it includes post-training): at a 30% MFU, \(2.1\times10^6 \cdot 3600\ \text{s} \cdot 989\ \text{TFLOP/s} \cdot 0.3 = 2.2\times10^{24}\) FLOPs, and with \(C \approx 6 N_{\text{act}} D\) and \(N_{\text{act}} = 5.13\)B that is \(D \lesssim 73\)T tokens. The card also states that no direct optimization pressure was put on the chain of thought, so that it can be monitored, which means the analysis channel can contain unfiltered or hallucinated text and should not be shown to users without moderation.

Total 4.50 GiB, against 9.0 GiB if every layer were dense. The cache is 4.5 GiB per sequence for a model whose weights take 60.7 GiB, so on one GPU long-context serving is limited by the weights, not by the cache.

What converged, and what did not

  • KV bytes per token is the shared target, attacked on different axes. GQA-8 is the baseline everywhere. Gemma and gpt-oss cut the token axis (local layers cap at a window), Mistral Large 3 and Small 4 cut the feature axis with MLA, Gemma 4 cuts features again in global layers (K=V, fewer and wider heads). These stack, as page 07 noted for DeepSeek.
  • Short-window hybrids became the open dense-model default, after Mistral's all-window design was abandoned. The two shipped hybrids differ sharply: Gemma 3 and 4 keep one global layer in six with a 1,024 window, gpt-oss keeps one in two with a 128 window. Per-layer cache size matters as much as the ratio: gpt-oss caches 1,024 numbers per token per layer, Gemma 3 27B 4,096.
  • Stability tools solve different problems. QK-norm (Gemma 3, 4) bounds the growth of logits. Sinks (gpt-oss) give surplus softmax mass a home. Soft-capping bounded the range only. They are complementary: the Gemma reports do not mention sinks, and the gpt-oss card does not mention QK-norm.
  • MoE moved from 8 coarse experts to 128 small ones. Mixtral: 8, top-2. Large 3, Small 4, gpt-oss and Gemma 4's 26B-A4B: 128 with top-4, 4 and 8, and a shared expert in Mistral 3 and 4 and in Gemma 4 but not in gpt-oss.
  • Low-precision weights became a release format. gpt-oss was post-trained for MXFP4 experts, Gemma ships QAT checkpoints (Gemma 3: int4 and switched fp8; Gemma 4: Q4_0 and mobile formats), Mistral announced an NVFP4 checkpoint of Large 3 (page 17).
  • Disclosure differs. gpt-oss and the Gemma reports give architectures precisely and few training details. Mistral gives least since Mixtral. Any "why" for Mistral's changes is inference.

Choosing the local:global ratio and the window

Take \(r\) local layers per global layer, window \(W\) and context \(T\). Relative to all-global, the KV cache (and the decode-time attention read, and approximately the prefill attention FLOPs) is

\[ f(r) = \frac{1}{r+1} + \frac{r}{r+1}\,\min\!\Big(1, \frac{W}{T}\Big) \]

At \(T = 128\)K and \(W = 1024\), \(W/T = 1/128\), so:

Problem
Pick how many layers get full context and how wide the local window is, under a KV budget at the target context.
Idea
Solve \(f(r)\) for the budget, then choose the smallest global fraction and window that keep long-context evaluations intact after context extension, with sinks if the window is small.
Why it works
Local layers do local mixing at constant cost, and a minority of global layers do exact retrieval. Depth stacks the two.
Evidence
Gemma 3: perplexity is nearly flat from 1:1 to 7:1 and for windows 4,096 down to 512, and at 32K a 2B model's KV overhead falls from 60% (global only) to under 15% (the paper's "1:3" configuration with a 1,024 window) [Gemma 3, §5.2]. Cost
Fewer global layers means less retrieval capacity and more reliance on each. Windows interact with sinks, RoPE base per layer type, prefix caching and paged-KV block sizes.
Used by
Gemma 2 (1:1, 4,096), Gemma 3 and 4 (5:1, 1,024; Gemma 4 ends on a global layer), gpt-oss (1:1, 128).
From your jet tagger

In your tagger every particle could attend to every other, and the set was small enough that this cost nothing: \(T\) was tens or a few hundred. A local window there would have thrown away exactly the pairwise structure you wanted. A language model is the opposite regime: \(T\) is 105, most useful dependencies are short-range, and a few are extremely long-range. Local/global layering is a way of paying for full attention only where language needs it. Sinks have a cleaner analogy still: a class token that every particle can read, but as a place to put attention you do not want to spend.

Common misconceptions

  • "With a sliding window the model only uses the last \(W\) tokens." Information moves \(W-1\) positions per layer, so the top layer can depend on tokens about \(\ell (W-1)\) back (131K for Mistral 7B). But that is a bound, diluted through many layers, and exact retrieval beyond \(W\) is what global layers are for.
  • "5:1 local:global means 6× less KV cache." It is 5.96× for Gemma 3 27B at 128K only. At \(T \le W\) the saving is zero, it depends on 10 of 62 layers being global, and the server must actually allocate window-sized caches for local layers.
  • "Attention sinks are special tokens you keep in the cache." That is StreamingLLM's fix for models trained without them. gpt-oss's sink is a learned scalar per head in the softmax denominator: no token, no cache entry, 2,304 parameters in total.
  • "The sink logit is a bias added to every score." It enters the denominator only, as one extra term \(e^z\). The real weights sum to less than 1, and the head output is scaled by \(\sigma(\mathrm{LSE} - z)\).
  • "MXFP4 makes gpt-oss 4-bit and 4× faster." Only the MoE weights (98% of parameters) are MXFP4, at 4.25 bits including the scale. Attention, router and embeddings stay BF16, so the checkpoint averages 4.46 bits per parameter (3.58× smaller than BF16), and activations stay BF16. Bytes drop; matmul FLOPs only drop on hardware with FP4 tensor cores.
  • "Gemma's 'feedforward hidden dims' is \(d_{\text{ff}}\)." For GeGLU the paper's number is twice the width of each branch (Gemma 2B: 32,768 listed, 16,384 per branch). Also the head dimension is decoupled from \(d\): Gemma 7B has \(16 \times 256 = 4096 > d = 3072\), and gpt-oss has \(64 \times 64 = 4096 > 2880\).
  • "Gemma distillation means training on text generated by the teacher." In pretraining the corpus is fixed, and the student matches the teacher's next-token distribution on it (Gemma 3: 256 sampled logits per token). Teacher-generated text is used in the SFT stage.
  • "Soft-capping and QK-norm are two ways of doing the same thing." A cap bounds the range of a logit but not the sharpness of a row, and saturates the gradient. QK-norm bounds \(|z|\) by \(g^2\sqrt{d_h}\) for any weights. Gemma 4's config still has a final-logit cap, so they can coexist.

Interview questions

Warm-up Why does sliding-window attention still allow long-range information flow?

In a layer with window \(W\), the state at position \(i\) attends to the previous layer's states at positions \(i-W+1\) to \(i\). Those states have themselves attended to their windows, so the dependency set grows by \(W-1\) positions per layer: after \(\ell\) layers it reaches about \(\ell(W-1)\) tokens. Mistral 7B: \(32 \times 4096 = 131{,}072\), the paper's "theoretical attention span of approximately 131K tokens".

Three caveats an interviewer expects. It is a bound: the path crosses \(\ell\) attention and MLP layers, each mixing with softmax and residual streams, so signal from far tokens is diluted and exact retrieval is not guaranteed (the paper shows no long-range retrieval test, and the model's listed context is 8,192). It is one-directional and per layer, so the model can only route information, not look it up. And the fix used in practice is hybrid: keep a minority of global layers for exact lookup (Gemma 3's 1 in 6, gpt-oss's every other layer) and let the local layers stay constant-cost.

Warm-up How big is Mistral 7B's KV cache with the rolling buffer, and why does RoPE not break it?

Per token: \(32 \cdot 2 \cdot 8 \cdot 128 \cdot 2\) B = 128 KiB. The buffer holds \(W = 4096\) entries per layer, key and value of position \(i\) in slot \(i \bmod W\), so it is \(4096 \times 128\) KiB = 512 MiB per sequence for any length beyond 4,096. At 32K a full cache is 4 GiB, so the saving is the paper's 8×.

RoPE is fine because keys are rotated by their absolute position when they are written, and a score depends only on the position difference, so entries can stay in slot order (softmax does not care about key order). Contrast StreamingLLM, which evicts middle tokens and therefore assigns positions inside the cache and caches keys before rotation (page 09).

Warm-up Gemma 1 2B's Table 1 lists "feedforward hidden dims 32768" and Table 2 lists 1,981,884,416 non-embedding parameters. Reconcile them.

GeGLU has two input projections (gate and up) plus a down projection, so the per-branch width is half of 32,768: \(d_{\text{ff}} = 16{,}384\). Per layer (\(d = 2048\), 8 query heads and 1 KV head of dimension 256): attention \(2048 \cdot 2048\) (Q) \(+ 2 \cdot 2048 \cdot 256\) (K, V) \(+ 2048 \cdot 2048\) (O) = 9,437,184; FFN \(3 \cdot 2048 \cdot 16384 = 100{,}663{,}296\); two RMSNorm vectors 4,096; total 110,104,576. Times 18 layers is 1,981,882,368, plus the final norm 2,048 gives 1,981,884,416, exactly the table. The embedding \(256{,}128 \times 2048 = 524{,}550{,}144\) is shared with the output and counted once.

The lesson is to check the gating convention before trusting any "hidden dim". The same method reproduces Gemma 2's three sizes exactly once you add four norms per layer.

Core What are attention sinks, and how does gpt-oss implement them?

Softmax weights sum to one, so a head with no relevant key must still put its mass somewhere. Trained models dump it on the first tokens, visible to every later query. StreamingLLM showed that evicting them breaks a windowed model (Llama-2-13B: perplexity 5,158 with a plain 1,024 window, 5.40 with 4 initial tokens kept), and that it is position, not content, that matters (newlines work: 5.60).

gpt-oss gives each head in each layer one learned scalar \(z\) added to the softmax denominator: \(p_j = e^{s_j}/(\sum_k e^{s_k} + e^z)\). It is a key with a zero value vector, so the weights over real keys sum to \(1 - p_{\text{sink}}\) and a head can output nearly zero. Code: append a column of \(z\) to the scores, softmax, drop the column. It costs 64 scalars per layer (2,304 in the 120b). A logit beats StreamingLLM's sink token because a token must stay pinned in the cache (their 160M model: 18.01 with it, 1,235 without) while a logit has no cache entry, and it works identically in the banded layers where the first token is outside the 128-token window.

Core Why did Gemma 3 switch from soft-capping to QK-norm?

What the report says: "we replace the soft-capping of Gemma 2 with QK-norm", inspired by ViT-22B, Wortsman et al. and Chameleon. It gives no Gemma-specific ablation, so the rest is the technical case (page 11).

Soft-capping \(c\tanh(z/c)\) with \(c = 50\) bounds a logit's range but not the sharpness of a row: one key at 50 among 8,191 zeros is still one-hot to 18 digits, and beyond the cap the \(\tanh\) gradient vanishes (0.42 at \(z = c\), 0.07 at \(2c\)). It also puts a \(\tanh\) inside every attention score, which fused kernels had to add support for (FlashAttention added a softcap argument in v2.6). QK-norm normalizes \(q\) and \(k\) per head before RoPE, giving \(|z| \le g^2\sqrt{d_h}\) for any weights, so logit growth cannot come from the two weight matrices and is limited to the \(d_h\) gains. Costs: two norms per attention layer, and it needs materialized keys (so it cannot be used with absorbed MLA). One nuance: Gemma 4's released config has final_logit_softcapping = 30, so the final cap returned, while the attention cap did not.

Core How does MXFP4 let gpt-oss-120b fit on one GPU? What is the accuracy risk?

MoE experts are 114.71B of the 116.83B parameters (98.2%). MXFP4 stores blocks of 32 E2M1 values with one shared 8-bit power-of-two scale: \((32 \cdot 4 + 8)/32 = 4.25\) bits. Experts: \(114.71\text{B} \times 4.25/8 = 60.94\) GB = 56.75 GiB. Attention, embeddings and unembedding (2.12B) stay in BF16: 3.95 GiB. Total 60.7 GiB (the card says 60.8), against 217.6 GiB in BF16, so it fits an 80 GB GPU (74.5 GiB) with about 13.8 GiB left for KV cache (4.5 GiB per 128K sequence) and activations.

Risks: 15 distinct element values (relative rounding error up to about 20%, values below a quarter of the scale flush to zero); a power-of-two scale means a block maximum in \([6,8)X\) clamps to 6X (up to 25% error); one outlier weight degrades its 31 neighbors. Direct-cast MXFP4 hurts (LLaMA-7B wikitext perplexity 9.49 to 11.48 with MXFP8 activations, 27.20 with MXFP4 activations). Mitigations: weights only, BF16 activations, BF16 attention and router, and post-training with the quantization in the loop. The card publishes no BF16-versus-MXFP4 comparison, so the residual loss is unquantified. The speed benefit is bandwidth (3.58× fewer weight bytes), not FLOPs.

Core Compute the KV cache at 128K tokens for Gemma 3 27B (5:1 local:global, window 1,024) and compare it with all-global.

Config: 62 layers, 16 KV heads, head dimension 128, so \(2 \cdot 16 \cdot 128 = 4096\) numbers per token per layer, 8 KiB in bf16. Global layers are at indices 5, 11, ..., 59: 10 global, 52 local. At \(T = 131{,}072 = 2^{17}\): a global layer holds \(8\text{ KiB} \times 2^{17} = 1\) GiB, a local layer \(8\text{ KiB} \times 1024 = 8\) MiB.

All-global: 62 GiB. Hybrid: \(10 + 52 \times 8/1024 = 10.41\) GiB, a 5.96× reduction (not exactly 6: 10 of 62 layers are global, and local layers still hold 1,024 tokens). With bf16 weights of 50.3 GiB, all-global needs 112 GiB and does not fit on one 80 GB GPU; the hybrid needs 60.7 GiB. Caveats: at \(T \le 1024\) there is no saving, and the saving exists only if the server allocates window-sized caches for local layers. Gemma 4 31B, which shares K=V in 4 wide global heads, is 5.78 GiB by the same arithmetic.

Core What did the Mixtral routing analysis find, and what does it imply?

Expert assignments at layers 0, 15 and 31 look very similar across ArXiv, PubMed and PhilPapers text: there is no domain specialization (only DM Mathematics differs a little). The router does track syntax: 'self' in Python, 'Question' and indentation tokens go to consistent experts. And consecutive tokens repeat their first-choice expert well above the 12.5% chance level: 13.6 to 14.9% at layer 0 (close to random), 23.6 to 28.4% at layer 15, 19.7 to 26.3% at layer 31 (Tab. 5).

Implications: do not describe experts as "the math expert" (specialization by domain appears only under particular balancing regimes, page 08). Temporal locality means that within one sequence some experts are over-subscribed under expert parallelism, and it makes expert caching or offloading plausible, because the set of hot experts changes slowly. It also means the "all experts are read at large batch" argument is softened for small batches of correlated tokens.

Core Explain Gemma 2's distillation: the loss, why it helps a small model, what it costs, and what the evidence is.

Loss: \(-\sum_x P_T(x|x_c)\log P_S(x|x_c)\) at every position, so the student's logit gradient is \(P_S - P_T\) instead of \(P_S - \text{one-hot}\). Each position teaches the whole distribution over 256K tokens, a richer, lower-variance signal. The report's argument: small models are under-trained and simply training longer scales only logarithmically, so distill for a very large number of tokens ("more than 50× the compute-optimal quantity") to "simulate training beyond the number of available tokens". With 20 tokens per parameter I get 38× (2B, 2T tokens) and 43× (9B, 8T).

Evidence: 2B student, 500B tokens: 67.7 average over three benchmarks distilled from a 7B teacher against 60.3 from scratch; perplexity 23 to 21, 19 to 17, 17 to 15 for 200M, 400M, 1B students. Cost: a teacher forward per token; with \(6N_S + 2N_T\) FLOPs, a 9B student and a hypothetical 27B teacher is \(54 + 54 = 108\) GFLOPs per token, 2× plain (the teacher is not named; whether logits are precomputed is not stated). The 27B was trained from scratch. Gemma 3 uses 256 sampled logits per token, renormalized.

Deep-dive Local:global ratio: how would you choose it?

Start from the budget. Relative to all-global the KV cache (and decode read, and roughly prefill attention FLOPs) is \(f = \frac{1}{r+1} + \frac{r}{r+1}\min(1, W/T)\) for \(r\) local per global layer. At 128K and \(W = 1024\): 1:1 is 0.50, 3:1 0.26, 5:1 0.17, 7:1 0.13, 11:1 0.09. Diminishing returns: 5:1 to 11:1 saves 8 points of cache and halves the layers able to do exact lookup. Per-layer cache size matters too: gpt-oss at 1:1 with a 128 window caches 2 KiB per token-layer, Gemma 3 27B 8 KiB, so gpt-oss ends at 4.5 GiB and Gemma 3 at 10.4 GiB despite the worse ratio.

Then quality. Perplexity is nearly flat from 1:1 to 7:1 and windows to 512 (Gemma 3 §5.2), but it mostly measures local prediction. I would pick the smallest global fraction and window that keep RULER, NoLiMa and multi-hop tasks intact after context extension, at 32K and 128K, as per-length curves. MiMo's ablation is the warning: 512 collapsed after extension while 128 did not; MiniMax saw hybrids degrade past 32K. Also ablate sinks (a small window needs them), place a global layer last (Gemma 4), give global layers a higher RoPE base (Gemma 3), and check that the serving stack supports window-sized paged-KV blocks and prefix caching. Default: 5:1 to 7:1, a 512 to 1,024 window, sinks, then revise from the curves.

Deep-dive Show that a sink is a sigmoid gate on the head output, and say what it means for a FlashAttention-style forward and backward kernel.

Let \(Z = \sum_j e^{s_j}\), \(\mathrm{LSE} = \log Z\), and \(o = \sum_j (e^{s_j}/Z) v_j\) the plain output. With a sink, \(o' = \sum_j e^{s_j} v_j / (Z + e^z) = o \cdot Z/(Z + e^z) = o \cdot \sigma(\mathrm{LSE} - z)\), since \(Z/(Z+e^z) = 1/(1 + e^{z - \mathrm{LSE}})\).

Forward: the tiled loop is unchanged. It already keeps the running max and sum and ends with \(\mathrm{LSE}\), so the kernel applies the gate as an epilogue, or equivalently stores \(\mathrm{LSE}' = \operatorname{logaddexp}(\mathrm{LSE}, z)\) and scales \(o\) by \(e^{\mathrm{LSE} - \mathrm{LSE}'}\). Backward: use \(P = e^{S - \mathrm{LSE}'}\). The sink column has a zero value, so its \(dP\) is 0 and \(D_t = \sum_j P_{tj}\, dP_{tj} = \langle dO_t, O'_t\rangle\) is the usual flash term; \(dS = P \circ (dP - D)\) is unchanged. For the sink itself, \(\partial\mathcal L/\partial z = -\sum_t p_{\text{sink},t}\,\langle dO_t, O'_t\rangle\), one more reduction over the \(D_t\) values (I checked this against autograd). The drill test verifies the forward identity, and the sink-off case (\(z \to -\infty\)) recovers plain attention.

Deep-dive Reconcile gpt-oss-120b's 116.83B total and 5.13B active parameters from its config.

Config: 36 layers, \(d = 2880\), 64 query heads and 8 KV heads of dimension 64, 128 experts of width 2,880 with top-4, vocabulary 201,088, untied embeddings. Experts: \(36 \cdot 128 \cdot (3 \cdot 2880^2 + 8640) = 114.70\)B (the biases are needed to hit the card's 114.71B). Attention per layer: \(2880 \cdot 4096 + 2 \cdot 2880 \cdot 512 + 4096 \cdot 2880\) plus 8,000 biases (4,096 + 512 + 512 + 2,880) = 26,550,080; \(\times 36 = 0.956\)B. Embedding plus unembedding: \(2 \cdot 201{,}088 \cdot 2880 = 1.158\)B. Total 116.83B.

Active: 4 of 128 experts, \(36 \cdot 4 \cdot 3 \cdot 2880^2 = 3.583\)B, plus attention 0.956B, plus the unembedding 0.579B (the card counts the unembedding but not the embedding), plus routers \(36 \cdot 2880 \cdot 128 = 0.013\)B: 5.13B. Experts are 98.2% of the parameters, which is why quantizing only them gives 3.58×. Conventions differ across labs: Gemma 4's 3.8B active appears to include its tied embedding table, DeepSeek counts differently again (page 26), so always ask what is counted.

Deep-dive Design question: a new 36-layer, ~100B-total MoE with GQA-8 heads of dimension 128 must serve 128K contexts. Compare attention options by KV memory, and say what you would evaluate.

Baseline all-global GQA-8: \(2 \cdot 8 \cdot 128 \cdot 2\) B = 4 KiB per token per layer, so 144 KiB per token and 18 GiB at 128K. Options: (a) Gemma-style 5:1 with a 1,024 window: 6 global layers, \(6 \times 4\text{ KiB} \times 2^{17} = 3\) GiB plus \(30 \times 4\text{ KiB} \times 1024 = 120\) MiB: 3.12 GiB (5.8×). (b) gpt-oss-style 1:1 with a 128 window: 9 GiB (2×) at this head size, and the small window needs sinks. (c) MLA as in Mistral Small 4: \(36 \times 320 \times 2\) B = 22.5 KiB per token, 2.81 GiB (6.4×), uniform and no window, but with heavier kernels, decode FLOPs that grow with the head count, and no head-sharded tensor parallelism (page 07). (d) Stack them: MLA in the few global layers of a hybrid.

What each saves: windows cut capacity and bandwidth for local layers but not the global ones; MLA cuts both per layer; neither reduces the FLOPs of global layers at 128K. Risks: retrieval in hybrids, and kernel or TP complexity for MLA. Evaluation: perplexity as a regression check only, RULER, NoLiMa and multi-hop at 32K and 128K after context extension, ablations of window, ratio and sinks, measured decode tokens/s and batch capacity on the target hardware. I would pick (a) or (d) as the main bet, with the full-attention twin as the control.

Cheat sheet

  • Mistral 7B: GQA 32/8, \(d_h = 128\), window 4,096, rolling buffer at slot \(i \bmod W\), span \(32 \times 4096 = 131{,}072\) (a bound), 128 KiB per token so 512 MiB flat, 8× less than full at 32K. Later Mistral configs drop the window.
  • Mixtral: 8 experts, top-2, softmax over the top-2 logits, every layer. 8x7B: 47B/13B. 8x22B: 141B/39B, 64K. No topic specialization; consecutive-token expert repeat 24 to 28% at layer 15 versus 12.5% chance.
  • Mistral Large 3 / Small 4: MLA with V3-style dims (Large 3: 61 layers, \(d_c\)=512), 128 routed + 1 shared experts, top-4; 675B/41B and 119B/6B. Cache 576 or 320 numbers per token per layer.
  • Gemma 1/2: head dim 256, GeGLU (table lists 2× per-branch width), 256K vocab, embeddings × \(\sqrt d\), MQA on 2B. Gemma 2: 1:1 local (4,096)/global (8,192), soft-cap 50/30, pre+post norms (four per layer), GQA, 2B and 9B distilled (2T, 8T tokens), 27B from scratch (13T).
  • Distillation: loss \(-\sum P_T\log P_S\), gradient \(P_S - P_T\). 2B: 67.7 versus 60.3 (500B tokens). Gemma 3: 256 sampled logits per token, renormalized.
  • Gemma 3: 5:1 local:global, window 1,024, QK-norm instead of soft-cap, RoPE base 10K local / 1M global with factor-8 interpolation, 32K pretraining extended to 128K, vocab 262K. 27B at 128K: 62 GiB all-global versus 10.41 GiB (10 global, 52 local, 8 KiB per token-layer).
  • Gemma 4: Apache 2.0, April 2026. 5:1 (4:1 for E2B), last layer global, global K=V with 4 KV heads × 512 (31B), p-RoPE 0.25, QK-norm, final cap 30. 31B at 128K: 5.78 GiB. 26B-A4B: 128 experts, top-8 + shared, 25.2B/3.8B. MTP drafters, thinking mode.
  • gpt-oss-120b: 36 layers, \(d = 2880\), 64 × 64 heads, 8 KV heads, banded (128) and dense alternating from layer 0, 128 experts top-4 (width 2,880), 116.83B/5.13B, YaRN ×32 to 131,072, vocab 201,088. KV at 128K: 4.50 GiB.
  • Sinks: \(p_j = e^{s_j}/(\sum_k e^{s_k} + e^z)\), one \(z\) per head per layer (2,304 in 120b), zero-valued key, rows sum to \(1 - p_{\text{sink}}\), output \(= o\cdot\sigma(\mathrm{LSE} - z)\). StreamingLLM: Llama-2-13B 5,158 to 5.40 with 4 initial tokens.
  • MXFP4: 32 E2M1 values + one E8M0 scale = 4.25 bits, \(X = 2^{\lfloor\log_2\max|v|\rfloor - 2}\), grid 0, 0.5, 1, 1.5, 2, 3, 4, 6. gpt-oss-120b: 56.75 + 3.95 = 60.7 GiB (card 60.8) versus 217.6 GiB BF16; only experts are 4-bit.
