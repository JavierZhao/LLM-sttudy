How LLM coding rounds work

Scope of this section

Labs publish little about their loops, and formats differ by team, role and year. What follows is general guidance derived from what the drills exercise and from common practice in ML interviews, not a sourced description of any lab's process. Ask your recruiter which tools are allowed (documentation, autocomplete, a shared notebook, a plain editor) and whether the round is live or a take-home.

Four formats to prepare for

  1. Implement a component from a spec. "Write causal multi-head attention", "implement top-p sampling", "write the DPO loss", in PyTorch or NumPy, with follow-ups that change one requirement (add a KV cache 键值缓存, make it stable in bf16). Most drills below are this format.
  2. Debug broken code. A module or training loop that runs but is wrong, with a symptom (loss too low, NaN after step 300). The training-loop exercise is this format.
  3. Optimize a slow function. Vectorize a loop over tokens, avoid materializing a \(T\times T\) matrix, fuse two passes. The vocabulary is complexity and memory traffic.
  4. Systems-flavored coding. Simulate an all-reduce, write a tokenizer or a request scheduler, sometimes with concurrency, more often in research-engineer loops. Classic algorithm questions also appear; this course does not cover them, so budget separate practice.

What the interviewer is checking

Read this as a rubric for your own solutions:

  • Shapes: you can state every intermediate shape. Write it in a comment on each line, as the course code does.
  • Masking: mask polarity, the causal mask 因果掩码 applied to scores before the softmax, the end-aligned mask when queries are fewer than keys.
  • Numerical stability: subtract the row maximum, upcast before reductions, keep \(-\infty\) from turning into NaN, prefer log_softmax to log(softmax).
  • Tests: a tiny case by hand, then properties, before being asked. A candidate who runs a causality test unprompted has answered half the follow-ups.
  • Complexity: time, memory and, for anything that decodes, cost per generated token. Say it unprompted.
  • Communication: state assumptions, narrate trade-offs, correct yourself early. A correct, slower solution you can defend beats a fast one you cannot.

The practice protocol

Do every drill the same way, so the time targets in the index mean something.

  1. Timebox. Set a timer for the index target. When it rings, stop and note how far you got. A first attempt often takes about twice the target.
  2. No references. Open the stub in exercises/drills/ (signatures and docstring only) and write the body without a browser or the earlier page. If you cannot recall an API, write what you would call it and move on, as in an interview.
  3. Run the tests. pytest exercises/tests/test_<name>.py. Read only the first failure, fix it, rerun. Test names state the property being checked, which is often the hint you needed.
  4. Compare with the reference. Confirm with --solutions, then read exercises/solutions/<name>.py beside your code. Sort each difference into a typo, a missed edge case or a conceptual gap. Only the last deserves another drill.
  5. Log the class of mistake with the labels of the checklist. After ten drills the log shows the two or three classes that cost you time.
  6. Redo from scratch two or three days later at half the target, then explain the solution aloud. Speaking is a separate skill from typing, and most rounds involve both.

LayerNorm and RMSNorm backward by hand

Interviewers like this problem: it has one checkable answer, it applies the chain rule through a mean and a variance, and it leads into kernel design. The drill is exercises/drills/layernorm_backward.py: write layernorm_forward (returning the output and a cache), layernorm_backward (returning \(dx, d\gamma, d\beta\)) and the same pair for RMSNorm. The tests compare with autograd in float64, run gradcheck through your pair, and check properties that need no reference.

The forward pass and what to cache

Both norms, LayerNorm 层归一化 and RMSNorm 均方根归一化, act on the last axis of one token's vector \(x\in\R^d\) (page 04 explains why RMSNorm replaced LayerNorm). With \(r\) the reciprocal standard deviation and \(\hat x\) the normalized vector:

\[ \text{LayerNorm:}\quad \mu=\tfrac1d\sum_i x_i,\;\; r=\big(\tfrac1d\sum_i (x_i-\mu)^2+\epsilon\big)^{-1/2},\;\; \hat x_i=(x_i-\mu)\,r,\;\; y_i=\gamma_i\hat x_i+\beta_i \] \[ \text{RMSNorm:}\quad r=\big(\tfrac1d\sum_i x_i^2+\epsilon\big)^{-1/2},\;\; \hat x_i=x_i\,r,\;\; y_i=\gamma_i\hat x_i \]

The variance divides by \(d\), not \(d-1\), and \(\epsilon\) sits inside the root. Everything the backward pass needs is \(\hat x\), \(r\) and \(\gamma\), so that is the cache. Compute the statistics in at least float32 (in code: torch.promote_types(x.dtype, torch.float32)), so bf16 inputs are upcast while float64 inputs, which the gradient checks need, are left alone.

The backward pass, step by step

Write \(\delta_i=\partial L/\partial y_i\) for the incoming gradient and \(\bar v\) for the mean of a vector \(v\) over its \(d\) entries. Three steps, easiest first.

Step 1, the parameters. Since \(y_i=\gamma_i\hat x_i+\beta_i\) and the same \(\gamma,\beta\) are used at every token, their gradients sum over all batch and position axes:

\[ \frac{\partial L}{\partial\gamma_i}=\sum_{\text{rows}}\delta_i\,\hat x_i,\qquad \frac{\partial L}{\partial\beta_i}=\sum_{\text{rows}}\delta_i \]

Step 2, the normalized values. \(u_i:=\partial L/\partial\hat x_i=\gamma_i\delta_i\).

Step 3, the input. For LayerNorm, \(x_j\) reaches \(\hat x_i=c_i r\) (with \(c_i=x_i-\mu\)) along two routes: through the centered value \(c_i\) (directly, and through the mean), and through \(r\), which depends on \(\sigma^2=\overline{c^2}\). The pieces are \[ \frac{\partial c_i}{\partial x_j}=\delta_{ij}-\frac1d,\qquad \frac{\partial\sigma^2}{\partial x_j}=\frac2d\sum_k c_k\Big(\delta_{kj}-\frac1d\Big)=\frac2d\,c_j,\qquad \frac{\partial r}{\partial x_j}=-\tfrac12 r^3\frac{\partial\sigma^2}{\partial x_j}=-\frac{r^2}{d}\,\hat x_j\,, \] where the middle equality uses \(\sum_k c_k=0\) and the last one uses \(r c_j=\hat x_j\). Then \[ \frac{\partial L}{\partial x_j}=\sum_i u_i\Big(r\,\frac{\partial c_i}{\partial x_j}+c_i\,\frac{\partial r}{\partial x_j}\Big)=r\,(u_j-\bar u)-r\,\hat x_j\,\overline{u\hat x}\,. \]

\[ dx_j \;=\; r\Big(u_j-\bar u-\hat x_j\,\overline{u\odot\hat x}\Big),\qquad u=\gamma\odot\delta \qquad\text{(LayerNorm)} \] \[ dx_j \;=\; r\Big(u_j-\hat x_j\,\overline{u\odot\hat x}\Big),\qquad u=\gamma\odot\delta \qquad\text{(RMSNorm)} \]
RMSNorm has no centering, so no mean(u) term, and no bias

For RMSNorm take \(c_i=x_i\): there is no \(-1/d\) in \(\partial x_i/\partial x_j=\delta_{ij}\), and \(\partial r/\partial x_j=-r^2\hat x_j/d\) again, which gives the second line. I checked both lines against autograd (maximum error about \(10^{-15}\) in float64), and the drill's tests repeat that check.

Key idea: the gradient lives in a subspace

LayerNorm's output is unchanged if you add a constant to every entry of \(x\) or (exactly so at \(\epsilon=0\)) multiply \(x\) by a positive scalar, so the gradient with respect to \(x\) has no component along the all-ones vector or, at \(\epsilon=0\), along \(x\). The two correction terms subtract exactly those components. At \(\epsilon=0\) the Jacobian is \(r\,(I-\tfrac1d\mathbf 1\mathbf 1^\top-\tfrac1d\hat x\hat x^\top)\), \(r\) times an orthogonal projection of rank \(d-2\), because \(\hat x\perp\mathbf 1\) and \(\|\hat x\|^2=d\). RMSNorm is scale-invariant but not shift-invariant: its Jacobian is \(r\,(I-\tfrac1d\hat x\hat x^\top)\), rank \(d-1\). Two reference-free tests follow: \(\sum_j dx_j=0\) for LayerNorm, and \(\sum_j dx_j x_j=0\) for both at \(\epsilon=0\).

Checking it: gradcheck through your own pair

Wrap your pair as a torch.autograd.Function and let PyTorch compare it against finite differences (this is what the drill's tests do):

import torch
from layernorm_backward import layernorm_forward, layernorm_backward   # your module

class MyLayerNorm(torch.autograd.Function):
    @staticmethod
    def forward(ctx, x, g, b):
        y, ctx.cache = layernorm_forward(x, g, b, 1e-5)
        return y

    @staticmethod
    def backward(ctx, dy):
        return layernorm_backward(dy, ctx.cache)          # (dx, dg, db)

x = torch.randn(3, 5, 8, dtype=torch.float64, requires_grad=True)
g = torch.randn(8, dtype=torch.float64, requires_grad=True)
b = torch.randn(8, dtype=torch.float64, requires_grad=True)
print(torch.autograd.gradcheck(MyLayerNorm.apply, (x, g, b)))   # True

Float64 matters: gradcheck perturbs inputs by \(10^{-6}\) and compares to a tolerance near \(10^{-5}\), which float32 cannot resolve.

Worked numbers

Take \(d=4\), \(x=(1,2,3,6)\), \(\gamma=\mathbf 1\), \(\beta=0\), \(\epsilon=0\). Then \(\mu=3\), \(\sigma^2=(4+1+0+9)/4=3.5\), \(r=1/\sqrt{3.5}=0.5345\), and \(\hat x=(-1.069,\,-0.535,\,0,\,1.604)\). Let \(\delta=(1,0,0,0)\), so \(u=\delta\), \(\bar u=0.25\) and \(\overline{u\hat x}=-1.069/4=-0.2673\):

\[ dx_j=0.5345\big(u_j-0.25+0.2673\,\hat x_j\big)\;\Rightarrow\;dx=(0.2482,\,-0.2100,\,-0.1336,\,0.0955). \]

The entries sum to \(0\) (\(2.8\times10^{-17}\) in float64) and \(\sum_j dx_jx_j=0.2482-0.4200-0.4008+0.5730=0\), as the subspace argument predicts, and autograd gives the same four numbers. Also \(d\gamma=(-1.069,0,0,0)\) and \(d\beta=(1,0,0,0)\). For RMSNorm on the same input, \(r=1/\sqrt{12.5}=0.2828\) and \(dx=(0.2772,\,-0.0113,\,-0.0170,\,-0.0339)\): it sums to \(0.215\), not zero, but \(\sum_j dx_jx_j\) is still zero.

What the interviewer checks

  • Reduction axes of \(d\gamma\) and \(d\beta\). Sum over all leading axes with reshape(-1, d).sum(0). PyTorch's x.sum(dim=()) reduces over every dimension, so a 1-D input silently returns a scalar (checked on torch 2.14).
  • A dropped mean term (the RMSNorm formula used for LayerNorm) passes a shape check and is off by \(r\,\bar u\); \(\sum_j dx_j=0\) catches it in one line.
  • Precision. Statistics in float32 or better. In bf16, values near 100 are spaced 0.5 apart, so bf16 statistics destroy the normalization: on the check input a naive bf16 implementation was off by about 0.3 and the float32-statistics one by about 0.015 (output rounding). The drill's low-precision test uses that input.
  • Mutating the cache. xhat *= ... in backward corrupts a second call (activation recomputation, double backward). The test calls backward twice.
  • Degenerate rows. A constant row has zero variance; \(\epsilon\) keeps \(r=1/\sqrt\epsilon\) finite (316 for \(10^{-5}\)), so outputs are finite but large.
Cache the normalized values, or recompute them?
Problem
Backward needs \(\hat x\). Storing it costs \(d\) numbers per token per norm layer, and each of the \(L\) blocks has two norms.
Idea
Save the input (usually alive anyway) and two scalars per row, and recompute \(\hat x=(x-\mu)\,r\) inside backward.
Why it works
Normalization is memory-bound: a few FLOPs per element against an HBM read. Recomputing adds negligible arithmetic and removes a full-size tensor from the activation footprint.
Evidence
PyTorch's fused op returns (out, mean, rstd) and its backward takes (grad_out, input, ..., mean, rstd, weight, bias), so it does not keep \(\hat x\) (I read both operator schemas on torch 2.14). The Triton layer-norm tutorial saves x, mean and rstd [Triton tutorial 05].
Cost
A few extra FLOPs per element in backward, and \(x\) must stay alive until then. In a from-scratch drill, caching \(\hat x\) is simpler and equally correct.
Used by
PyTorch's native layer norm and the Triton tutorial kernel, per the sources above. The kernel view (one program per row, partial sums for \(d\gamma\) and \(d\beta\)) is worked out in a deep-dive question below.

import torch
from torch import Tensor

def _acc_dtype(dtype: torch.dtype) -> torch.dtype:
    # statistics in at least float32; float64 inputs stay float64 (needed for gradcheck)
    return torch.promote_types(dtype, torch.float32)


def layernorm_forward(x: Tensor, g: Tensor, b: Tensor, eps: float = 1e-5) -> tuple[Tensor, tuple]:
    xf = x.to(_acc_dtype(x.dtype))
    mu = xf.mean(-1, keepdim=True)
    xc = xf - mu
    var = (xc * xc).mean(-1, keepdim=True)          # biased variance: divide by d, not d - 1
    rstd = torch.rsqrt(var + eps)                    # eps inside the square root
    xhat = xc * rstd
    y = xhat * g.to(xf.dtype) + b.to(xf.dtype)
    return y.to(x.dtype), (xhat, rstd, g, x.dtype)


def layernorm_backward(dy: Tensor, cache: tuple) -> tuple[Tensor, Tensor, Tensor]:
    xhat, rstd, g, x_dtype = cache
    d = xhat.shape[-1]
    dyf = dy.to(xhat.dtype)
    dxhat = dyf * g.to(xhat.dtype)                   # gradient w.r.t. the normalized values
    # remove the mean (shift invariance) and the component along xhat (scale invariance)
    dx = rstd * (dxhat
                 - dxhat.mean(-1, keepdim=True)
                 - xhat * (dxhat * xhat).mean(-1, keepdim=True))
    # reshape(-1, d).sum(0) also works for 1-D input, where sum(dim=()) would reduce everything
    dg = (dyf * xhat).reshape(-1, d).sum(0)
    db = dyf.reshape(-1, d).sum(0)
    return dx.to(x_dtype), dg.to(g.dtype), db.to(g.dtype)


def rmsnorm_forward(x: Tensor, g: Tensor, eps: float = 1e-6) -> tuple[Tensor, tuple]:
    xf = x.to(_acc_dtype(x.dtype))
    rstd = torch.rsqrt((xf * xf).mean(-1, keepdim=True) + eps)
    xhat = xf * rstd
    y = xhat * g.to(xf.dtype)
    return y.to(x.dtype), (xhat, rstd, g, x.dtype)


def rmsnorm_backward(dy: Tensor, cache: tuple) -> tuple[Tensor, Tensor]:
    xhat, rstd, g, x_dtype = cache
    d = xhat.shape[-1]
    dyf = dy.to(xhat.dtype)
    dxhat = dyf * g.to(xhat.dtype)
    dx = rstd * (dxhat - xhat * (dxhat * xhat).mean(-1, keepdim=True))   # no mean term: no re-centering
    dg = (dyf * xhat).reshape(-1, d).sum(0)
    return dx.to(x_dtype), dg.to(g.dtype)

Beam search with length normalization and EOS handling

Page 06 explains when beam search 束搜索 is the right tool and why chat models rarely use it. Here you write it. The interview version has four parts: the search itself (a flat top-\(k\) over \(b\times V\) candidates), what happens at EOS, how finished hypotheses of different lengths are compared (length normalization 长度归一化), and when to stop. The drill is exercises/drills/beam_search.py, and its tests check your result against exhaustive search.

The interface and the conventions

The model is a black box called once per step on all live hypotheses, like a batched decoder with a KV cache: step_logprobs_fn(prefixes) takes an \((n,t)\) tensor of token ids (every row starts with BOS) and returns \((n,V)\) log-probabilities of the next token, possibly \(-\infty\) for forbidden tokens. State your conventions before coding, since libraries differ:

QuestionConvention in the drill
Does the length \(\lvert Y\rvert\) count EOS?Yes, and EOS's log-probability is in the sum. Hugging Face's BeamSearchScorer.process also counts it (cur_len = input_ids.shape[-1] + 1, transformers v4.44), but say which you use.
What ranks candidates inside one step?The raw cumulative log-probability. All candidates have the same length, so a length penalty would not change their order.
What compares finished hypotheses?\(\log P(Y)/lp(Y)\) with \(lp(Y)=\big((5+\lvert Y\rvert)/6\big)^{\alpha}\), the GNMT form without the coverage term [Wu et al. 2016, §7, Eq. 14]. \(\alpha=0\) means no normalization.
What happens at EOS?The extension is recorded as finished and never expanded. The beam refills from non-EOS candidates, so it keeps \(b\) live hypotheses.
What if max_len is reached without EOS?The hypothesis is finished and truncated, with length max_len.

The algorithm

Start from the single prefix [bos] with score 0 and repeat for step \(=1,\dots,\texttt{max\_len}\):

  1. Call the model on the \(n\le b\) live prefixes and form total = scores[:, None] + logp, shape \((n,V)\).
  2. Each live hypothesis's EOS extension total[i, eos] (if finite) is a finished hypothesis with score \(\text{total}/lp(\text{step})\).
  3. Set the EOS column to \(-\infty\), flatten to \(nV\) entries, take the top \(\min(b,nV)\), and drop entries equal to \(-\infty\). A flat index \(f\) is parent \(\lfloor f/V\rfloor\), token \(f\bmod V\).
  4. Gather the parents' prefixes and append the tokens. This gather is the "reorder the KV cache" step of a real decoder.
  5. After the last step, the survivors are truncated hypotheses. Sort all finished hypotheses by normalized score and return the best \(b\).

The toy conditions on the last token only: BOS is followed by a, b, EOS with probabilities \(0.45, 0.40, 0.15\); a by \(0.05, 0.85, 0.10\); b by \(0.35, 0.10, 0.55\). Every number in Figure 3 is a sum of logarithms you can check by hand, for example \(\log(0.45\cdot0.85)=-0.961\). Length normalization for finished hypotheses
Problem
Each token adds a negative log-probability, so raw sums favor short outputs. Plain beam search "will favor shorter results over longer ones on average" (Wu et al.), and exact search can prefer the empty output (page 06).
Idea
Divide by a length penalty before comparing finished hypotheses: GNMT's \(lp(Y)=((5+\lvert Y\rvert)/6)^\alpha\), or the simpler \(\lvert Y\rvert\) (mean token log-probability) or \(\lvert Y\rvert^{\alpha}\).
Why it works
\(\alpha\) interpolates between no correction and a per-token average, and the offset 5 stops very short outputs from being over-rewarded (\(lp(1)=1\) for every \(\alpha\)).
Evidence
GNMT first divided by length, then by length\(^\alpha\) (best \(\alpha\) in 0.6 to 0.7), then adopted the form above. On the WMT'14 En-Fr development set \(\alpha=\beta=0.2\) raised BLEU from 30.3 to 31.4 without RL refinement, and helped less after it [Wu et al. 2016, §7, Tab. 2-3]. Hugging Face divides by generated_len ** length_penalty, default 1.0 (transformers v4.44, beam_search.py).
Cost
A tuned heuristic. It changes which finished hypothesis wins, not the mode-seeking behavior: likelihood as a decoding objective gives text that is "bland and strangely repetitive" [Holtzman et al. 2019, abstract]. It also complicates the stopping rule.
Used by
GNMT (the form above) and Hugging Face generate (the \(\lvert Y\rvert^\alpha\) form).

Design points an interviewer will probe

  • One live row at the start. \(b\) copies of BOS make step 1 pick the same best token from each copy, so the beam is \(b\) duplicates and behaves like greedy decoding. The drill checks that the first model call has one row.
  • Record every EOS extension. It is free (one per live hypothesis). Hugging Face's scorer takes the top \(2b\) candidates and records an EOS candidate only if its rank in that list is below \(b\) (transformers v4.44), which discards some finished hypotheses for narrow beams. The rules agree for wide beams.
  • \(-\infty\) and narrow candidate sets. Never let a \(-\infty\) candidate into the beam, and take \(\min(b,nV)\) so topk never asks for more entries than exist (a beam wider than \(V\) crashes at step 1).
  • Ties and precision. torch.topk promises no order among equal values (sort with stable=True if determinism matters). Keep cumulative scores in float32 or float64 even if the model runs in bf16.

When to stop, exactly

Running all max_len steps is always correct. Stopping early is easy to get wrong with length normalization, because a live hypothesis that scores poorly now can still win: its normalized score can rise as it grows, when each added token costs little and the divisor \(lp\) increases. A rigorous bound: a live hypothesis with log-probability \(L\le0\) has completions with \(L'\le L\) and length \(n'\le n_{\max}\), so for \(\alpha\ge0\)

\[ \frac{L'}{lp(n')}\;\le\;\frac{L}{lp(n')}\;\le\;\frac{L}{lp(n_{\max})}. \]

Once \(b\) finished hypotheses are kept, stop if \(\max_{\text{live}}L/lp(n_{\max})\) is strictly below the worst kept score. The drill's early_stop=True implements this and must return exactly what early_stop=False returns. Its tests include a model built to fool the two tempting shortcuts: comparing raw scores, and normalizing by the current length. The second is Hugging Face's default heuristic (early_stopping=False), which its source calls "not entirely accurate" for positive length penalties; its "never" mode uses \(n_{\max}\) like the bound [transformers v4.44, BeamHypotheses.is_done].

Checking it against brute force

exhaustive_search enumerates every finished hypothesis by recursion (121 for \(V=4\), max_len 4) with the same scoring rule. On random recurrent models whose next-token law depends on the whole prefix, the tests assert:

  • a beam wide enough that nothing is pruned returns exactly the exhaustive top 5, tokens and scores, for \(\alpha\in\{0,0.6,1,2\}\);
  • every returned hypothesis is well formed and its score equals an independent teacher-forced recomputation;
  • no finished hypothesis is fed back to the model, the first call has one row, and no call has more than \(b\) rows;
  • beam 1 scores at least as well as greedy decoding, and the toy above gives the table's orderings;
  • forbidden tokens, a model that never emits EOS, a beam wider than the candidate set, and float32 outputs all behave.

I also ran the suite against deliberately broken solutions (EOS left in the beam, no min(b, nV), \(-\infty\) kept, length excluding EOS, \(b\) copies of BOS, three wrong early-stop bounds, no trimming). It failed for each.

Cost. Each step is one model call on at most \(b\) rows, so FLOPs are \(b\) times a single sequence while weight traffic is shared as in any batch of \(b\). The top-\(k\) over \(bV\) entries is small next to the model. The cache gather is the awkward part, which is why serving systems share prompt blocks and copy on write (page 17); a deep-dive question below puts numbers on it.

from typing import Callable
import torch
from torch import Tensor

NEG_INF = float("-inf")


def normalized_score(sum_logprob: float, length: int, alpha: float) -> float:
    return sum_logprob / (((5.0 + length) / 6.0) ** alpha)      # GNMT: lp = ((5 + |Y|) / 6) ** alpha


def beam_search(
    step_logprobs_fn: Callable[[Tensor], Tensor],
    bos: int,
    eos: int,
    beam: int,
    max_len: int,
    length_penalty: float = 0.0,
    early_stop: bool = False,
) -> list[tuple[list[int], float]]:
    if beam < 1 or max_len < 1:
        raise ValueError("beam and max_len must be at least 1")
    if length_penalty < 0:
        raise ValueError("length_penalty must be >= 0")
    alpha = length_penalty
    prefixes = torch.tensor([[bos]], dtype=torch.long)           # (n, t) live hypotheses, all the same length
    scores = torch.zeros(1, dtype=torch.float64)                 # (n,) cumulative log-probability
    finished: list[tuple[float, list[int]]] = []                 # (normalized score, tokens without bos)

    def trim() -> None:
        finished.sort(key=lambda h: -h[0])                       # stable: earlier finishers win ties
        del finished[beam:]

    for step in range(1, max_len + 1):                           # step = number of generated tokens so far
        logp = step_logprobs_fn(prefixes).to(torch.float64)      # (n, V), one model call per step
        n, V = logp.shape
        total = scores[:, None] + logp                           # cumulative score of every extension
        # 1. every EOS extension is a finished hypothesis and is never expanded again
        for i in range(n):
            s = total[i, eos].item()
            if s > NEG_INF:
                finished.append((normalized_score(s, step, alpha), prefixes[i, 1:].tolist() + [eos]))
        # 2. the live beam is the top-`beam` non-EOS extensions, ranked by RAW cumulative log-prob
        #    (all candidates have the same length here, so normalizing would not change the order)
        total[:, eos] = NEG_INF
        vals, idx = total.reshape(-1).topk(min(beam, n * V))     # k may exceed n * V for a wide beam
        keep = vals > NEG_INF                                    # forbidden tokens never enter the beam
        vals, idx = vals[keep], idx[keep]
        if vals.numel() == 0:
            prefixes = prefixes[:0]
            break
        parent, tok = idx // V, idx % V                          # flat index -> (which hypothesis, which token)
        prefixes = torch.cat([prefixes[parent], tok[:, None]], dim=1)   # this gather is the "cache reorder"
        scores = vals
        trim()
        # 3. optional exact stopping rule: no descendant can beat the worst kept finished hypothesis
        if early_stop and step < max_len and len(finished) == beam:
            bound = scores.max().item() / (((5.0 + max_len) / 6.0) ** alpha)
            if bound < finished[-1][0]:
                prefixes = prefixes[:0]
                break
    else:
        # max_len reached: the survivors are truncated hypotheses (no EOS), scored at length max_len
        for i in range(prefixes.shape[0]):
            finished.append((normalized_score(scores[i].item(), max_len, alpha), prefixes[i, 1:].tolist()))
    trim()
    return [(toks, s) for s, toks in finished]


def exhaustive_search(
    step_logprobs_fn: Callable[[Tensor], Tensor],
    bos: int,
    eos: int,
    max_len: int,
    length_penalty: float = 0.0,
    top_n: int = 1,
) -> list[tuple[list[int], float]]:
    results: list[tuple[float, list[int]]] = []

    def dfs(prefix: list[int], logp: float) -> None:
        row = step_logprobs_fn(torch.tensor([[bos] + prefix]))[0].to(torch.float64)
        for tok in range(row.shape[0]):
            lp = row[tok].item()
            if lp == NEG_INF:
                continue
            seq = prefix + [tok]
            if tok == eos or len(seq) == max_len:                # finished by EOS or truncated at max_len
                results.append((normalized_score(logp + lp, len(seq), length_penalty), seq))
            else:
                dfs(seq, logp + lp)

    dfs([], 0.0)
    results.sort(key=lambda h: -h[0])
    return [(toks, s) for s, toks in results[:top_n]]

The one test to memorize: causality

For any decoder-only code, feed a batch, rewrite the tokens from position \(k\) on with random ones, and compare the logits before \(k\). They must be bitwise equal:

def check_causal(model, idx, k=10, vocab=16):
    model.eval()
    with torch.no_grad():
        a = model(idx)
        idx2 = idx.clone()
        idx2[:, k:] = torch.randint(0, vocab, idx[:, k:].shape)   # rewrite the future
        b = model(idx2)
    return torch.equal(a[:, :k], b[:, :k])

On the fixed model this returns True; with the softmax-then-mask bug it returns False (the logits differ by about 0.06 at initialization, before any training). It also catches a forgotten mask, wrong polarity, a misaligned KV-cache path, and a packing mask that lets a document see later documents. It does not catch a packing mask that is merely causal across document boundaries (a later document reading an earlier one is not a future leak): perturb one document and check that the others' logits do not move.

A diagnosis order that works on real code

  1. Compare the loss with what is possible. You rarely know the floor on real data, but you know \(\ln V\) at initialization and roughly what a comparable model reaches. A loss far below that is a leak, never a success.
  2. Read the train/val gap. Train near zero with high val points at the training path (bug 2); both low points at the forward pass (bug 1).
  3. Log the pre-clip gradient norm. One number per step exposes bugs 3, 4 and 6, and later real loss spikes.
  4. Overfit one batch. A healthy loop drives the loss on one tiny batch toward zero; one that cannot has an optimization bug.
  5. Run the property tests (causality, evaluation determinism, batch-size invariance) before hunting by eye.

    opt.zero_grad(set_to_none=True)
    loss.backward()
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)              # after backward, before step
    opt.step()
    if step % 100 == 99:
        model.eval()
        with torch.no_grad():
            vl = lm_loss(model(val), val)
        print(step + 1, loss.item(), vl.item())

What changed: the mask is applied to the scores as \(-\infty\) before the softmax (bug 1); lm_loss compares logits[:, :-1] with idx[:, 1:] (bug 2); zero_grad runs each step before backward (bug 3); the loss is a token mean, the default (bug 4); validation switches to eval() under no_grad and returns to train() at the top of the next step (bug 5); clip_grad_norm_ sits between backward and step (bug 6). With mixed precision, gradients must also be unscaled before the clip, so the order there is backward, unscale, clip, step.

Common misconceptions

  • "Coding rounds test whether you remember the code." They usually test whether you produce correct code and can defend it. Recited code fails at the first follow-up ("now with a KV cache", "now in bf16").
  • "It passes my example, so it is right." One example cannot see mask polarity, an off-by-one, or a broadcast that misbehaves only on square inputs. Test properties, with dimensions that are all different.
  • "A lower training loss means a healthier run." A loss below what the data allows is a leak. In the debug exercise the leaky loop reports 0.000 while the honest validation loss is about eleven.
  • "The LayerNorm backward is the RMSNorm backward plus a bias gradient." LayerNorm has an extra \(-\bar u\) term from the mean, and its input gradient sums to zero. Dropping the term passes every shape check.
  • "Beam search returns the highest-probability sequence." Only if nothing is pruned. Otherwise it returns a good sequence, and the winner among finished hypotheses depends on the length penalty and on conventions (does EOS count toward the length?).
  • "Normalize by length at every step." Inside a step all candidates have the same length, so it changes nothing, and carrying the normalized value forward corrupts the next step's sums. Normalize only to compare finished hypotheses.
  • "With Adam, the reduction and the clip do not matter." They barely move a smooth loss curve but matter for spikes, accumulation, logging and other optimizers. A bug with no symptom on one run is still a bug.
  • "Gradcheck works in float32." It perturbs by \(10^{-6}\) and needs float64 to resolve the difference.

Warm-up What is wrong with this softmax, and which inputs expose each problem? 
def softmax(x):                 # x: (B, V)
    e = torch.exp(x)
    return e / e.sum(-1)

Two bugs. sum(-1) drops the axis, so \((B,V)/(B,)\) divides column \(j\) by row \(j\)'s sum: an error for most \(B\ne V\) (\(B=1\) happens to work), silent when \(B=V\) (a random \(4\times4\) input gave row sums 0.47, 1.69, 1.20, 1.99). Fix: keepdim=True. And there is no max subtraction: \(\exp\) overflows above about 88.7 in float32 and 11.09 in float16, then inf/inf is NaN. Subtracting the row max leaves the result unchanged. Tests: a non-square input against torch.softmax; logits of 1000 stay finite; rows sum to one; \(-\infty\) entries get probability 0; a fully \(-\infty\) row needs an explicit rule, because \(-\infty-(-\infty)\) is NaN.

Core A bf16 RoPE model matches the reference below about 256 tokens and diverges after. Why? 
angles = pos.to(x.dtype)[:, None] * inv_freq[None, :]     # x is bf16

bf16 has 8 significant bits, so integers are exact only up to 256. Above that positions are rounded: 257 becomes 256, 259 becomes 260, 1001 becomes 1000 and 100,000 becomes 99,840 (checked with torch.bfloat16). Neighbors can share a position, which corrupts the relative offsets RoPE depends on, with an error that grows with position. Core What is wrong with this GRPO advantage? 
adv = (rewards - rewards.mean()) / rewards.std()     # rewards: (P * G,), verifier rewards in {0, 1}

It normalizes over the whole batch instead of inside each prompt's group of \(G\) samples: an easy prompt whose samples are all correct gets a positive advantage against the batch mean, though its samples say nothing about which answer is better. And a group with identical rewards has zero standard deviation, so per-group normalization gives \(0/0\) without an \(\epsilon\). Fix: r = rewards.view(P, G); adv = (r - r.mean(1, keepdim=True)) / (r.std(1, keepdim=True) + eps). torch.std divides by \(G-1\), the drill's convention; Dr. GRPO drops the division (page 24). Tests: a uniform group gives exactly zero, groups are independent, each group's advantages have mean zero.

Core Find the three bugs in this beam search. Which tests catch each? 
def beam_search(fn, bos, eos, beam, max_len, alpha):
    seqs = torch.full((beam, 1), bos)                     # (beam, 1)
    scores = torch.zeros(beam)
    for t in range(1, max_len + 1):
        logp = fn(seqs)                                   # (beam, V)
        cand = (scores[:, None] + logp) / ((5 + t) / 6) ** alpha
        scores, idx = cand.flatten().topk(beam)
        parent, tok = idx // logp.size(1), idx % logp.size(1)
        seqs = torch.cat([seqs[parent], tok[:, None]], dim=1)
    return seqs[0, 1:].tolist()
  1. \(b\) copies of BOS. The rows are identical at step 1, so the top-\(b\) takes the same best token from each and the beam stays \(b\) duplicates: greedy decoding in disguise. On the drill's toy model with beam 2 and \(\alpha=0\) it returns abEOS (probability 0.2104) instead of bEOS (0.22). Catch: the first model call has one row; beam 2 finds bEOS.
  2. Normalizing inside the loop. scores becomes a normalized value and the next step adds a raw log-probability to it, mixing scales. Catch: wide-beam agreement with exhaustive search for \(\alpha>0\).
  3. No EOS handling. EOS is an ordinary token: hypotheses continue past it, finished ones are never recorded or compared, and the result is the best live row at max_len. Catch: no prefix containing EOS is fed back; returned hypotheses end with EOS or have length max_len.

Also: topk(beam) fails when the beam exceeds the candidate count (use min), and \(-\infty\) log-probs must not enter the beam. A single-answer test at \(\alpha=1\) on this toy passes by luck, because the duplicated greedy path abEOS is also the \(\alpha=1\) winner. Pick cases where the bugs give different answers.

Core Write a test for your LayerNorm backward that does not use autograd.

Use properties of the answer. (1) Shift invariance: \(\sum_j dx_j=0\) in every row, for any \(\delta\) and \(\epsilon\); it catches a dropped \(-\bar u\) term. (2) Scale invariance: at \(\epsilon=0\), \(\sum_j dx_jx_j=0\) for LayerNorm and RMSNorm (RMSNorm's row sum is not zero, and the test should assert that). (3) Directional finite differences in float64: for a random \(v\), \(\big(L(x+hv)-L(x-hv)\big)/2h\approx\langle dx,v\rangle\) with \(L=\sum\delta\odot y\), \(h=10^{-6}\). (4) Reductions: \(d\beta=\sum_{\text{rows}}\delta\), \(d\gamma=\sum_{\text{rows}}\delta\odot\hat x\), shape \((d,)\) for 1-D, 2-D and 3-D inputs. (5) Locality: changing \(\delta\) in one row leaves other rows' \(dx\) unchanged. (6) Two backward calls with the same cache agree. The drill's tests include all of these beside the autograd comparison.

Deep-dive Calculate the cost of beam search with \(b=4\) on Llama-3-8B at 2K context, and what the cache reorder adds.

Decode is memory-bound, so estimate bytes over bandwidth (H100 SXM, 3.35 TB/s, as on page 34). Weights: \(8.03\text{B}\times2\) B \(=16.06\) GB, read once per step at any batch. KV: \(32\cdot2\cdot8\cdot128\cdot2=131{,}072\) B per token, so one sequence at 2,048 tokens reads 0.268 GB and the step takes \((16.06+0.27)/3350=4.87\) ms. Four hypotheses read 1.07 GB: \((16.06+1.07)/3350=5.11\) ms, 4.9% slower, the same as four independent samples. If the reorder copies the whole cache each step (read plus write, \(2\times1.07\) GB), the step moves 19.28 GB and takes 5.76 ms, 18% slower than one sequence. With a paged cache the reorder is a block-table update plus copy-on-write of the newest block, so the extra cost is near zero (page 17). Caveats: this ignores compute, and once batching makes the model compute-bound, four hypotheses cost four times the FLOPs and occupy four batch slots, so per-request throughput falls about fourfold.

Deep-dive Estimate the time of a fused LayerNorm backward for 8,192 tokens at \(d=4096\) in bf16, and describe the kernel.

Traffic per element: read \(x\) (2 B), read \(\delta\) (2 B), write \(dx\) (2 B), so 6 B, plus 8 B of mean and rstd per row. Total \((6\cdot4096+8)\cdot8192\approx201\) MB, about \(60\ \mu\)s at 3.35 TB/s. Arithmetic is roughly 13 FLOPs per element (recompute \(\hat x\), \(u\), two reductions, the correction, the \(d\gamma\) and \(d\beta\) accumulations): \(4.4\times10^8\) FLOPs, about 2 FLOPs per byte against a machine balance near 295, so the kernel is bandwidth-bound and the traffic estimate is the answer. Design: one program per row, so both reductions for \(dx\) stay in registers and \(x\) is read once; float32 statistics; \(\hat x\) recomputed from \(x\), mean and rstd. \(d\gamma\) and \(d\beta\) sum across rows, so accumulate partial sums per group of rows into a small buffer (locks, atomics or two levels) and finish with a second small reduction kernel, as the Triton tutorial does [Triton tutorial 05]. Fusing means one pass over \(x\) and \(\delta\) instead of one per elementwise op.

Deep-dive A run shows training loss 0.3 after 2,000 steps and validation loss 3.1. Give three hypotheses in order and a test for each.

(1) Leakage in the training path: unshifted or misaligned labels, softmax before the mask, a packing mask that lets a document see later documents, wrong mask polarity. Tests: the loss at initialization is near \(\ln V\); the causality test; a loss on shuffled targets rises to about \(\ln V\); per-position loss (a leak often collapses the loss at every position, memorization does not). If validation shares the leaky forward path, it looks fine too, as bug 1 above showed. (2) Contamination or duplication that makes training easier than validation: identical documents across shards, many repeated epochs. Test: deduplicate against validation, count unique versus seen tokens, and measure loss on fresh data from the same source. (3) Real memorization of a small dataset by a large model. Test: unique tokens against parameters and steps; validation loss falls, then rises. Order by cost: the first tests take minutes and rule out the causes that invalidate the whole run.

Deep-dive The LayerNorm input gradient is orthogonal to the input. What does the same fact imply for the weights that feed a normalization layer?

Take \(y=\mathrm{LN}(xW)\) with \(\epsilon=0\). Scaling \(W\) by \(c>0\) scales \(xW\) and leaves \(y\) unchanged, so \(L(cW)=L(W)\). Differentiating in \(c\) at \(c=1\) gives \(\langle\nabla_W L,W\rangle=0\), the same orthogonality as \(\sum_j dx_jx_j=0\). For plain SGD, a step \(W\leftarrow W-\eta\nabla L\) has \(\|W'\|^2=\|W\|^2+\eta^2\|\nabla L\|^2\), so the weight norm only grows; and since \(\nabla L\) scales like \(1/\|W\|\), the effective step on the direction of \(W\), roughly \(\eta/\|W\|^2\), shrinks as the norm grows. Weight decay counteracts the growth, and the pair sets an equilibrium effective learning rate. Adam sets update size per coordinate, not by gradient scale, so the details change, though the norm still drifts and the effective rate still depends on it. That is why a norm layer changes how learning rate and weight decay interact. Treat the SGD statements as the derivation and the Adam statement as qualitative.
